Use the bundled Firebase Analytics helper to enable collection while your
app's measurement permission is granted. Pending or denied permission disables
collection. The helper also sends Firebase's consent settings and keeps all
advertising permissions denied.

The helper is included in `C15tApple`, `c15t-android` and
`@c15t/react-native/integrations`. Firebase remains a dependency your app
installs. Adding c15t does not add Firebase to the app.

For browser analytics, follow the [Google Tag integration](/docs/integrations/google-tag).
This page covers Firebase Analytics in native mobile apps.

## Before you start

Complete the [Swift](/docs/frameworks/swift/quickstart),
[Android](/docs/frameworks/android/quickstart) or
[React Native](/docs/frameworks/react-native/quickstart) quickstart. Your Inth
policy and native configuration must include `measurement`, or the optional
category you choose for analytics. Use the same installed engine for the
consent screens and the integration.

Add Firebase through its official [Apple](https://firebase.google.com/docs/ios/setup),
[Android](https://firebase.google.com/docs/android/setup) or
[React Native Firebase](https://rnfirebase.io/analytics/usage) instructions.
Configure the Firebase app and Analytics module before connecting its APIs.
c15t's mobile packages are currently a private prerelease; see
[mobile availability](/docs/guides/mobile-status) for installation access.

This recipe is for analytics without Firebase advertising storage, advertising
user data or ad personalization. It does not grant IAB vendor permissions,
replace a Google Mobile Ads integration or request ATT. Use
[mobile IAB and ads](/docs/guides/mobile-iab) for advertising requirements.

## Control native startup first

Set Firebase's collection default to disabled in the app's native build
configuration. For iOS, add this Boolean to the app target's `Info.plist`:

{/* example: fragment */}

```xml title="Info.plist"
<key>FIREBASE_ANALYTICS_COLLECTION_ENABLED</key>
<false/>
```

On Android, add this metadata inside your manifest's existing `application`:

{/* example: fragment */}

```xml title="AndroidManifest.xml"
<meta-data
	android:name="firebase_analytics_collection_enabled"
	android:value="false" />
```

These are startup defaults. Firebase persists runtime collection settings, and
a previous runtime grant overrides the default on a later launch. Install
c15t and reconcile the vendor's collection permission in native startup before
optional collection can begin. Where your Firebase setup permits it, defer
vendor initialization until native permission allows it. Inspect any
automatically registered Android providers or app-delegate setup in that path.
[Firebase's collection guide](https://firebase.google.com/docs/analytics/configure-data-collection)
explains the persisted setting.

For React Native and Expo, a JavaScript connection runs after native startup.
It cannot prevent earlier Firebase collection. Apply the native settings
through the vendor's supported build configuration and keep the
[native startup gate](/docs/frameworks/react-native/native-behaviour). Expo
needs a custom native build containing both packages. c15t's config plugin
does not configure Firebase, and Expo Go cannot load this integration.

## Connect a Swift app

Create `FirebaseAnalyticsOwner.swift` in your app target. This owner retains
the bundled helper and exposes teardown and reset synchronization:

<include src="../shared/examples/native/core-swift/AppleInstallation/swift-firebase-analytics-binding.mdx" />

After the native c15t engine and your Firebase app are installed, construct
the owner with Firebase's actual APIs. This fragment belongs in the app's
service setup; retain `firebaseOwner` as an app-lifetime property:

{/* example: fragment */}

```swift
import FirebaseAnalytics

let firebaseOwner = FirebaseAnalyticsOwner(
    core: core,
    setConsent: { consent in
        Analytics.setConsent([
            .analyticsStorage: consent.analyticsStorage ? .granted : .denied,
            .adStorage: .denied,
            .adUserData: .denied,
            .adPersonalization: .denied,
        ])
    },
    setCollectionEnabled: { Analytics.setAnalyticsCollectionEnabled($0) }
)
```

`core` is the `ConsentCore` returned by the app's installation. The helper
applies current permission before its initializer returns. Firebase callbacks
run synchronously on the registering thread or the thread publishing a native
consent change. Pass the vendor calls directly; dispatching them into separate
asynchronous tasks can reorder grants and withdrawals.

The owner uses `measurement` by default. For another optional category,
configure `category` on its `FirebaseAnalyticsIntegration` initializer. Keep
the owner alive across screen changes. Releasing it cancels the integration
and disables collection.

## Connect an Android app

Copy this helper into your app's Kotlin source directory, using your app's
package name:

<include src="../shared/examples/native/examples/consent-demo/android-firebase-integration.mdx" />

Call it from your `Application` service setup after installing c15t and
configuring Firebase. Map the helper's analytics permission to the Firebase
instance you actually use:

{/* example: fragment */}

```kotlin
import com.google.firebase.analytics.FirebaseAnalytics
import com.google.firebase.analytics.FirebaseAnalytics.ConsentStatus
import com.google.firebase.analytics.FirebaseAnalytics.ConsentType

val firebase = FirebaseAnalytics.getInstance(this)
val firebaseConsent = connectAppFirebaseAnalytics(
	setConsent = { consent ->
		firebase.setConsent(mapOf(
			ConsentType.ANALYTICS_STORAGE to
				if (consent.analyticsStorage) ConsentStatus.GRANTED else ConsentStatus.DENIED,
			ConsentType.AD_STORAGE to ConsentStatus.DENIED,
			ConsentType.AD_USER_DATA to ConsentStatus.DENIED,
			ConsentType.AD_PERSONALIZATION to ConsentStatus.DENIED,
		))
	},
	setCollectionEnabled = firebase::setAnalyticsCollectionEnabled,
	onError = ::reportAnalyticsError,
)
```

Retain `firebaseConsent` on the application or service owner. The native core keeps
applying consent until you call `close()`, even if the app drops the handle. Replace
`reportAnalyticsError` with an error handler that works while optional
analytics is disabled and does not throw. The required `onError` receives automatic update
failures. Construction, `sync()` and `close()` can also throw to their caller;
handle those failures in the app's service lifecycle.

Native callbacks run synchronously and are serialized per helper. Do not post
the vendor changes into independent jobs. The helper disables collection
before changing consent and enables it only while the category remains
allowed. A vendor failure means you cannot assume that the requested change
reached Firebase.

## Connect React Native or Expo

Copy the checked connection function into `firebase-consent.ts`:

<include src="../shared/examples/react-native-bare/rn-firebase-integration.mdx" />

In a separate `firebase-vendor.ts` file, supply React Native Firebase's modular
functions. This fragment assumes the installed Firebase app is the one
returned by `getAnalytics()`:

{/* example: fragment */}

```ts title="firebase-vendor.ts"
import {
	getAnalytics,
	setAnalyticsCollectionEnabled,
	setConsent,
} from '@react-native-firebase/analytics';

import { connectAppFirebaseAnalytics } from './firebase-consent';

export function connectFirebaseVendor(onError: (error: unknown) => void) {
	const analytics = getAnalytics();
	return connectAppFirebaseAnalytics(
		{
			setConsent: (settings) => setConsent(analytics, settings),
			setAnalyticsCollectionEnabled: (enabled) =>
				setAnalyticsCollectionEnabled(analytics, enabled),
		},
		onError
	);
}
```

Call `connectFirebaseVendor` once from app startup, retain its returned handle
and await `ready` inside your existing asynchronous startup function before
using Analytics. For example:

{/* example: fragment */}

```ts
const firebaseConsent = connectFirebaseVendor(reportAnalyticsError);
await firebaseConsent.ready;
```

The `onError` callback receives initial and later failures. `ready`, `sync()`
and `disconnect()` also reject when their vendor operations fail, so handle
those promises at their call sites. Keep the handle in an app-lifetime owner;
a route's effect should not disconnect app-wide analytics on navigation.

The connection serializes asynchronous Firebase calls and rereads native
permission before enabling collection. While permission is pending or denied,
it disables collection and sends denied consent. On a grant, it sends
analytics storage consent and enables collection. The three advertising
consent fields remain `false` on every update.

## Handle reset and teardown

If app code resets Firebase's settings, reapply current c15t permission after
the reset completes. Call `syncAfterReset()` on the Swift owner, `sync()` on
the Kotlin helper or `await firebaseConsent.sync()` in React Native. This
updates Firebase without recording a new consent choice.

For final service teardown, use the Swift owner's `stop()`, Kotlin's
`close()` or `await firebaseConsent.disconnect()` in React Native. These
detach the subscription and request collection disablement. They do not
delete historical Firebase data or retract requests already sent.

## Check the integration

Use Firebase's supported debug tools and inspect actual collection in your
app. Test a policy that asks for a choice:

1. Launch with no saved choice. Analytics collection stays disabled while
   native permission is pending and after Reject all.
2. Grant measurement. Confirm analytics storage is granted, the three
   advertising fields remain denied and collection becomes enabled.
3. Withdraw measurement. Confirm collection is disabled and analytics storage
   becomes denied.
4. Terminate and relaunch after both grant and refusal. Check native startup
   before JavaScript as well as the eventual SDK state.
5. Reset vendor settings, call `sync()` and confirm that current permission
   is reapplied without creating a consent record.
6. Exercise your vendor-failure handler and final teardown.

The c15t helper tests exercise native authority, lifecycle changes, reset and
callback ordering. The RN mapping was type-checked against React Native
Firebase 27.1.0; native mappings follow Firebase's published API references.
These checks do not establish real Firebase startup or network behavior on
your devices. Complete the [mobile verification](/docs/guides/mobile-verify)
steps with the Firebase versions and build configuration your app ships.
