Use the headless APIs when consent needs to fit your app's settings screen,
onboarding or design system. React renders your controls, while the native
engine keeps the policy, saved choices and SDK permissions.

## Start with the same native setup

Complete [Expo](/docs/frameworks/react-native/expo) or
[bare RN setup](/docs/frameworks/react-native/bare), then keep one
`ConsentProvider` above your app. You can omit the quickstart's `PrivacyEntry` if
your app owns both the initial prompt and the standing settings screen.
Without `PrivacyEntry`, your custom flow is responsible for showing an owed
prompt and keeping preferences reachable.

Headless hooks are included in `@c15t/react-native`. By default the build
also links the stock native screens. An app that draws all of its consent UI
can leave them out; see
[Build without the stock native screens](#build-without-the-stock-native-screens).

## Read one permission

For a feature that only needs measurement permission, use
`useConsent('measurement')`. It returns `false` while policy is unresolved
and whenever that category is denied. The component subscribes to that
permission, so unrelated snapshot changes do not rerender it.

Use `useConsentDecision('measurement')` when your interface needs to distinguish
`pending` from `denied`. Both keep optional collection off.

## Build a preferences screen with a draft

For a screen that collects several choices and saves them together, stage them
in a draft with `useConsentDraft()`. It uses the same names as the web
preference dialog's draft in `@c15t/react`. Edits stay in JavaScript until you
call `save()`, which records every displayed category in one commit:

<include src="../../shared/examples/react-native-bare/draft-preferences.mdx" />

`displayedCategories` lists the categories the resolved policy puts in scope,
`necessary` first. A category with a saved receipt starts at that choice. One
without a receipt starts at its effective permission. The draft shows the
subject's own choices, so a GPC restriction does not appear as a staged
refusal. `isDirty` tells you whether anything changed. `acceptAll` and
`rejectAll` stage values only; they save nothing.

While the draft has no edits, it follows the saved record. While it has
edits, a category you did not change still takes the newly saved value, so a
save writes back only what the subject changed. A save through
`useSaveConsents()` with `'all'`, `'none'` or a per-category object clears the
edits the draft held when the save began; an edit made while a save is pending
stays staged. If the policy or
the displayed categories change under an unsaved edit, `isStale` turns true and
`save()` resolves `ok: false` with `reason: 'concurrent-change'`, writing
nothing. Call `reset()` and let the subject review again.

Every component outside a `ConsentDraftProvider` shares one draft, so a Save
button elsewhere on the screen can call `useSaveConsents()()` with no argument,
as on the web. Wrap a screen in `ConsentDraftProvider` to give it a draft of its
own; its `initial` prop sets values for categories that have no receipt yet.

Effective permission is different from an explicit saved choice. An opt-out
policy may allow a category before anyone uses the switch. Read
`snapshot.explicitChoice` when you need to display whether a choice was
recorded. Do not submit a save merely because the initial effective value is
true.

Use this form with category policies. For a TCF policy, see
[Build your own IAB screen](#build-your-own-iab-screen).

## Build your own IAB screen

Under a TCF policy the same draft holds a purpose and vendor selection. The
hooks use the names `@c15t/react` exports for IAB: `useIAB()` stages changes,
`usePurposeConsent`, `useVendorConsent` and `useSpecialFeatureOptIn` read the
staged selection, and `useTCString()` reads the committed TC String:

<include src="../../shared/examples/react-native-bare/iab-preferences.mdx" />

`useIAB()` returns `null` unless the policy is `iab`, a vendor list was served
and native can open a draft now. `useIABSnapshot()?.editable` is `false` while
the list is stale or offline or a required Additional Consent list is missing;
show the committed decision, call `useConsentActions().refresh()` and offer
controls again once it turns `true`. A binary built before this release also
reads `false`, because it cannot commit a headless selection. The draft opens
with the committed choices, or with nothing granted.
`save()` sends the whole selection and the displayed categories as one native
commit, pinned to the snapshot revision the draft was opened on. The native
core checks every ID and legal basis against the served list, encodes the TC
String, writes the `IABTCF_*` keys and queues the backend record, exactly as it
does for the stock screens. A refused selection resolves `ok: false` with the
reason. If the vendor list or policy changed under an unsaved edit, the draft
turns stale and refuses to save until you call `reset()`.

`acceptAll()` stages exactly what native Accept all saves: the core projects
every live partner's bases under your disclosure and publisher restrictions,
and every displayed category is granted, so the headless and stock buttons
record the same signals. `rejectAll()` stages withdrawal of every consent and
a denial for every displayed category, and leaves legitimate interest alone,
as on the web. A first decision opens with every consent off and the disclosed
legitimate interests not objected to, as the stock screens open it. For one-tap buttons, `useSaveConsents()('all')` and `('none')` save
without staging. `setPurposeLegitimateInterest` and
`setVendorLegitimateInterest` with `false` record an objection; purposes 1 and
3 to 6 never take legitimate interest.

The snapshot carries the served vendor list as published, not the native
disclosure projection. When your configuration sets publisher restrictions or
the policy lists Additional Consent providers, the raw list does not show the
legal bases your app discloses, and it does not name the providers
`setAdTechProviderConsent` saves. In that setup, keep the stock screens for
the disclosure layer; the headless hooks can still stage and save the choice.

The staged values are for rendering controls. Gate vendors on the committed
decision, which native SDK gates and `IABTCF_*` readers already use.
`useIABSnapshot()` returns the served vendor list for your disclosure text and
the committed decision; `useIABEnabled()` tells you whether the policy is TCF.
Keep the TCF disclosures, the partner count and your privacy-policy link on
the screen, as the [IAB setup](/docs/guides/mobile-iab) guide requires.

## Handle accept, reject and save failures

Use `useSaveConsents()` for explicit button actions. The function it returns
takes `'all'`, `'none'` or a per-category object, or no argument to save the
current draft, and resolves with a local `CommitResult`; check `ok` before
dismissing your form. This reusable Reject button keeps a retry path on failure:

<include src="../../shared/examples/react-native-bare/commit-results.mdx" />

Use `onSaved` to close your app-owned screen after durable local success.
Pending network delivery does not require leaving the form open. Read
[commands and outcomes](/docs/frameworks/react-native/usage) for the result
fields and presenter APIs.

## Show your own first prompt

`ConsentPrompt` calls its child only while a resolved policy requires an
interaction. The child receives `activeUI`, `promptRequirement` and `actions`.
Use `promptRequirement.kind` to distinguish a consent `choice` from a
`notice`; the `none` case renders the fallback.

For a category choice, wire your Accept, Reject and Save controls to the
corresponding actions and handle their results as above. For a notice,
`dismissNotice()` records acknowledgement. It does not record an optional
consent grant. Keep the policy disclosures and your privacy-policy link in the
custom prompt.

Use `ConsentReady` around UI that needs a resolved policy. Its fallback renders
until `ready` is true and `policyPending` is false. It does not need to wrap the
whole app; necessary features can remain usable while consent is loading.

Keep `start` stable, for example as a module-level function. Its cleanup must
stop or disable collection using the vendor's supported API. A hook cannot
reverse a native initializer that ran before JavaScript; disable that path
and use [native startup gates](/docs/frameworks/react-native/native-behaviour)
as well.

The tracking variant combines category permission with platform authorization.
It is for features that require both. It does not ask for authorization.

## Choose a subscription

| API | Use it for |
| --- | --- |
| `useConsent(category)` | One effective permission. |
| `useConsentDecision(category)` | A permission with `pending`, `denied` and `granted` states. |
| `useConsentStatus()` | Readiness, pending policy, active UI and owed prompt. |
| `useConsentSelector(selector, equals?)` | A custom snapshot slice with optional equality. |
| `useSnapshot()` | A screen that needs several snapshot fields, such as scope and restrictions. |
| `useSaveConsents()` | Save `'all'`, `'none'`, a per-category choice, or the current draft. |
| `useConsentDraft()` | Stage several category choices and save them together. |
| `ConsentDraftProvider` | A separate draft for one screen, with defaults for undecided categories. |
| `useIAB()` | Stage and save a TCF purpose and vendor selection. |
| `usePurposeConsent(id)`, `useVendorConsent(id)`, `useSpecialFeatureOptIn(id)` | One staged TCF selection, for a control. |
| `useTCString()` | The committed TC String. |
| `useIABSnapshot()`, `useIABEnabled()` | The served vendor list and committed decision, and whether the policy is TCF. |
| `useDismissNotice()` | Acknowledge a notice without recording a choice. |
| `useIdentify()` | Attach an external id from your account system. |
| `useSetOverrides()` | Pin country, region, language or GPC for testing. |
| `useConsentActions()` | Stable `refresh`, `logout`, `reset` and `requestTrackingAuthorization` commands. |
| `useC15tBootstrap()` | The native protocol and subject bootstrap payload, and `nativeUI`, whether the stock native screens are linked. |
| `ConsentGate` | Render-prop content for an allowed category, with an optional fallback. |
| `ConsentReady` | Render-prop content after native readiness and policy resolution. |
| `ConsentPrompt` | Your initial prompt while an interaction is owed. |
| `useTrackingAuthorization()` | The separate platform tracking status. |
| `useIsTrackingAllowed(category)` | A category permission combined with platform tracking authorization. |

## Build without the stock native screens

When your app draws its banner, preferences and IAB screens with the hooks
above, leave the SwiftUI and Compose screens out of the binary. In Expo, set
`nativeUI: false` in the config plugin options:

{/* example: fragment */}

```ts title="app.config.ts plugin options"
nativeUI: false,
```

Prebuild then writes `c15t.nativeUI` as `false` to `ios/Podfile.properties.json`
and `android/gradle.properties`. In a bare app, add `c15t.nativeUI=false` to
`android/gradle.properties`, and either add `"c15t.nativeUI": "false"` to
`ios/Podfile.properties.json` or run `C15T_NATIVE_UI=0 pod install`. Run
`pod install` and rebuild both apps after changing it.

The iOS pod then compiles without the SwiftUI screens, and the Android build
drops the `c15t-consent-ui` dependency. The consent engine, IAB encoding,
storage and SDK gates stay. `useC15tBootstrap().nativeUI` reads `false`, and
`presentConsentPrompt` and `presentPreferences` reject with
`C15T_NATIVE_UI_EXCLUDED`. Check that value before anything asks native to
present a screen. The plugin refuses `nativeUI: false` together with `theme`,
because the theme would style screens the build leaves out; pass that object to
`createConsentTheme` instead.

Your app must then show the owed prompt itself, for example with
`ConsentPrompt`, and keep a privacy settings entry that opens your own
preferences screen.

## Check the custom flow

Test both a fresh prompt and reopened settings. Confirm that a refused save
keeps the control's old value, a successful change survives relaunch, and
withdrawal stops optional work. Test larger text, focus, labels and error
announcements as part of your app's accessibility checks.

For IAB, check the decoded TC String and the platform `IABTCF_*` keys after a
save, as described under [IAB setup](/docs/guides/mobile-iab).
