Inth matches each visitor to a regional policy rule in your project, deciding the permission model, prompt type, category scope, and privacy controls without branching in your app code.

## What a policy rule controls

Your app reads the resolved rule and `effectivePermissions`. Do not swap rules in client code just to hide a banner.

| Policy setting | Behavior |
| --- | --- |
| `model: 'opt-in'` | Optional categories in scope stay denied until the visitor grants consent. |
| `model: 'opt-out'` | Categories in scope start allowed. Saved refusals and privacy signals such as GPC can restrict them. |
| `model: 'iab'` | Categories and vendors follow IAB TCF 2.4 purpose consent, legitimate interest, and TC string rules. |
| `model: 'none'` | Categories in scope run without an initial prompt. Stock consent UI stays hidden unless the rule grants privacy rights. |
| `prompt: 'choice'` | Shows a banner asking for a decision whenever a choice is missing, expired, or invalidated by a policy update. |
| `prompt: 'notice'` | Shows a dismissible notice. Dismissing records an acknowledgement, not consent. |
| `prompt: 'none'` | Shows no automatic banner on load. The rule can still require a preferences entry point. |
| `scopeMode: 'strict'` | Denies optional categories outside the rule's configured category list. |
| `scopeMode: 'permissive'` | Allows out-of-scope categories unless another restriction applies. |
| Regional matching | Matches visitors by country and region or state, with a fallback rule for unknown locations. |
| Privacy rights | Controls persistent preferences access so visitors who rejected tracking or dismissed a notice can change their mind later. |

Keep a persistent preferences link or trigger wherever the resolved rule grants that right. Stock Inth components check the rule's rights automatically; custom UI must do the same.

Gate scripts and embeds with `effectivePermissions`, not `explicitChoice`. Under an opt-out rule, `effectivePermissions` can be `true` before the visitor clicks anything. See [a permission is not a recorded choice](/docs/concepts/how-consent-works#a-permission-is-not-a-recorded-choice).

## Where rules live

Define and publish policy rules in your [Inth](https://inth.com) project. Your app receives those rules through your configured [data-fetching path](/docs/concepts/data-fetching), either bundled at build time or fetched at runtime.

App styling, component props, and browser-side imports do not override your hosted Inth policy. Policy presets are starting templates, not legal advice. Review each rule's model, categories, and expiry against your actual data processing before allowing optional categories by default.

## Test policies locally

To test regional behavior locally or in automated tests without network calls, pass `testing()` from your framework package's `/testing` entry along with location `overrides`:

- `overrides: { country: 'DE' }` or `'GB'` matches an opt-in banner in the built-in rule pack.
- `overrides: { country: 'DE' }` with IAB enabled matches the IAB TCF banner.
- `overrides: { country: 'US', region: 'CA' }` matches an opt-out rule with no automatic banner.
- `overrides: { country: 'JP' }` matches a no-prompt `none` rule.
- An omitted or unknown country uses the pack's strict opt-in fallback. A US country without a state uses the US opt-out fallback.

Pass `testing({ policy })` with custom `PolicyRule` objects to test rules the default pack does not include, such as `prompt: 'notice'`. These defaults belong to the local test pack, not your live Inth project. See [testing()](/docs/concepts/modes#testing) for examples.

## Why the banner may be absent

A missing banner can be the expected result of a policy rule or an initialization error. Always inspect `resolution.status` before reading `policyRule` or `model`.

| Snapshot state | Cause and what to inspect |
| --- | --- |
| `resolution.status === 'matched'` and `promptRequirement.kind === 'none'` | The matched rule needs no initial prompt, or stored records already satisfy it. Check persistent preferences separately. |
| `resolution.status === 'matched'` and a category is denied | Inspect `effectivePermissions`, `explicitChoice`, `privacySignals`, and `restrictions`. A saved refusal, strict scope, or live GPC signal can keep a category denied even with no banner. |
| `resolution.status` is `'no-match'`, `'failed'`, or `'unconfigured'` | Policy resolution did not match. Check your Inth `projectUrl`, network connectivity, location headers, and project policy configuration. Optional categories stay denied until a policy matches. |

Do not treat `policyRule` alone as proof that your policy loaded. While resolution is pending or after it fails, the snapshot populates `policyRule` with a strict opt-in fallback so optional code stays blocked. Read `resolution.policy` only when `resolution.status === 'matched'`.
