Inth separates where a policy resolves from where choices are saved. Every path below reads policy configuration from your Inth project and saves choices to Inth, except `testing()`.

## Compare the fetching paths

| Fetching path | Where policy resolves | Where choices go | Choose it when |
| --- | --- | --- | --- |
| Build-time manifest | Your server, from a build snapshot | Inth | You run SSR and policy edits can ship with a rebuild. |
| Runtime cached manifest | Your server, caching `/v1/consent/manifest` | Inth | Policy edits must apply without rebuilding. |
| Hosted `/v1/consent/init` | Inth `/v1/consent/init` | Inth | You build a React, Vue, or Svelte SPA or static site with no app server. |
| Browser manifest | Browser, with supplied location or `/v1/consent/init` fallback | Inth | Your policy has no location rules or your edge host injects `{ country, region }`. |
| `testing()` | Browser, from local test rules | Nowhere | Local and automated tests only. Throws in production builds. |

Find your framework's recommended path in [choose your setup](/docs/concepts/choose-your-setup). Compare latency and bundle impact in [performance](/docs/performance).

## What is a consent manifest?

A consent manifest is a versioned public JSON document served by `GET ${projectUrl}/v1/consent/manifest`. It holds your project's policy rules, translations, and consent configuration. It contains no secrets, no visitor identifiers, and no saved consent records.

A resolver combines that public manifest with each visitor's country, region, language, and privacy signals to produce an init result per request. Because the manifest is public, your build or server reuses one copy across all visitors instead of calling `/v1/consent/init` on every page load.

Keep personalized init responses out of shared caches. After editing policies, translations, or vendors in Inth, rebuild build-time apps or wait for runtime caches to revalidate. See [download the manifest at build time](/docs/concepts/modes#download-the-manifest-at-build-time) and [what happens when the download fails](/docs/concepts/modes#what-happens-when-the-download-fails).

## Session counting

Inth counts visitor sessions from `/v1/consent/init` requests. Because server-side manifest resolution skips `/v1/consent/init`, server adapters post a session report to `POST ${projectUrl}/v1/consent/sessions` after the page response finishes.

The browser sends no request for this report, and the payload stores no visitor identity. Visitor IP and user agent follow standard Inth privacy handling. Static sites resolving manifests in the browser send no session report.

## Link an init to the save that follows

Inth attaches a random UUID journey ID to link each initialization with the consent save that follows:

| Request | Journey fields |
| --- | --- |
| `/v1/consent/init` | Query parameters `journey`, `journeyScope`, and `stored` set to `1` when a stored choice or notice dismissal exists |
| `POST /v1/consent/records` | Query parameters `journey` and `journeyScope` |
| `POST /v1/consent/sessions` | JSON field `journey: { id, scope, storedChoice, prompt, domain }` |

`prompt` is `'due'`, `'stored'`, or `'not-required'`. A stored answer counts as `'stored'` even when a policy update triggers a new prompt. The journey ID is random, never equals the subject ID, and is never stored in a cookie. Offline save replays omit it.

| `journey` option | Behavior |
| --- | --- |
| `'page'` | Default. One journey ID per page load, kept in memory. |
| `'tab'` | Stored in `sessionStorage` while a prompt is due and cleared once the visitor chooses or no prompt is due. Browser-resolved init only; SSR pages use `'page'`. |
| `false` | Disables journey IDs. |

Set `journey` on your runtime or provider: `defineConsentConfig({ journey })` in Next.js, matching values on `resolveConsent` and `InthProvider` in TanStack Start, or `buildPrefetchScript` and `consentManifest({ initPrefetch: { journey } })` for head prefetching. Vue, Svelte, Astro, and the script tag use `'page'`. Browser-only manifest resolution without `/v1/consent/init` sends no journey ID. If you pass a custom `fetch` to `hosted()`, match on URL pathname because requests include query parameters.

## Hosted `/init` and head prefetching

`hosted()` resolves policies through `GET ${projectUrl}/v1/consent/init` and posts choices to `POST ${projectUrl}/v1/consent/records`.

{/* example: fragment */}

```ts title="inth.config.ts"
import { defineConsentConfig, hosted } from '@inth/nextjs';

export default defineConsentConfig({ mode: hosted() });
```

See [import the factories from your framework package](/docs/concepts/modes#import-the-factories-from-your-framework-package) for where each framework passes `mode`.

In browser-resolved apps, an inline `<head>` script starts `/v1/consent/init` while your bundle downloads so `hosted()` reuses the response. Vite apps add this through `consentManifest()` by default, Nuxt injects it on `ssr: false` pages, and TanStack Start exports `consentPrefetchHead`. Elsewhere, render `buildPrefetchScript({ projectUrl })` from your package's `/engine` entry, such as `@inth/react/engine`. Pass the same `experiment` config to the prefetch script when running banner experiments so `hosted()` does not send a second `/v1/consent/init`.

## Same-origin proxy

A proxy routes browser consent HTTP requests through your own origin, such as `/api/inth`, instead of directly to `https://your-project.inth.app`. This removes an extra browser DNS lookup and TLS handshake. Your app server still connects to Inth for manifest refreshes and consent writes, and vendor scripts keep their own origins.

Server-rendered frameworks enable proxying with `proxy: true` and a consent route like `routePrefix: '/api/inth'`. Every framework rejects `routePrefix: '/'` so the route cannot shadow your site root. See the [Next.js proxy recipe](/docs/frameworks/next/optimization#keep-browser-consent-requests-on-your-origin).

In an SPA with a reverse proxy at `/api/inth` and a manifest-backed init endpoint, separate init and write paths with `initUrl`:

{/* example: fragment */}

```ts title="src/consent-mode.ts"
import { hosted } from '@inth/sdk/engine';

export const mode = hosted({
	projectUrl: '/api/inth',
	initUrl: '/api/inth/v1/consent/init',
});
```

Setting `initUrl` appends Inth query parameters to `initUrl` and defaults `assertDecisionInputs` to `true`, attaching decision inputs on saves when init returned no signed policy snapshot token. Static exports cannot serve runtime routes or rewrites; use your absolute Inth `projectUrl` or a proxy at your static host.

## Verify your fetching path

Inspect server logs and the browser Network panel separately, because server manifest fetches never appear in browser DevTools:

- **Build-time manifest.** Confirm zero upstream `/v1/consent/manifest` calls on page load. Edit a policy in Inth, rebuild, and confirm the change appears.
- **Runtime manifest.** Confirm page loads skip `/v1/consent/init`, choices reach `/v1/consent/records`, and policy edits appear after cache revalidation.
- **Same-origin proxy.** Confirm browser consent requests hit only `/api/inth/*` and verify upstream forwarding in server logs.
- **Edge cases.** Test region overrides, missing geo headers, GPC, saved choices, and network failures. See [verify consent](/docs/guides/verify-consent).
