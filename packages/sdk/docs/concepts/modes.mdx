## Set the backend, then choose a mode if you need to

Every Inth provider needs `projectUrl`: your Inth project URL, such as
`https://your-project.inth.app`. Consent choices are saved there. Most apps
set nothing else; `mode` is optional.

| Mode | Where the policy resolves | Backend requests on a first visit | Default in |
| --- | --- | --- | --- |
| `manifest()` | Your server, from the policy the build downloaded. With `resolve: 'browser'`, or in a single-page app, the browser. | None to resolve the policy, unless the browser needs a location it doesn't have. Choices post to `/v1/consent/records`. | Next.js, TanStack Start, Nuxt, SvelteKit, Astro, and Angular with `provideInthServer()` |
| `hosted()` | The backend's `GET /v1/consent/init` | One `/v1/consent/init` per page that resolves consent. | React, Vue, Svelte, Angular in the browser, `@inth/sdk` and the script tag |
| `testing()` | The browser, from a policy you pass or the recommended rule pack | None. | Never: import it from a package's `/testing` entry, in tests only |

Leave `mode` out unless you need something other than your framework's
default. Pass `hosted()` to make a server-rendered framework ask `/v1/consent/init` for
every visitor, or `manifest()` to tune how the manifest is read.

`manifest()` falls back to the backend's `/v1/consent/init` when the manifest is
unavailable: the build could not download it, the backend has no
`/v1/consent/manifest`, or reading it fails at runtime. Inth logs a warning and the
visitor still gets a banner. A configuration error, such as an invalid
`manifestUrl`, stays an error.

`projectUrl` is required unless `mode` is `testing()` or `enabled` is
`false`. TypeScript asks for it, and a provider without one throws one error
that names the option. Server-rendered frameworks also read it from an
environment variable; see [set the backend URL](#set-the-backend-url).

[Data fetching](/docs/concepts/data-fetching) compares these paths with
same-origin proxies.

## Import the factories from your framework package

There are two kinds of factory, and each framework package exports the kind
it needs.

| Framework | Import `manifest()` and `hosted()` from | `testing()` from | Pass the mode to | Kind |
| --- | --- | --- | --- | --- |
| Next.js | `@inth/nextjs` | `@inth/nextjs/testing` | `mode` in `inth.config.ts` | Data |
| TanStack Start | `@inth/tanstack-start` | `@inth/tanstack-start/testing` | `resolveConsent({ mode })` | Data |
| Nuxt | `@inth/nuxt` | `@inth/nuxt/testing` | `inth.mode` in `nuxt.config.ts` | Data |
| Astro | `@inth/astro` | `@inth/astro/testing` | `inth({ mode })` in `astro.config.mjs` | Data |
| SvelteKit | `@inth/svelte/kit` | `@inth/svelte/testing` | `inthHandle({ mode })` in `src/hooks.server.ts` | Data |
| React | `@inth/react` | `@inth/react/testing` | `ConsentProvider`'s `options.mode` | Transport |
| Vue | `@inth/vue/vue-plugin` | `@inth/vue/testing` | `app.use(inthVue, { mode })` | Transport |
| Svelte | `@inth/svelte` | `@inth/svelte/testing` | `<ConsentProvider mode={...}>` | Transport |
| Angular | `@inth/angular` | `@inth/angular/testing` | `provideInth({ mode })` | Transport |
| JavaScript | `@inth/sdk` | `@inth/sdk/testing` | `init({ mode })` | Transport |
| Script tag | none | `inth.testing.js` | `data-mode="manifest"` on the headless and IAB scripts | Name |

**Data factories** return a plain object such as `{ type: 'manifest' }`.
Server-rendered frameworks read their config on the server and in the
browser, and Nuxt and Astro serialize it, so the mode has to be data. The
framework turns it into a transport in the browser and loads the code of
any mode other than the default with `import()`. The same factories are
available from each framework package, and from `@inth/sdk/modes` for shared
code.

**Transport factories** return the transport itself, with its options
attached as properties. A single-page app has one environment, so the bundler
keeps only the mode you import. `hosted()` is data everywhere: it takes no
options and uses the provider's `projectUrl`.

## manifest()

`manifest()` resolves the visitor's policy from the backend's public consent
manifest instead of asking the backend's `/v1/consent/init`. A
[consent manifest](/docs/concepts/data-fetching#what-is-a-consent-manifest)
holds your policy rules and copy, and no visitor data.

| Option | Default | Behavior |
| --- | --- | --- |
| `source` | `'build'` | `'build'` uses the snapshot the build integration downloaded. Without one, such as after a failed download, it fetches the manifest at runtime. `'runtime'` always fetches at runtime, so policy edits apply without a rebuild. |
| `snapshot` | none | A manifest you supply. You can pass `snapshot` or `source`, not both. |
| `resolve` | `'server'` | `'server'` resolves each visitor on the server and ships no resolver to the browser. `'browser'` resolves in the browser, for pages the server does not render per visitor. Server-rendered frameworks only. |
| `manifestUrl` | see below | Where to fetch the manifest at runtime. In the browser it defaults to `${routePrefix}/v1/consent/manifest`, else `${projectUrl}/v1/consent/manifest`. On the server it defaults to `${projectUrl}/v1/consent/manifest`. An absolute URL is read at runtime on the server too, so the build downloads no snapshot for it. A `/`-relative URL keeps the build's snapshot; without one the server reads that URL, except a URL on the app's own consent route, where the server reads `${projectUrl}/v1/consent/manifest` as the route does. With `resolve: 'browser'` only the browser reads it. |
| `geoUrl` | none | A same-origin route that answers with the visitor's `{ country, region }`. Browser resolution only. |
| `inputs` | none | `{ country, region }` when the page already knows the visitor's location, for example from an edge worker. Browser resolution only. |

The transport `manifest()` from `@inth/react`, `@inth/vue/vue-plugin`,
`@inth/svelte`, `@inth/angular` and `@inth/sdk` always resolves in the
browser, so it has no `resolve` option. It also takes `projectUrl`,
`headers`, `credentials`, `domain`, `fetch` and `initFallback`. With no
options it reads the snapshot and the backend URL your build integration
downloaded.

When the policy depends on where the visitor is, and the browser does not
know the country or region, browser resolution asks `geoUrl`, then the
backend's `/v1/consent/init`. Set `initFallback: false` to resolve for an unknown location
instead. A policy with location rules therefore saves no request in a
single-page app unless you pass `inputs` or `geoUrl`. The `consentManifest()`
plugins from `@inth/sdk/build`, `@inth/vue/vite` and `@inth/svelte/vite` warn
about this when a single-page app build bundles such a policy.

### When the manifest is unavailable

Each place that reads the manifest falls back to the backend's `/v1/consent/init` and
logs one warning per manifest URL:

- The build cannot download it: the build warns and the server reads the
  manifest at runtime. Set `onBuildError: 'fail'` to stop the build instead;
  see [what happens when the download fails](#what-happens-when-the-download-fails).
- The server cannot read it, or the backend has no `/v1/consent/manifest`: the server
  render and the consent route answer from the backend's `/v1/consent/init`.
- The browser cannot fetch it with `resolve: 'browser'` or in a single-page
  app: the browser asks the backend's `/v1/consent/init`, and tries the manifest again
  on the next init.

## hosted()

`hosted()` asks the backend's `GET /v1/consent/init` for each visitor's policy and posts
choices to `${projectUrl}/v1/consent/records`. It takes no options. In React, Vue,
Svelte, Angular and `@inth/sdk` it is the default, so you write it only to
be explicit; in a server-rendered framework it replaces the manifest.

## testing()

`testing()` comes from a package's `/testing` entry and is for tests only. It
resolves a policy in the browser with no backend and sends nothing. It needs
no `projectUrl`, and it throws when `NODE_ENV` is `production`, so a test
config that reaches a production build fails on load instead of showing
visitors a banner whose choices nobody records. Its code is only in bundles
that import the `/testing` entry.

| Option | Default | Behavior |
| --- | --- | --- |
| `policy` | the recommended rule pack | A `PolicyRule` or an array of them, resolved instead of the pack. The location overrides pick the matching rule, as the backend would. |
| `iab` | whether the provider configures IAB | Resolve the IAB TCF variant of the recommended pack. |

Set `overrides.country` (and `overrides.region`) to pick a policy from the
recommended pack: an EEA country or `GB` shows the opt-in banner, `DE` with
IAB shows the TCF banner, a US privacy state such as `US`/`CA` is opt-out
with no automatic banner, and a country with no rule, such as `JP`, shows no
banner. No recommended rule shows the opt-out notice banner; pass a rule with
`prompt: 'notice'` as `policy` to test it.

{/* example: fragment */}

```tsx
import { ConsentProvider } from '@inth/react';
import { testing } from '@inth/react/testing';

<ConsentProvider
	options={{
		mode: testing({
			policy: {
				id: 'notice',
				match: { fallback: true, isDefault: true },
				model: 'opt-out',
				prompt: 'notice',
			},
		}),
	}}
/>;
```

To keep consent out of the way in an app's own tests instead, set
`enabled: false`: it grants every category, shows no UI and sends nothing.

The script tag has a separate file for tests, `inth.testing.js`. The other
script files are production builds and contain neither the testing transport
nor the policy pack.

## What each mode adds to first-load JavaScript

In a server-rendered framework, the browser receives the resolved state with
the page. It only needs the code to save a choice, and loads the rest when it
runs:

| Mode | First-load JavaScript | Loaded with `import()` when it runs |
| --- | --- | --- |
| `manifest()` | The code that saves choices and builds an init request | The hosted init path, if the browser has to resolve consent again |
| `manifest({ resolve: 'browser' })` | The code that saves choices | The browser resolver, English copy and the fetch of `${routePrefix}/v1/consent/manifest` or `${projectUrl}/v1/consent/manifest`, unless the server state already holds the policy. Other languages load per language. |
| `hosted()` | The code that saves choices | The hosted init path |
| `testing()` | Nothing mode-specific | The testing transport, the rule pack and its copy |

With `manifest()` resolved on the server, the manifest snapshot, the resolver,
the rule pack and other languages stay out of the browser bundle.

In a single-page app the bundle contains the mode you imported:

| Mode | In the bundle |
| --- | --- |
| `manifest()` | The snapshot, when the build downloaded one, and the code that saves choices. The resolver starts loading when `manifest()` runs, unless the policy needs a location the page does not know. English copy is bundled; other languages load the first time a visitor needs one. |
| `hosted()`, or no mode | The hosted transport |
| `testing()` | The testing transport, the recommended rule pack and its copy |

## Set the backend URL

Each framework reads its backend URL from a public environment variable, so
the quickstarts never write it in code. Put it in `.env` or your host's build
settings. The value is public configuration, not a secret.

| Framework | Variable | c15t fallback |
| --- | --- | --- |
| Next.js | `NEXT_PUBLIC_INTH_PROJECT_URL` | `NEXT_PUBLIC_C15T_BACKEND_URL` |
| Nuxt | `NUXT_PUBLIC_INTH_PROJECT_URL` | `NUXT_PUBLIC_C15T_BACKEND_URL` |
| Astro | `PUBLIC_INTH_PROJECT_URL` | `PUBLIC_C15T_BACKEND_URL` |
| SvelteKit and Svelte | `PUBLIC_INTH_PROJECT_URL`, then `VITE_INTH_PROJECT_URL` | `PUBLIC_C15T_BACKEND_URL`, then `VITE_C15T_BACKEND_URL` |
| TanStack Start, React, Vue and JavaScript with Vite | `VITE_INTH_PROJECT_URL` | `VITE_C15T_BACKEND_URL` |
| Script tag | `data-project-url` on the script element | – |

The c15t names still work as a fallback. When both are set, the Inth variable
wins.

A backend URL resolves in this order: the framework's `projectUrl` option,
then the Inth variable, then its c15t name. The build reads each variable from the process environment,
then from `.env.[mode].local`, `.env.[mode]`, `.env.local` and `.env` in the
project root, so an Inth variable in `.env` still beats a c15t variable in
the environment. The Vite plugins set an unset `VITE_INTH_PROJECT_URL` to the
URL they used, so `import.meta.env.VITE_INTH_PROJECT_URL` in app code reads
the same value. `withConsentManifest()` does the same for
`NEXT_PUBLIC_INTH_PROJECT_URL` in Next.js.

Next.js inlines `NEXT_PUBLIC_` variables at build time. Changing the variable
on a built app has no effect until you rebuild.

## Download the manifest at build time

`manifest()` with the default `source: 'build'` resolves from a snapshot that a
build integration downloads from `${projectUrl}/v1/consent/manifest`:

| Framework | Build integration | Name in messages |
| --- | --- | --- |
| Next.js | `withConsentManifest()` from `@inth/nextjs/build`, in `next.config.ts` | `@inth/nextjs/build` |
| TanStack Start | `consentManifest()` from `@inth/tanstack-start/build` | `@inth/tanstack-start/build` |
| React | `consentManifest()` from `@inth/react/build` | `@inth/sdk/build` |
| JavaScript | `consentManifest()` from `@inth/sdk/build` | `@inth/sdk/build` |
| Vue | `consentManifest()` from `@inth/vue/vite` | `@inth/vue/vite` |
| Svelte and SvelteKit | `consentManifest()` from `@inth/svelte/vite` | `@inth/svelte/vite` |
| Nuxt | the `@inth/nuxt` module | `@inth/nuxt` |
| Astro | the `inth()` integration | `@inth/astro` |

The integration downloads the manifest when the production build or the dev
server starts, and waits at most 10 seconds. Nothing is written into your
source tree. App code reads the result from the `generated` entry of its
framework package, such as `@inth/react/generated`, or from
`@inth/sdk/generated` in plain JavaScript:

{/* example: fragment */}

```ts
import { projectUrl, snapshot } from '@inth/react/generated';
```

Both exports are `undefined` when the build has no snapshot, so imports
compile on a fresh checkout. In the browser bundle of a server-rendered
framework, `snapshot` is always `undefined`. Next.js goes further: a client
component that imports `@inth/nextjs/generated` fails the build.

Rebuild after you change policies, translations or vendors in your project. If
your CI caches build output, force a fresh build.

## What happens when the download fails

The same policy applies in every framework: when the download fails or no
backend URL is set, the build and dev log a warning and finish without a
snapshot. The server, or a single-page app's browser, then fetches the
manifest at runtime, and asks the backend's `/v1/consent/init` while it is still
unavailable.

`onBuildError` changes that:

- `'fail'` stops the build and dev with an error.
- `'runtime'`, the default, warns and continues. Set it explicitly to turn
  the warning about a missing backend URL into a notice.

Pass it where you configure the integration: the second argument of
`withConsentManifest()`, `consentManifest({ onBuildError })`, the `inth` key
in `nuxt.config.ts`, or `inth({ onBuildError })` in Astro.

The `INTH_ON_BUILD_ERROR` environment variable overrides the option, so a CI
job can require a snapshot without a code change. `C15T_ON_BUILD_ERROR` still
works as a fallback:

```sh
INTH_ON_BUILD_ERROR=fail npm run build
```

Any value other than `fail` or `runtime` stops the command. Turborepo's strict
environment mode hides undeclared variables from tasks, so list
`INTH_ON_BUILD_ERROR` in the build task's `passThroughEnv` there.

A missing backend URL follows the same policy as a failed download. Astro
and Nuxt are stricter in `manifest()` mode, including
`manifest({ snapshot })`: the browser saves consent to the backend, so a
missing backend URL stops `astro dev` and `nuxt dev`.

The download is skipped without an error when the build cannot use a
snapshot:

- The backend URL is relative, such as `/api/inth`. With an explicit
  `onBuildError: 'fail'`, a relative URL stops the build instead.
- Next.js builds with `output: 'export'`, which has no server.
- The mode is `hosted()`, `testing()`, `manifest({ snapshot })` or
  `manifest({ source: 'runtime' })` in Next.js, Nuxt and Astro. Next.js reads
  the mode from `inth.config.ts`.
- A single-page app built with Vite (React, Vue, Svelte, JavaScript) does
  not use `manifest()`. The mode is set in app code, so the plugin downloads
  the manifest only once the bundle turns out to read it, after unused code
  is dropped. A build without `manifest()` never contacts the backend.
  SvelteKit and TanStack Start choose the mode on the server at runtime, so
  their builds always download it.

A failed download never reuses an older snapshot. The
[troubleshooting guide](/docs/guides/troubleshooting#why-does-the-build-fail-to-download-the-manifest)
lists each message and its fix.
