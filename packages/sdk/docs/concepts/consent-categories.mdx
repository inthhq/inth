Inth groups tracking, embeds, and optional site features into five consent categories and discovers active categories from your integrations automatically.

## Category reference

| Category | Purpose |
| --- | --- |
| `necessary` | Core features required for the site to work. Always allowed. |
| `functionality` | Optional features such as live chat or support widgets. |
| `measurement` | Analytics, telemetry, and usage measurement. |
| `experience` | Personalization, feature flags, and experimentation. |
| `marketing` | Advertising, retargeting, and conversion pixels. |

Assign every integration by what it actually does. Labeling analytics as `necessary` does not make it necessary.

## Automatic category discovery

Inth discovers categories from every gated integration you configure:

- Registered scripts, including compound category conditions that contribute every referenced category.
- Network blocker rules.
- `ConsentGate` components.
- Gated iframes with `data-category` handled by the iframe blocker.
- Inert HTML script tags with `data-inth-category` in the browser client.

Always write gated iframes with `data-src`, not `src`. The browser starts requesting a `src` attribute as soon as the iframe enters the document, before the iframe blocker can pause it, whether the iframe comes from server HTML or a client render.

In React frameworks, DOM iframe blocking and discovery are enabled by default and load lazily when the first `data-category` or `data-vendor` iframe appears on the page. Set `iframeBlocker: false` to disable automatic blocking, or pass `iframeBlocker: { disableAutomaticBlocking: true }` to trigger scans manually with `useIframeBlocker({ disableAutomaticBlocking: true }).processAllIframes()`.

Categories discovered after initial render are added immediately and stay active until the provider or runtime is recreated. Adding a new category can require a fresh visitor choice and reopen the banner. Removing a script or unmounting an iframe does not drop its category or erase stored consent, and discovery never grants permission on its own.

## Policy scope and the preference dialog

Inth merges discovered categories with any explicit `consentCategories` list you pass. The preference dialog always lists Necessary, plus any optional categories in that combined set that also fall inside the resolved policy scope. Choice completion uses the same set.

When neither your configuration nor your integrations declare optional categories, behavior depends on the matched policy's `scopeMode`:

- **`permissive` scope.** The dialog lists Necessary only. When the policy prompts for a choice, Accept All, Reject All, and Save each record a Necessary-only receipt in `hosted()` and `manifest()` modes and dismiss the banner until validity expires, the policy changes, or a new category is discovered.
- **`strict` or `iab` scope.** The dialog lists the full policy scope. Under IAB TCF, visitors grant consent per purpose and Inth stores the result in the TC string.

A `strict` policy denies categories outside its rule scope. A `permissive` policy can allow out-of-scope categories unless another restriction applies. An omitted policy scope, `['*']`, or `['necessary']` expands to the default optional categories rather than disabling tracking. Hidden optional categories do not block banner dismissal, but they still follow the policy: a hidden opt-in category stays denied without a grant.

## Optional per-vendor switches

When a visitor should be able to allow a category such as `marketing` while opting out of one specific vendor inside it, configure `vendors` alongside your categories. See [integrations](/docs/integrations/overview) for vendor setup, [policies](/docs/concepts/policies) for scope configuration, and [a permission is not a recorded choice](/docs/concepts/how-consent-works#a-permission-is-not-a-recorded-choice) for reading permissions safely.
