Use the [web integration](#web) for Sentry error monitoring, user data and
Session Replay. In [Swift, Android, React Native and Expo apps](#mobile), the
bundled helper controls manual Session Replay only. Your app keeps ownership
of native crash reporting, profiling and user-data configuration.

## Web

With a `dsn` and the default `loadMode`, the c15t `sentry` helper loads the
Sentry CDN bundle on every page, before the visitor chooses. Sentry reports
errors under the `necessary` category. While `measurement` has no consent, error
events contain no user data, cookies, request headers, or inferred IP address.
Session Replay also waits until `measurement` has consent. It stops after the
visitor withdraws consent. With `loadMode: 'after-consent'`, Sentry runs only
while `measurement` has consent.

### Configure Sentry

Remove any existing Sentry Loader Script or CDN tags, then add this configuration.
Errors run before consent by default; Replay and SDK data collection wait for
`measurement`.

The default SDK is 11.4.0 with subresource integrity: `bundle.min.js`, or
`bundle.tracing.min.js` when traces are sampled. `replay.min.js` loads after
consent when a Replay sample rate is above 0.

CDN URLs need an exact release version. Keep the default to use its integrity
hash, or set `version` to an exact release in the supported SDK range below.

### Use your own Sentry SDK

The supported browser SDK range is `^10.67.0 || ^11.0.0`, including framework
SDKs built on those versions. Version 10.67.0 added Replay's
`stop({ flush: false })`, which c15t uses to discard pending recordings when
consent is withdrawn. Earlier versions flush those recordings when stopping.

Pass your SDK's functions instead of `dsn`. Keep Replay in a separate module
so it can load after consent:

```ts title="src/sentry-replay.ts"
import { replayIntegration } from '@sentry/browser';

export const createReplay = () =>
	replayIntegration({ maskAllText: true, blockAllMedia: true });
```

In `src/consent-scripts.ts`, replace the CDN configuration with:

{/* example: fragment */}

```ts
import { getClient, init, setUser } from '@sentry/browser';

sentry({
	getClient,
	init,
	setUser,
	initOptions: {
		dsn: 'https://your-key@o0.ingest.sentry.io/0',
		replaysSessionSampleRate: 0.1,
		replaysOnErrorSampleRate: 1,
	},
	replay: {
		load: () => import('./sentry-replay').then((m) => m.createReplay()),
	},
});
```

Passing `init` protects startup captures before other SDK integrations run.
Custom initializers must forward the supplied options to `Sentry.init`, including
after a dynamic import. Avoid initialization as an import side effect.

Use named imports from the same Sentry package throughout your app. Next.js and
Vite split dynamically imported Replay into its own chunk; esbuild and Bun keep
it in the main bundle. A main-bundle `Sentry.replayIntegration` reference through
`import * as Sentry` also prevents the split.

#### If Sentry already initializes independently

c15t applies filters once it finds the client; it cannot retract earlier data.
For startup protection, disable collection and remove event users in your own
`Sentry.init` call. With SDK 10.67, omit `queues`:

{/* example: fragment */}

```ts
// Include these options in your app's Sentry.init call.
maxBreadcrumbs: 0,
dataCollection: {
	userInfo: false,
	cookies: false,
	httpHeaders: { request: false, response: false },
	httpBodies: [],
	urlQueryParams: false,
	graphQL: { document: false, variables: false },
	genAI: { inputs: false, outputs: false },
	databaseQueryData: false,
	queues: false,
	stackFrameVariables: false,
	frameContextLines: 0,
},
beforeSend(event) {
	delete event.user;
	delete event.request;
	return event;
},
```

These settings keep collection and event users disabled after consent too.
To restore event users, check effective c15t permission in `beforeSend`. Wait
until the adapter is registered before assigning scope users or capturing logs
and metrics.

### Options

| Option | Default | Behavior |
| --- | --- | --- |
| `dsn` | Required to load Sentry | Your project's DSN. c15t loads the SDK and calls `Sentry.init`. A blank DSN logs an error and the script does not load. |
| `initOptions` | `{}` | Passed to `Sentry.init` with c15t's consent integration first. CDN `integrations` callbacks can access `window.Sentry`. |
| `version` | `'11.4.0'` | SDK version to load. Another version loads without subresource integrity. |
| `tracing` | `true` when traces are sampled | Loads the tracing bundle and adds `browserTracingIntegration()`. |
| `replay` | Loads CDN Replay when sampled | CDN: `{ category, options }` or `false`. SDK: `{ category, load }`. |
| `getClient` | Required for your own SDK | Your SDK's `getClient`. Supports initialization after c15t starts. |
| `setUser` | None | `setUser` from your Sentry SDK. Called with `null` while user data is not allowed. Required with `pii.user`. |
| `init` | None | Your SDK's `init`, called once when `loadMode` allows. Required for SDK mode with `'after-consent'`. |
| `replay.load` | None | With your own SDK, returns a new `replayIntegration()`. Called once, the first time Replay is allowed. |
| `loadMode` | `'always'` | When error monitoring runs. See the table below. |
| `replay.category` | `'measurement'` | Consent condition for Replay. `pii.category` must also be allowed. |
| `pii.category` | `'measurement'` | Consent condition for SDK data collection and user data. `'necessary'` permits it while the Sentry vendor is enabled. |
| `pii.user` | None | Returns the user to set when user data becomes allowed. |
| `onError` | Report to an available Sentry client | Receives CDN and Replay lifecycle failures. Set it to report CDN download failures before Sentry exists. |

Replay's category is registered only with an SDK `replay.load` function or
enabled CDN Replay with a positive sample rate.

### Loading and revocation

| `loadMode` | When Sentry runs | On withdrawal without a reload |
| --- | --- | --- |
| `'always'` | On every page, before consent | Replay stops; errors keep reaching Sentry without user data |
| `'after-consent'` | Only while `measurement` is allowed | Sentry stops sending anything |

Replay needs both `replay.category` and `pii.category`, because recordings
include page URLs with queries and fragments. Keep Replay out of `Sentry.init`:
`replaysOnErrorSampleRate` can buffer recordings before consent. On denial or
final removal, c15t stops Replay without flushing, discards queued uploads and
blocks restarts. Data already sent stays in Sentry; a later grant preserves
the original sampling decision.

While PII is denied, c15t disables supported `dataCollection` settings and IP
inference. Before sending, it removes user fields, feedback contact details,
visitor identifiers in sessions, request data and URL queries/fragments from
supported events, spans, logs, metrics and breadcrumbs, including retained
breadcrumbs. A grant restores your resolved collection settings and allowlists.
Tracing itself is not gated. Custom messages, tags, extras, attachments and
URL paths remain diagnostics, so keep sensitive values out of them.

The vendor slug is `sentry`. Turning it off denies Replay and PII, plus errors
in `'after-consent'` mode. See [vendor consent](/docs/integrations/overview#vendor-switches-and-cookie-cleanup).

#### Shared clients and configuration changes

Keep callback functions stable across renders. Equal options and callbacks
reuse the SDK bundle and active recording. Changed CDN options initialize a
client with the new DSN and settings, while reusing the page's single Replay
recorder. Its original Replay options and sampling decision last until reload.

Every active configuration targeting one client must allow each feature;
removing a loader releases its restriction and preserves surviving loaders and
downloads. Final removal denies PII and stops Replay, and also disables errors
in `'after-consent'` mode. An app-initiated `Sentry.close()` stays closed after
a grant. Separate clients have separate permissions.

### Content security policy

Allow `worker-src blob:` for Replay and your ingest or tunnel endpoint in
`connect-src`. CDN mode also needs `https://browser.sentry-cdn.com` in
`script-src`. The loader or provider's `nonce` applies to both CDN bundles;
a per-script nonce overrides it.

### Verify Sentry

Test in a private window with an opt-in policy and
`replaysSessionSampleRate: 1`. Filter DevTools Network by `sentry`.

1. Load the page. `bundle.min.js` loads and errors reach Sentry, without `user`.
   No `replay.min.js` or `replay_recording` request is sent. With
   `loadMode: 'after-consent'`, nothing loads.
2. Allow measurement. Without a reload, Replay loads and `replay_recording`
   requests start.
3. Turn measurement off and save. c15t reloads the page, and no replay request
   follows.

See the [consent verification guide](/docs/guides/verify-consent) for
navigation, expiry and hosting checks.

## Mobile

Use the bundled Sentry Replay helper to start recording while the chosen native
category is allowed and stop it when permission is pending or denied. This
integration controls Session Replay only. Your app configures crash reporting,
profiling, user identifiers and other Sentry products separately.

The helper ships in `InthApple`, `inth-android` and
`@inth/react-native/integrations`. Your app installs Sentry. No Sentry dependency
is added by c15t.

### Before you start

Complete the [Swift](/docs/frameworks/swift/quickstart),
[Android](/docs/frameworks/android/quickstart) or
[React Native](/docs/frameworks/react-native/quickstart) quickstart. Include
the chosen optional category in both the native configuration and your Inth
policy. The helper defaults to `measurement`. This is effective category
permission, which can follow policy defaults. If replay requires a separate
explicit choice in your app, use a policy and UI that capture that choice before
connecting it. See [mobile availability](/docs/guides/mobile-status) for SDK access.

Use a Sentry SDK with manual replay start and stop APIs. The checked mappings
use Sentry Cocoa 9.32.0, Android 8.62.0 and React Native 8.33.0. These examples
do not target older SDKs without manual controls.

Android Replay requires API 26 or later, even though c15t itself supports API
24\. Do not treat a successfully initialized Sentry client on an older device
as proof that replay can record there.

Set both session and error replay sample rates to zero before initializing
Sentry, including any native initialization before JavaScript. Leaving error
sampling enabled can buffer screen data before consent. Add the replay module
following Sentry's platform instructions and retain its default masking until
you have tested your app's sensitive screens.

### Connect Swift

Add this owner to your app target:

<include src="../shared/examples/native/core-swift/AppleInstallation/swift-sentry-replay-binding.mdx" />

In your existing Sentry setup, set
`options.sessionReplay.sessionSampleRate = 0` and
`options.sessionReplay.onErrorSampleRate = 0`. After Sentry and c15t are
installed, retain this owner on your app's service owner:

{/* example: fragment */}

```swift
import Sentry

let replayOwner = SentryReplayOwner(
    core: core,
    start: { SentrySDK.replay.start() },
    stop: { SentrySDK.replay.stop() }
)
```

`core` is the installed `ConsentCore`. Pass direct vendor calls. The helper
serializes their submission; Sentry's internal work can finish asynchronously.
Call `stop()` on the owner for final teardown.

### Connect Android

Add this function to your app, replacing the sample package name:

<include src="../shared/examples/native/examples/consent-demo/android-sentry-replay-integration.mdx" />

In the existing Sentry setup, set
`options.sessionReplay.sessionSampleRate = 0.0` and
`options.sessionReplay.onErrorSampleRate = 0.0`. After installing both SDKs,
connect the manual controls:

{/* example: fragment */}

```kotlin
import io.sentry.Sentry

val replayConsent = connectAppSentryReplay(
	start = { Sentry.replay().start() },
	stop = { Sentry.replay().stop() },
	onError = ::reportReplayError,
)
```

Keep the helper on an application or service owner. The native core keeps
applying consent until you call `close()`, even if the app drops the handle. The error handler must
work with replay disabled and must not throw. Automatic callback failures go
to `onError`. Construction, `sync()` and `close()` can throw to their caller.
Use `close()` for final service teardown.

### Connect React Native or Expo

Set `replaysSessionSampleRate: 0` and `replaysOnErrorSampleRate: 0` in your
existing Sentry configuration. Configure the mobile replay integration using
[Sentry's manual control instructions](https://docs.sentry.io/platforms/react-native/session-replay/#manual-control).
Keep the mobile replay option `avoidForegroundResumeHang` disabled in this
recipe. In the checked SDK, that experimental workaround can restart buffering
on foreground independently of the consent-controlled stop command.
If your app initializes Sentry natively first, disable native replay sampling
there too. Expo needs a build containing both SDKs; Expo Go cannot provide
c15t's native engine.

Copy this function into `sentry-replay-consent.ts`:

<include src="../shared/examples/react-native-bare/rn-sentry-replay-integration.mdx" />

After Sentry initialization, connect the active replay instance:

{/* example: fragment */}

```ts
import * as Sentry from '@sentry/react-native';

const replay = Sentry.getReplay();
if (!replay) {
	throw new Error('Configure Sentry Session Replay before connecting c15t.');
}
const replayConsent = connectAppSentryReplay(replay, reportReplayError);
await replayConsent.ready;
```

Retain the connection for the replay service's lifetime. `ready` waits for
the supplied calls to return; a `void` vendor method can still have pending
native work. `stop()` returns a promise in the checked Sentry RN SDK, so
withdrawal updates and `disconnect()` await that promise. Handle errors
through `onError` and at the returned promise's call site.

### Keep recording aligned with the vendor lifecycle

Use the Swift owner's `syncAfterReset()`, Kotlin's `sync()` or
`await replayConsent.sync()` after an app-owned vendor reset or reinitialization. Sentry can
also stop a manually started replay when it starts a new app session. With
sampling disabled, it may then remain stopped even though c15t permission is
still granted. Reapply permission after the vendor's session transition.
This keeps consent authoritative without turning automatic replay sampling on.

For final teardown, use the Swift owner's `stop()`, Kotlin's `close()` or
`await replayConsent.disconnect()`. Do not close an app-wide connection on
screen navigation or Activity rotation.

### Understand what stopping does

Sentry can send a final recorded segment when stopping a full-session replay.
Stopping does not guarantee that unsent data is discarded or that all network
traffic ends. The helper submits stop; it does not call `flush()`, delete
historical recordings or change crash reporting configuration.

Masking and permission are separate. Test the actual screen content in your
app, including native views and sensitive input screens. A successful consent
test does not prove that Sentry's masking works for every rendered component.

### Verify your app

With both sample rates zero, launch pending and then refuse permission. Confirm
no replay starts or buffers. Grant permission, record a deliberate screen
transition, withdraw and confirm new capture stops. Inspect the final segment
separately from later capture. Test background and foreground transitions,
vendor reinitialization, reconnection and teardown. Confirm the configured
crash-reporting behavior remains unchanged.

The helper tests cover native permission and callback ordering. Vendor consumer
checks validate the mappings, rather than your app's capture or network behavior.
Complete [mobile verification](/docs/guides/mobile-verify) with the exact Sentry
build and lifecycle your app ships.
