[Expo Observe](https://docs.expo.dev/eas/observe/introduction/), formerly EAS Observe, records startup metrics, events, and crash reports from native app launch. `expo-observe` has no consent API and no way to turn local recording off, but it persists a send switch via `Observe.configure({ dispatchingEnabled })`. This guide wires that switch to Inth's `measurement` category so Inth controls whether queued data leaves the device.

## What Observe collects and when it sends

With `expo-observe` installed and your root component wrapped in `ObserveRoot.wrap`, Observe automatically records cold and warm launches, bundle load, time to first render, time to interactive via `markInteractive()` (with frame, thermal, battery, and launch-network summaries), unhandled JS errors (SDK 57+), native crashes, and EAS Update download timings. Your code can add more via `Observe.logEvent`, `Observe.reportError`, `ObserveErrorBoundary`, spans, navigation integrations, and `networkTraces`.

Every event includes app, release, device, and route context plus a persisted random install ID (`expo.eas_client.id`). Expo states Observe collects no PII, and its iOS privacy manifest declares crash, performance, diagnostic, device ID, and product interaction data as not linked to the user or used for tracking. Confirm with privacy counsel whether this data needs consent in your markets.

Observe sends OTLP payloads to `https://o.expo.dev/<project id>` (or `extra.eas.observe.endpointUrl`) when `extra.eas.projectId` is set. Debug builds send only when `dispatchInDebug` is `true`.

Because Expo autolinking hooks into native startup before JavaScript loads, Observe writes events to a local database and flushes them at these points:

| Platform | Observe sends the queue when |
| --- | --- |
| iOS | The app resigns active or is about to terminate |
| Android | An activity backgrounds and a WorkManager job runs online |
| Both | Your code calls `Observe.dispatchEvents()` |

At each send, Observe checks the last saved `configure` state. With `dispatchingEnabled: false`, it marks pending metrics and logs as sent and deletes pending spans without transmitting them. A fresh install that has never called `configure` defaults to sending, and Observe has no build-time setting to start with sending disabled.

## Choose the category

Use `measurement`. `dispatchingEnabled` controls metrics, events, spans, and errors together. On SDK 58+, if your legal review allows crash reports without consent, keep `dispatchingEnabled: true` and pass `sampleRate: 0` with `errorSampleRate: 1` while `measurement` is denied. SDK 57 and earlier lack `errorSampleRate`, so all telemetry must be gated together.

Render `<ObserveConsent />` once inside `InthProvider` in the root component wrapped by `ObserveRoot.wrap` (such as Expo Router's root `_layout.tsx`) and keep it mounted for the app lifetime.

While `useConsentDecision('measurement')` is `pending`, a returning user (`useInthBootstrap().hasStoredSnapshot === true`) keeps their previous saved state so launch metrics are not lost, while a new user (`hasStoredSnapshot === false`) or a post-`reset()` session turns sending off until a decision arrives. Under an opt-in policy, `denied` persists `dispatchingEnabled: false` so Observe drops its queue on the next send.

`Observe.configure` replaces the entire configuration on every call, resetting omitted fields (`sampleRate`, `integrations`, and SDK 58's `errorSampleRate`, `networkTraces`, and `errorHandlingEnabled`) to their defaults. Remove other `configure` calls and put all options in `observeConfig`. On SDK 55 (`expo-observe` 0.2.x), use `import Observe from 'expo-observe'` and the `Config` type.

## What the gate does not cover

- **First launch.** If a new user backgrounds the app before React mounts `<ObserveConsent />`, Observe uses its default and sends recorded startup data.
- **Data recorded before a grant.** Observe records locally while sending is off and discards only on a send attempt. Granting `measurement` before any send attempt flushes the earlier startup queue.
- **Withdrawal race.** Because the React effect runs after render while Observe sends natively on background, backgrounding immediately after withdrawal can still send under the previous saved value.
- **Local recording.** Observe always writes metrics, events, and crashes to the device database.

If your app cannot accept these gaps, omit `expo-observe` from builds in markets requiring pre-consent gating, ship it ungated with privacy-policy disclosure where legally permitted, or request a build-time off switch in the [Expo repository](https://github.com/expo/expo/issues).

## Check the gate

Test a release build, or set `dispatchInDebug: true` in `observeConfig` for a dev build, and inspect requests to `o.expo.dev` with Proxyman or Charles:

1. Fresh install, wait for the consent prompt, then background without choosing. Confirm no requests go to `/v1/metrics`, `/v1/logs`, or `/v1/traces`.
2. Reject all and background. Confirm nothing sends.
3. Grant `measurement` and background. Confirm `/v1/metrics` and `/v1/logs` requests fire.
4. Withdraw `measurement`, use the app, and background. Confirm nothing sends.
5. Relaunch after refusal and background before opening privacy settings. Confirm nothing sends.

Type-checked against `expo-observe` `58.0.19` and `expo-app-metrics` `58.0.15` (SDK 56 and 57 ship the same `dispatchingEnabled` option). Verify network traffic on real devices with your shipped versions.
