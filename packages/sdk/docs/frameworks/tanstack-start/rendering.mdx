Choose how your TanStack Start app resolves consent on the server or in the browser without changing your page components or hooks.

## Pick your rendering path

Rendering choices live in `src/routes/__root.tsx`, plus the Vite plugin for build-time manifests and an optional server route for same-origin requests.

| Your app | Root loader | Banner in server HTML | Setup |
| --- | --- | --- | --- |
| Start server, recommended | Awaits consent from a build-time manifest | Yes | [Quickstart](/docs/frameworks/tanstack-start/quickstart) |
| Policy changes apply without a rebuild | Awaits consent from a runtime manifest cache | Yes | [Runtime fetching](#await-consent-in-the-loader) |
| Runtime fetching on a serverless host | Streams consent | Yes, in a later chunk before hydration | [Stream the page](#stream-the-page-while-consent-resolves) |
| Browser must talk only to your origin | Awaits consent | Yes | [Same-origin route](#keep-consent-requests-on-your-origin) |
| SPA mode, prerendered pages, or static host | None | No, browser resolves consent | [No server render](#spa-mode-prerendered-pages-and-static-hosts) |

## Await consent in the loader

The [quickstart](/docs/frameworks/tanstack-start/quickstart) root loader awaits the consent server function. The server reads the visitor's cookie and location headers, resolves their policy from the build-time snapshot, and renders the banner into the HTML. To apply policy updates without rebuilding, pass `mode: manifest({ source: 'runtime' })` to `createConsentStateHandler` using `manifest` from `@inth/tanstack-start`. The server then fetches and caches the manifest in memory while `consentManifest()` continues supplying the project URL.

`createConsentStateHandler({ mode })` accepts `manifest()`, `hosted()`, or `testing()` from `@inth/tanstack-start`. They are plain serializable objects, so the state passes the mode to `InthProvider` and the browser bundles only that mode's code while keeping `snapshot` on the server. See [Consent modes](/docs/concepts/modes).

With runtime fetching, the first request after a cold start waits up to 500 ms for the manifest before rendering without consent UI and letting the browser resolve consent. Subsequent requests read from cache. Adjust the timeout with `timeoutMs` on `createConsentStateHandler`.

When the server state already allows entries in `scripts`, through a stored choice or an opt-out policy, `InthProvider` emits an inline script after page content that starts those vendor helpers after first paint and before hydration. `alwaysLoad` entries start the same way unless the policy still owes a choice prompt, and prerendered pages start nothing. The script loader adopts those tags on hydration instead of inserting duplicates. All `@inth/integrations` helpers except Cloudflare Zaraz and Sentry support server start; custom `scripts` entries start after hydration. Pass `scriptLoader={{ serverStart: false }}` to `InthProvider` to start all scripts after hydration.

## Stream the page while consent resolves

With runtime fetching, return the pending server function promise instead of awaiting it. TanStack Router streams the promise to the browser and `InthProvider` accepts it via `state`:

<include src="../../shared/examples/tanstack-start/streamed-root.mdx" />

Streaming starts the response immediately without waiting on Inth:

- The page streams immediately, and the banner follows in a later chunk before hydration. Set `options={{ streamBanner: false }}` on `InthProvider` to mount it after hydration instead.
- Until the promise settles, every optional category stays denied so gated scripts and embeds remain blocked.
- If Inth times out, the promise falls back to cookie and header state and the browser resolves consent directly.
- Allowed `scripts` entries start as soon as the consent chunk arrives.

Use streaming when cold-start latency on a serverless host must never delay page HTML; keep an awaited loader when the banner should arrive with the first bytes.

## Keep consent requests on your origin

By default, the browser sends saves and client-side requests directly to your Inth project URL. To keep all browser consent traffic on your origin, mount the consent route:

<include src="../../shared/examples/tanstack-start/consent-route.mdx" />

Pass `routePrefix` and `proxy: true` to `createConsentStateHandler`:

<include src="../../shared/examples/tanstack-start/same-origin-root.mdx" />

| Request | Handled by |
| --- | --- |
| `GET /api/inth/v1/consent/init` or `GET /api/inth` | The route, resolving the bundled manifest for the request's location, language, and GPC header |
| `GET /api/inth/v1/consent/manifest` | The route, serving the bundled manifest |
| `POST /api/inth/v1/consent/records` and other consent paths | Forwarded to your Inth project when `proxy: true` |
| Any other path | `404`, preventing an open proxy |

Keep these details in mind:

- `createConsentStateHandler` keeps the absolute project URL from `consentManifest()` for its own requests and never fetches under `routePrefix`.
- `routePrefix` routes browser `/v1/consent/init` and IAB vendor lists through `/api/inth`. It has no default, and passing `'/'` or an empty string throws at handler creation: ``@inth/tanstack-start: `routePrefix` can't be '/': a consent route at the site root would catch every page. Use a path such as '/api/inth'.``
- `proxy: true` routes saves through the same-origin route and requires `routePrefix`, throwing ``@inth/tanstack-start: `proxy` sends saves through the consent route, so it needs `routePrefix`.`` without it. With `hosted({ projectUrl })`, pass the same `projectUrl` to `createConsentRoute({ projectUrl })`. Drop `proxy: true` from both to route only `/v1/consent/init` through your origin while sending saves directly to Inth.
- The proxy forwards user agent, language, origin, and location headers. Set `trustForwardedHeaders: true` on `createConsentRoute` only when your host overwrites `x-forwarded-for`, such as Vercel or Cloudflare.

## SPA mode, prerendered pages and static hosts

Prerendered HTML is shared across all visitors, so it cannot embed one visitor's consent. Drop the root loader, pass `state={{}}`, and let the browser resolve consent from the URL supplied by `consentManifest()`:

<include src="../../shared/examples/tanstack-start/static-root.mdx" />

- `state={{}}` renders without consent UI and denies optional categories until the browser resolves the policy. Without `consentManifest()`, an empty state throws unless you pass `state={{ mode: testing() }}`.
- The browser calls `/v1/consent/init` and `/v1/consent/records` directly on your Inth project URL, requiring no server routes. Add your site's origin to your Inth project's trusted origins.
- `consentPrefetchHead` is optional: it injects an inline script in `<head>` that starts `/v1/consent/init` before app JavaScript downloads. If Inth assigns a banner experiment arm, pass `consentPrefetchHead({ projectUrl, experiment })` so `InthProvider` does not send a second `/v1/consent/init`.

If a root loader remains during `tanstackStart({ prerender: { enabled: true } })`, `resolveConsent` detects `TSS_PRERENDERING` and treats the render as shared, reading no cookies or geo headers and baking no visitor state into static HTML. Pass `shared: true` to force the same behavior for any cached HTML response.

`@inth/tanstack-start/static` provides lower-level build-time manifest helpers such as `createStaticConsentResolver({ manifest, geoUrl })` if you need custom browser-side resolution backed by a `geoUrl` endpoint.

## Know when InthProvider loads its engine

`InthProvider` defers loading the consent engine out of the initial browser bundle while keeping the server-rendered banner, its styles, and server-started scripts in the first HTML.

Until the engine loads, hooks return the server-rendered state and actions such as `useSetActiveUI()` queue until the engine arrives. Taps on the server-rendered banner work immediately:

- **Accept or Reject** hides the banner immediately, inserts plain allowed `scripts` entries during the tap, then loads a small chunk to persist the choice, queue `/v1/consent/records`, and fire callbacks before the full engine loads.
- **Customize** hides the banner immediately and opens the dialog from its own chunk, preloaded on pointer down. With `consentManifest()` in Vite, dialog code bundles cleanly into a minimal round trip, and the engine loads once the dialog opens.

| Visitor | Engine loads |
| --- | --- |
| First visit with a choice banner and no optional categories allowed | After every `<img fetchpriority="high">` finishes (or `load` when none exists), on first pointer/key/scroll input outside the banner, after a banner tap, or after 10 seconds |
| Returning visitor with a stored choice and no banner | Same triggers as above; until then `InthProvider` starts plain allowed `scripts` and `useScriptLoader()` entries during hydration |
| IAB policy, or browser state newer than server cookie | Immediately when `InthProvider` boots, before hydration |

On slow connections, deferring the engine keeps it from competing with your hero image for Largest Contentful Paint.

For returning visitors, an inline script checks `localStorage`, GPC, and choice expiry against server state and loads the engine immediately if anything changed. `InthProvider` also loads the engine immediately when `scripts` entries use callbacks (`onLoad`, `onError`, `onDispose`, `persistAfterDispose`, or denied `observeConsentBeforeLoad` with `onConsentChange`), vendor or IAB fields, `persistence: false`, `options.consentSource`, `state={{}}`, `options.enabled: false`, `options.experiment`, `networkBlocker`, `clearOnRevocation`, or `IABProvider`.

With `consentManifest()` in `vite.config.ts`, the browser bundle reuses the server-rendered `<style>` element instead of duplicating banner CSS.

## Run on hosts that stop work after the response

After rendering, the server function reports session data and refreshes stale runtime manifests in the background. On serverless hosts that terminate background work once the response closes, pass your platform's `waitUntil` function as `onBackgroundRevalidate` to `createConsentStateHandler` and `createConsentRoute`.

## Check the rendering path

1. View page source in a private window under an opt-in policy. Confirm `data-testid="consent-banner-root"` appears for awaited and streamed loaders, and is absent on prerendered pages.
2. Filter DevTools Network by `records` and reject. Confirm `POST` goes to `/api/inth/v1/consent/records` with the same-origin route, or directly to your Inth project URL otherwise.
3. Confirm vendor requests stay absent until their category is allowed.
