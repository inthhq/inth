## Pick your rendering path

Rendering choices change `src/routes/__root.tsx`. The recommended build-time
manifest also adds a Vite plugin; the same-origin path adds one server route. Pages, components and hooks stay the same.

| Your app | Root loader | Banner in the server response | Setup |
| --- | --- | --- | --- |
| Start server, recommended | Awaits consent from a build-time manifest | Yes | [Quickstart](/docs/frameworks/tanstack-start/quickstart) |
| Policy changes must apply without a rebuild | Awaits consent from a runtime manifest cache | Yes | [Runtime fetching](#await-consent-in-the-loader) |
| Runtime fetching on a serverless or often cold-started server | Streams consent | Yes, in a later chunk, before hydration | [Stream the page](#stream-the-page-while-consent-resolves) |
| Browser must only talk to your origin | Awaits consent | Yes | [Same-origin route](#keep-consent-requests-on-your-origin) |
| SPA mode, prerendered pages or a static host | None | No, the browser resolves consent | [No server render](#spa-mode-prerendered-pages-and-static-hosts) |

## Await consent in the loader

The [quickstart](/docs/frameworks/tanstack-start/quickstart) root loader awaits
the consent server function. The server reads the visitor's cookie and location
headers, resolves their policy from the build-time snapshot, and renders the
banner into the HTML. To apply policy updates without rebuilding, pass
`mode: manifest({ source: 'runtime' })` to `createConsentStateHandler`, with
`manifest` from `@inth/tanstack-start`. The server then fetches the manifest
and caches it in memory. Keep the plugin: it still supplies the backend URL.

`createConsentStateHandler({ mode })` takes `manifest()`, `hosted()` or
`testing()` from `@inth/tanstack-start`. They are plain data, so the state
carries the mode to `ConsentRoot`, and the browser loads only that mode's
code. A mode's `snapshot` stays on the server.
[Consent modes](/docs/concepts/modes) compares them.

With runtime fetching, the first request after a server starts has no cached
manifest and waits for
the backend. The server function waits at most 500 ms, then renders without
consent UI and lets the browser resolve consent. Later requests read the cached
manifest and add little time. Change the wait with `timeoutMs` in
`createConsentStateHandler`.

When the state shows that the visitor's consent already allows some `scripts`
entries, through a stored choice or a policy that asks for none, `ConsentRoot`
renders an inline script after your page content. After first paint, it runs
those entries' setup and inserts their tags, so they start loading before the
page hydrates. Entries with `alwaysLoad` start this way whatever the visitor
chose. The script loader adopts those tags instead of inserting its own. Nothing
starts from the HTML while the policy asks the visitor to choose, not even
`alwaysLoad` entries, and a prerendered page starts nothing.

This works on React 18 and 19. The vendor helpers from `@inth/integrations`
start this way, except Cloudflare Zaraz and Sentry. Those two helpers, and
`scripts` entries you write yourself, start after hydration.

To start every `scripts` entry after hydration instead, pass
`scriptLoader={{ serverStart: false }}` to `ConsentRoot`. It then renders no
inline script.

## Stream the page while consent resolves

With runtime fetching, return the pending server function call instead of
awaiting it. TanStack Router streams the promise to the browser and
`ConsentRoot` accepts it as `state`. This root fetches the manifest at
runtime, and its loader does not await:

<include src="../../shared/examples/tanstack-start/streamed-root.mdx" />

The response starts without waiting for the backend. What changes for the
visitor:

- The page streams at once. The banner follows in a later chunk of the same
  response, before hydration. Pass `streamBanner: false` in `ConsentRoot`'s
  `options` to mount it after hydration instead.
- Until then every optional category is denied, so gated scripts and embeds
  stay blocked. A returning visitor's stored choice applies when the state
  arrives.
- If the backend does not answer in time, the promise resolves to the cookie
  and header state and the browser resolves consent itself.
- The `scripts` entries the state allows start from the chunk that carries the
  state, as soon as it arrives. When that chunk comes after the app's
  JavaScript, the rest of the page may already be hydrating.

Stream when a slow or unreachable backend must never delay your page, for
example on serverless hosts where many requests start with an empty manifest
cache. Keep the awaited loader when the banner should arrive with the page.

## Keep consent requests on your origin

By default the browser calls your backend URL directly. To keep every consent
request on your own origin, mount the consent route:

<include src="../../shared/examples/tanstack-start/consent-route.mdx" />

Then give the server function the route's prefix, and `proxy: true` so the
browser saves through the route too:

<include src="../../shared/examples/tanstack-start/same-origin-root.mdx" />

What the route serves:

| Request | Handled by |
| --- | --- |
| `GET /api/inth/init` or `GET /api/inth` | The route, from the bundled manifest, for this request's location, language and privacy signal |
| `GET /api/inth/manifest` | The route, serving the bundled manifest |
| `POST /api/inth/subjects` and other consent paths | Forwarded to your backend because `proxy: true` |
| Any other path | `404`, so the route is never an open proxy |

Keep these details right:

- `createConsentStateHandler` keeps the absolute backend URL from
  `consentManifest()` for its own requests. It never fetches under
  `routePrefix`, so the render cannot call its own route.
- `routePrefix` puts the prefix on the state, so `ConsentRoot` sends the
  browser's init to `/api/inth/init` and binds each save to the policy it
  resolved. It also makes the page load IAB vendor lists through the route.
  It means the same as Next.js `defineConsentConfig({ routePrefix })`, and
  like there it has no default. `'/'` throws
  ``@inth/tanstack-start: `routePrefix` can't be '/': a consent route at the site root would catch every page. Use a path such as '/api/inth'.``
  when the handler is created. An empty string throws too, because it isn't
  a path that starts with `/`. To run without a consent route, leave
  `routePrefix` out.
- `proxy: true` on `createConsentStateHandler` sends saves through the route,
  like Next.js `defineConsentConfig({ proxy: true })`. It needs `routePrefix`,
  and throws
  ``@inth/tanstack-start: `proxy` sends saves through the consent route, so it needs `routePrefix`.``
  without it. With `hosted({ projectUrl })`, the browser still goes through
  the route; only the server asks that URL, so pass the same URL to
  `createConsentRoute({ projectUrl })`. To send only init through the route
  and keep saves going straight to your backend, drop `proxy: true` from
  both and keep `routePrefix`.
- The proxy forwards the visitor's user agent, language, origin and location
  headers so the backend's firewall sees a normal visitor. Set
  `trustForwardedHeaders: true` on `createConsentRoute` only when your
  host overwrites `x-forwarded-for`, as Vercel and Cloudflare do. Otherwise a
  visitor could send a false IP address to your backend.

## SPA mode, prerendered pages and static hosts

A prerendered page is the same HTML for every visitor, so it cannot contain one
visitor's consent. Drop the loader, pass an empty `state`, and let the browser
resolve consent from the backend URL `consentManifest()` read:

<include src="../../shared/examples/tanstack-start/static-root.mdx" />

- `state={{}}` means no server state. The page renders without consent UI and
  every optional category stays denied until the browser has the policy.
  `ConsentRoot` takes the backend URL from `consentManifest()`; without the
  plugin, an empty state throws, because there is no backend to ask. Pass
  `state={{ mode: testing() }}` to resolve without one.
- The browser sends its `/init` request straight to your backend URL, so the
  host needs no server route or server function. Add the site's origin to
  your Inth project's trusted origins.
- `consentPrefetchHead` is optional. It adds an inline script to `<head>` that
  starts the `/init` request before the app's JavaScript loads, and
  `ConsentRoot` uses that response instead of sending its own. If Inth
  assigns a banner experiment's arm, pass the experiment too:
  `consentPrefetchHead({ projectUrl, experiment })`. Without it,
  `ConsentRoot` sends a second `/init` for visitors who have not chosen yet.

Drop the consent loader from a prerendered root. A loader that stays anyway
is safe: while TanStack Start prerenders (`TSS_PRERENDERING`),
`resolveConsent` treats the render as shared. It reads no cookie or location
header, returns no stored consent, clock or GPC signal, and makes no manifest
request, so no build-time state is baked into the HTML. Pass `shared: true`
to force the same for other HTML you cache for every visitor. To prerender
every page, configure the Vite plugin as
`tanstackStart({ prerender: { enabled: true } })` and serve the output as
static files. SPA mode renders the same root route
into its shell.

`@inth/tanstack-start/static` is a lower-level alternative that bundles the
manifest at build time. `createStaticConsentResolver({ manifest, geoUrl })`
gives first paint the manifest's unknown-location policy, its fallback rule
or else its default rule, then the visitor's regional policy once `geoUrl`
answers. You write the consent transport yourself, and new policy needs a
rebuild. A manifest with neither rule resolves to a failed
`insufficient-inputs` result.

## Know when ConsentRoot loads its engine

`ConsentRoot` keeps Inth's consent engine out of the page's first-load
JavaScript. The engine is the code that stores consent, saves choices and
renders the banner in React. The server still renders the whole root, so the
banner, its styles and any scripts the server starts are in the first HTML,
with the consent state the page rendered from.

In the browser the page under `ConsentRoot` hydrates at once. Until the engine
loads, Inth's hooks return the consent state the server rendered with, and
most of their actions, such as `useSetActiveUI()`, wait for the engine and run
when it arrives. The banner keeps its server HTML.

A tap on the banner before the engine loads is handled without waiting for
all of it:

- **Accept or Reject** hides the banner at once. For a visitor with no stored
  choice, the choice takes effect while the browser is still handling the tap,
  before any download. Plain `scripts` entries the choice allows (a `src` with
  no callbacks, vendor or IAB fields) are inserted first, so their requests
  start at the tap. A small chunk requested right after the tap then stores
  the consent record, queues the save for your backend and calls
  `onChoiceRecorded` and `onPermissionsChanged`. Then the engine loads. It
  starts from the stored choice, sends the queued save and records nothing a
  second time.
- **Customize** hides the banner at once and opens the dialog from its own
  chunk. That chunk starts downloading when the pointer goes down on the
  button. With `consentManifest()` in the Vite config, the build gives the
  dialog's code a few files of its own instead of one per set of importers,
  so the tap fetches it in about one round trip. The engine loads once the
  dialog is on screen.

When the engine loads depends on the visitor:

| Visitor | Engine loads |
| --- | --- |
| The banner asks them to choose and no optional category is allowed | When the first of these happens: every `<img fetchpriority="high">` on the page has loaded, the visitor presses a pointer or key or scrolls anywhere outside the banner, a tap on the banner was recorded, or 10 seconds pass. A page without a priority image waits for the `load` event instead. |
| A returning visitor who already chose and sees no banner or dialog | At the same moments as the row above. Until then `ConsentRoot` inserts the plain `scripts` and `useScriptLoader()` entries their choice allows itself, as hydration starts. |
| Any other visitor, such as one under an IAB policy or one whose browser holds a newer choice than the server read | As soon as the browser runs `ConsentRoot`'s first-load chunk, before hydration. |

On a slow connection the engine would otherwise share bandwidth with the
page's largest image and delay Largest Contentful Paint. The browser stops
measuring that paint at the first input or scroll, so loading the engine then
costs it nothing.

For a returning visitor, the server leaves a small inline script after the
page that checks the browser's stored records against the state the server
read. When the browser holds something the server did not see, such as a
newer denial in `localStorage`, a Global Privacy Control signal or a decision
that has expired, the engine loads at once instead: it applies the change,
and `onPermissionsChanged` reports it, before the page's priority images
finish. The root checks again before each script it starts, and whenever
another tab writes storage, the page becomes visible or gets focus, or the
decision reaches its expiry while the engine waits. When the stored choice
is current, nothing changes at load, so
`onChoiceRecorded`, `onPermissionsChanged` and `onSurfaceShown` fire as they
would with the engine loaded at once, when the visitor next acts. A `scripts`
entry with a vendor or IAB fields still loads the engine at once, and so do
some entries with callbacks (see below).

`useScriptLoader()` loads the script loader once the engine is in, a banner
choice was recorded, or a returning visitor's stored choice allows its
scripts, and at once for a script that may run now.

`ConsentRoot` loads the engine at once when a `scripts` entry may run for this
visitor (`alwaysLoad`, or a category that is allowed) and nothing else starts
it: the server did not start it from the HTML, and it is not a plain `src`
entry the root starts itself for a returning visitor (see the table above).
An entry with callbacks, vendor or IAB fields needs the engine, as does any
entry under `persistence: false` or `options.consentSource`.

For an entry the server started, only `onLoad`, `onError`, `onDispose` and
`persistAfterDispose` load the engine at once. The script loader is the only
thing that hears the element's `load` and `error` events, so those callbacks
would otherwise run late, or not at all if the visitor navigates away first.
A root that unmounts before its engine removes what the server started, so
only the script loader can keep the element or call `onDispose`. The other
fields let the engine wait. The server start already ran the setup that
`onBeforeLoad` does. `onConsentChange` reports a later change, which loads
the engine anyway, and the grant the page started with once the script
loader takes the script over. `persistAfterConsentRevoked` only acts on a
revoke, which loads the engine too. An entry the visitor denied that sets
`observeConsentBeforeLoad` and `onConsentChange` loads the engine at once,
so it hears the denial straight away.

`ConsentRoot` renders the engine before the page hydrates, as a statically
imported root would, when the state was not resolved for this request (a
prerendered page, or the static root's `{}`), when `options.enabled` is
`false`, with `options.experiment`, with a `networkBlocker` or
`clearOnRevocation`, for an IAB policy, or when the app renders
`IABProvider`.

With `consentManifest()` in `vite.config.ts`, the browser bundle carries no
second copy of the banner's styles: it uses the `<style>` the server put in
the page, and loads the text only when a banner renders first in the browser.

## Run on hosts that stop work after the response

After a render, the server function reports the visitor's session to the
backend in the background. With runtime fetching, the manifest cache also
refreshes in the background after its `s-maxage`. Some serverless runtimes
stop background work once the response is sent. Pass your
platform's `waitUntil` as `onBackgroundRevalidate` to
`createConsentStateHandler` and `createConsentRoute` so that work
finishes. The promise never rejects.

## Check the rendering path

1. **View the page source** in a private window under a policy that asks for a
   choice. An awaited loader includes an element with
   `data-testid="consent-banner-root"`, and so does a streamed loader. A
   prerendered page does not.
2. **Filter DevTools Network by `subjects`** and reject. The `POST` goes to
   `/api/inth/subjects` on your origin with the same-origin route, and to your
   backend URL otherwise.
3. **Vendor requests** stay absent until you allow their category, on every
   path.
