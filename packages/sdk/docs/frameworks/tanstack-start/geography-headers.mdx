Inth resolves regional policies on your TanStack Start server by reading location, language, and Global Privacy Control headers added by your host or CDN.

## Where the location comes from

The server helpers read request headers directly and never look up visitor IP addresses. When no location header is present, the policy resolves using its fallback rule for an unknown location.

## Which headers are read

`consentRequestMiddleware`, `createConsentStateHandler`, `resolveConsent`, and the `/api/inth/v1/consent/init` route check these headers in priority order, using the first value found:

| Input | Headers, highest priority first | Set by |
| --- | --- | --- |
| Country | `x-inth-country`, `cf-ipcountry`, `x-vercel-ip-country`, `x-amz-cf-ipcountry`, `x-country-code`, `x-country` | Inth override, Cloudflare, Vercel, CloudFront, generic proxies |
| Region | `x-inth-region`, `cf-region-code`, `x-vercel-ip-country-region`, `x-region-code` | Inth override, Cloudflare, Vercel, generic proxies |
| Language | `accept-language`, negotiated by quality value to a primary tag such as `de` | Browser |
| Global Privacy Control | `x-inth-gpc`, `sec-gpc` (`1` and `0` only) | Inth override, browser |

Vercel adds country and region headers automatically. Cloudflare adds `cf-ipcountry`; enable Cloudflare's visitor location headers for `cf-region-code`. On another host or standalone Node server, set `x-inth-country` and `x-inth-region` at your edge.

## Read the headers once per request

`createConsentStateHandler` and `createConsentRoute` read these headers automatically, so the [quickstart](/docs/frameworks/tanstack-start/quickstart) needs no middleware. Register `consentRequestMiddleware` in `src/start.ts` when your own server code needs resolved location context, or to force a location globally:

On every request, including server functions and server routes, the middleware:

- reads the headers listed above,
- normalizes them onto the request as `x-inth-country`, `x-inth-region`, and `sec-gpc`,
- exposes them on `context.consent`,
- and prevents shared caches from storing personalized consent HTML. See [Keep visitor pages out of shared caches](#keep-visitor-pages-out-of-shared-caches).

You can also attach it to a single server function:

On runtimes with immutable request headers, the middleware stores the normalized values internally and Inth helpers read from that store first. Pass `normalizeHeaders: false` to leave request headers untouched.

## Keep visitor pages out of shared caches

The middleware sets no cookie. The visitor's subject ID (`sub_...`) lives inside the consent records written on their first save, which `resolveConsent` reads from cookies.

If a subject ID contains an unpaired UTF-16 surrogate such as `'sub_\uD800'`, Start's server-to-client serialization replaces it with U+FFFD while valid Unicode passes through unchanged. When `localStorage` holds the browser copy, Inth uses the original ID; if cookies are the only copy, the browser adopts the serialized ID.

Shared caches can store any response whose `Cache-Control` omits `private` and `no-store` (`private="Set-Cookie"` alone is not enough), and CDNs prioritize `CDN-Cache-Control`, `Vercel-CDN-Cache-Control`, `Cloudflare-CDN-Cache-Control`, and `Surrogate-Control`. Whenever `resolveConsent` reads visitor cookies for a page, `consentRequestMiddleware` sets `Cache-Control: private`, removes `public`, `s-maxage`, `proxy-revalidate`, and CDN cache headers, while preserving browser directives such as `max-age` and `no-cache`.

Responses from `createConsentRoute()` keep their own headers: `/v1/consent/manifest` is public and cacheable, while `/v1/consent/init` is private. To cache shared HTML for all visitors, pass `shared: true` to `resolveConsent`.

If you customized `storageConfig.storageKey` in the browser, pass the same name as `cookieName` to `resolveConsent`:

{/* example: fragment */}

```ts title="resolveConsent call (partial)"
resolveConsent({ cookieName: 'my-consent' });
```

## Where the location goes

What happens next depends on your [rendering setup](/docs/frameworks/tanstack-start/rendering):

| Code | What it does with the location |
| --- | --- |
| `createConsentStateHandler` and `resolveConsent` | Resolves policy on the Start server from the bundled or cached manifest. Manifest fetches to Inth send no visitor location, only headers listed in `forwardHeaders` |
| `/api/inth/v1/consent/init` from `createConsentRoute` | Resolves policy on the Start server from request headers for browser init |
| `createConsentRoute({ proxy: true })` | Forwards location headers, `accept-language`, `sec-gpc`, `user-agent`, `origin`, `sec-fetch-site`, and `referer` to Inth on proxied requests such as `POST /v1/consent/records` |
| State without `routePrefix` | Browser calls `/v1/consent/init` on your Inth project directly, and Inth reads its own edge headers |

## Forwarding headers are ignored by default

A relative `projectUrl` or `manifestUrl` resolves against the request URL received by the Start server. Inth ignores `x-forwarded-host`, `x-forwarded-proto`, and `forwarded` by default so untrusted clients cannot redirect server fetches or proxied saves. If your server accepts arbitrary `Host` headers directly, always pass an absolute `projectUrl` and `manifestUrl`.

The consent proxy sets `x-forwarded-host` and `x-forwarded-proto` from the request URL and forwards `x-forwarded-for` only when you pass `trustForwardedHeaders: true` on `createConsentStateHandler` and `createConsentRoute`. Enable that flag only behind a proxy that overwrites those headers and strips client-supplied values.

## Trust the location headers

Because `x-inth-*` headers have top priority and clients can send them, strip incoming `x-inth-*` headers at your edge if policy selection must strictly follow CDN geolocation. Note that stripping them also disables browser-side `options.overrides` testing through your edge.

Generic headers (`x-country-code`, `x-country`, `x-region-code`) reflect client input unless overwritten by your proxy. Platform headers (`cf-ipcountry`, `x-vercel-ip-country`) are trustworthy as long as clients cannot bypass the platform to hit your origin directly.

## Force a location

Pass `country`, `region`, or `language` to override detected values:

- `consentRequestMiddleware({ country: 'DE' })` applies to every request.
- `createConsentStateHandler({ country: 'DE' })` applies to that server function (`country` and `language` only).
- `InthProvider` accepts `options={{ overrides: { country, region, language } }}` for client-side overrides after hydration.

Server function options override middleware options.

## Test another location

Send override headers to your local server and check whether the banner appears in the HTML:

{/* example: fragment */}

```sh
curl -s -H 'x-inth-country: DE' http://localhost:3000/ | grep -c consent-banner-root
curl -s -H 'x-inth-country: US' -H 'x-inth-region: CA' http://localhost:3000/ | grep -c consent-banner-root
```

The first command outputs `1` under an EU opt-in policy; the second matches your California rule. With the consent route mounted, send the same headers to `/api/inth/v1/consent/init` to inspect the JSON `location` and `policyResolution`.

## Verify

1. Log `context.consent` once on your deployed site from a server route or server function and confirm your CDN sends the expected country and region.
2. View page source from two regions with different policies (for example via a VPN) and confirm the banner appears only where required.
3. Send `x-inth-country` from outside your edge and confirm your edge strips it if enforced.
