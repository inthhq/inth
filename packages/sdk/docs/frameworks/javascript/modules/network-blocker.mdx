Hold `fetch` and `XMLHttpRequest` requests to tracking domains until their
consent category is allowed.

## When you need it

Use the network blocker for requests you cannot move behind the
[script loader](/docs/frameworks/javascript/modules/script-loader), such as a
first-party events endpoint or a bundled vendor SDK.

## Add rules

Pass `networkBlocker` to `init()` or `createConsentRuntime()`:

{/* example: fragment */}

```ts
networkBlocker: {
	rules: [
		{
			id: 'events',
			domain: 'example.com',
			pathIncludes: '/api/track',
			methods: ['POST'],
			category: 'measurement',
		},
	],
},
```

Matching requests are held as soon as the client or runtime is constructed,
even before `start()` runs. For a manual kernel, attach
`createNetworkBlocker`:

<include src="../../../shared/examples/javascript/network-blocker.mdx" />

`createNetworkBlocker` returns `{ dispose, updateRules, setEnabled }`.
Dispose blockers in reverse creation order so original `fetch` and
`XMLHttpRequest` references restore cleanly.

## Rule fields

| Field | Required | What it does |
| --- | --- | --- |
| `domain` | Yes | Host to match, including subdomains. |
| `category` | Yes | Required category or condition. |
| `pathIncludes` | No | Matches URLs whose path contains this string. |
| `methods` | No | Restricts to listed HTTP methods (all methods if omitted). |
| `id` | No | Rule identifier for logs and `onRequestBlocked`. |
| `vendor` | No | Also blocks when the visitor turned this vendor off. |
| `vendorId`, `iabPurposes`, `iabLegIntPurposes`, `iabSpecialFeatures` | No | IAB TCF conditions under an IAB policy. |

## Blocker options

| Option | Default | What it does |
| --- | --- | --- |
| `rules` | required | Rule list above. |
| `enabled` | `true` | `false` keeps configuration without blocking. |
| `logBlockedRequests` | `true` | Logs blocked requests with `console.warn` (`[inth] blocked ...`). |
| `onRequestBlocked` | none | Receives `{ method, url, rule }` for each blocked request. |

## What a blocked request sees

- Blocked `fetch` calls resolve with HTTP status `451` (check `response.ok`).
- Blocked `XMLHttpRequest` calls abort and fire an `error` event.
- Requests sent while policy loads wait until resolution (blocked if policy
  loading fails); synchronous XHRs throw `NetworkError` instead of waiting.
- If an on-demand blocker chunk fails to load, matching requests block until
  the browser comes back online and the retry succeeds.
- Unmatched requests proceed immediately.

## What it cannot block

The blocker patches `fetch` and `XMLHttpRequest` in the current window only.
It does not intercept `navigator.sendBeacon`, WebSockets, `EventSource`,
`<img>`/`<script>` requests, other frames or service workers.

## Check it works

1. Trigger a matching request before choosing; Console logs `[inth] blocked`
   and Network shows no request.
2. Allow the category and repeat; the request succeeds.
3. With `reloadOnConsentRevoked: false`, withdraw the category and confirm
   subsequent requests block again.
