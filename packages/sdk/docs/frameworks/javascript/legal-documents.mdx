## Check and accept on a sign-up page

`createRuntimeDocuments` from `@inth/sdk/runtime/documents` binds `check`
and `accept` to your client's runtime: they use its backend, subject ID and
property. Their code loads only when you first call one. The script-tag files
(`inth.js` and the others) do not support them yet: they cannot load code on
demand.

```ts title="src/sign-up.ts"
import { init } from '@inth/sdk';
import { createRuntimeDocuments } from '@inth/sdk/runtime/documents';

const client = init({ projectUrl: 'https://your-project.inth.app' });
const { check, accept } = createRuntimeDocuments(() => client.runtime);
const form = document.querySelector<HTMLFormElement>('#sign-up');
const label = document.querySelector<HTMLElement>('#terms-label');
const button = document.querySelector<HTMLButtonElement>('#sign-up-button');

const terms = await check('terms_us');
if (label && !terms.accepted) {
	label.hidden = false;
	label.querySelector('.version')?.replaceChildren(terms.document.version);
	// Required only while shown: a visitor who accepted can still submit.
	const checkbox = label.querySelector('input');
	if (checkbox) {
		checkbox.required = true;
	}
}
if (button) {
	button.disabled = false;
}

form?.addEventListener('submit', async (event) => {
	event.preventDefault();
	if (!terms.accepted) {
		// Rejects when the backend did not record it: no account then.
		await accept({ type: 'terms_us', hash: terms.document.hash });
	}
	// Create the account.
});
```

```html title="index.html"
<form id="sign-up">
	<label id="terms-label" hidden>
		<input type="checkbox" /> I accept the
		<a href="/terms">terms of service</a> (version <span class="version"></span>)
	</label>
	<button id="sign-up-button" type="submit" disabled>Sign up</button>
</form>
```

The button stays disabled until `check` has answered, and the account is
created only once `accept` has succeeded.

## What `check` and `accept` do

`check(type)` reads the release of `type` in force from
`GET /v1/documents/{type}/current` and resolves with `{ document, accepted }`.
`document` carries the `version`, `hash`, `effectiveDate` and
`requiresAcceptance` of that release. `accepted` is `true` only when this
browser remembers an acceptance of that release, by its hash, for the same
project and the visitor's current subject ID. An earlier release accepted does
not count, because the browser cannot see the releases published in between.
When `document.requiresAcceptance` is `false` you may choose not to ask again a
visitor who accepted before; that is your app's call. A type with no release in
force rejects with an API error whose `code` is `not_found`.

`accept(documents, options?)` takes one `{ type, hash }` or an array of them,
with the `hash` that `check` gave. It waits until the visitor's subject ID is
settled, then sends one `POST /v1/documents/acceptances` under it, with the
property the consent records use, and resolves with what the backend recorded.

The subject ID belongs to consent: `accept` never creates or changes it. When it
changes, for example when another tab's consent record replaces it or the
records are cleared, the visitor is asked again.

Without a verified identity, the acceptance is recorded for the device. Pass
`externalId` and `identityProvider` with an `identityToken` your server signed,
and it is recorded for the person; this browser then remembers nothing for the
device.

Both calls need a backend: the one your consent records go to. In tests, with
`testing()` or an offline mode, they reject.

## What this browser remembers

The backend has no route that tells a browser what it accepted, so this browser
remembers each acceptance it recorded, for the project and subject ID it was
recorded under. While the visitor has a consent record, it is stored in
`localStorage` and lasts as long as consent keeps that subject ID. Before the
visitor's first consent choice it is remembered for the page only, so after a
reload they are asked again. Clearing the visitor's consent records forgets it.
Where storage is blocked, it is remembered for the page only.

When your server knows who the person is, for example after sign-up, record the
acceptance from the server with the project's secret key and the person's
`externalId`. That record does not depend on this browser.

## Handle errors and retry

Both calls reject with an API error when the backend refuses them; test it with
`isInthApiError`. `accept` never sends anything again by itself. To retry after a
network failure or a server error, send the same action with the same
idempotency key, so the backend records it once. Do not retry other errors,
such as `document_unknown` for a release the project never published, or
`subject_conflict`.

```ts
import {
	createIdempotencyKey,
	isInthApiError,
} from '@inth/sdk/runtime/documents';

const idempotencyKey = createIdempotencyKey();
const send = () =>
	accept({ type: 'terms_us', hash }, { idempotencyKey });

try {
	await send();
} catch (error) {
	const temporary =
		!isInthApiError(error) || error.status >= 500 || error.code === 'rate_limited';
	if (!temporary) {
		throw error;
	}
	await send();
}
```

The code behind `check` and `accept` loads the first time you call one of
them, so a page that never calls them does not download it.
