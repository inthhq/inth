Run custom logic when visitors save consent, effective permissions change,
network requests fail or a revocation reload is about to fire.

## Pick the hook for the job

| You want to | Use |
| --- | --- |
| Start or stop code when permissions change | `callbacks.onPermissionsChanged` or `consent.on('consent', ...)` |
| Track explicit accept, reject or save actions | `callbacks.onChoiceRecorded` |
| Wait for initial policy resolution | `consent.ready()` or `consent.on('ready', ...)` |
| Control a custom banner or dialog | `consent.on('ui', ...)` or `kernel.subscribe` |
| Report failed backend requests | `callbacks.onError` or `consent.on('error', ...)` |
| Flush state before a revocation reload | `callbacks.onBeforeConsentRevocationReload` |

Prefer gating vendor scripts through `scripts` and using per-script `onLoad`
and `onConsentChange` callbacks; see
[script loader](/docs/frameworks/javascript/modules/script-loader).

## Pass callbacks

`callbacks` works identically in `init()` and `createConsentRuntime()`:

<include src="../../shared/examples/javascript/callbacks.mdx" />

| Callback | Payload | When it runs |
| --- | --- | --- |
| `onChoiceRecorded` | `{ snapshot, confirmed, actionAt }` | Visitor accepted, rejected or saved. |
| `onPermissionsChanged` | `{ snapshot, previous }` | Effective permissions changed for any reason. |
| `onError` | `{ error }` (message string) | A command failed (such as `/v1/consent/init` or save). |
| `onBeforeConsentRevocationReload` | `{ preferences }` | Synchronously right before a withdrawal reload. Keep it brief. |

Callbacks are read once when the client or runtime is created.

## A recorded choice is not a permission change

`onChoiceRecorded` runs only for explicit visitor actions (not restored
choices, expiry or notice dismissal). `onPermissionsChanged` runs whenever
permitted categories change (saves, restored choices, policy resolution,
expiry or GPC). Never trigger a save inside `onPermissionsChanged`. See
[a permission is not a recorded choice](/docs/concepts/how-consent-works#a-permission-is-not-a-recorded-choice).

## Kernel events

With `createConsentRuntime` or a manual kernel, subscribe directly to kernel
events:

{/* example: fragment */}

```ts
const stop = runtime.kernel.events.on('choice:recorded', ({ confirmed }) => {
	console.info('Visitor confirmed', confirmed);
});
```

Callbacks are wired onto `choice:recorded`, `permissions:changed` and
`command:error`; see [kernel events](/docs/frameworks/javascript/api/kernel#events).
Use `wireRuntimeCallbacks({ kernel, callbacks })` from `@inth/sdk/runtime`
to attach callbacks to a manual kernel.

## Errors thrown by your code

Errors thrown in callbacks or kernel listeners do not abort the consent
action or other listeners; Inth reports them via `reportError` (or
`console.error` for client `on()` listeners).

## Check it works

1. Register `onChoiceRecorded` and `onPermissionsChanged`, then open the app
   in a private window under an opt-in policy. Neither logs on load.
2. Click **Accept All**. Both log.
3. Reload. `onPermissionsChanged` logs restored permissions while
   `onChoiceRecorded` stays silent.
