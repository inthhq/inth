## What the runtime owns

`createConsentRuntime` builds a [consent kernel](/docs/frameworks/javascript/api/kernel)
and connects the modules a page needs, such as stored choices, script
loading, iframe gating, network blocking, data clearing, IAB, callbacks and
the reload after a withdrawal. It renders nothing. Use it when you render your own UI, connect a
framework without an Inth adapter, or share one consent state between several
parts of a page. `@inth/sdk` builds one for you; see
[choose a headless API](/docs/frameworks/javascript/headless#choose-a-headless-api).

<include src="../../../shared/examples/javascript/runtime.mdx" />

Creating the runtime has no side effects. It reads no storage and sends no
request until `start()`, so the module can also load on a server.

## Options

Only `mode` is required.

| Option | Type | Default | What it does |
| --- | --- | --- | --- |
| `projectUrl` | `string` | required | Your Inth backend URL. Not needed with `mode: testing()` or `enabled: false`. |
| `mode` | `hosted()`, `manifest()` or `testing()` | `hosted()` | Where the policy comes from. `testing()` comes from `@inth/sdk/testing` and throws in production builds. See [transports](/docs/frameworks/javascript/transports). |
| `scripts` | `Script[]` | none | Vendor scripts the loader mounts as categories are allowed. See [script loader](/docs/frameworks/javascript/modules/script-loader). |
| `consentCategories` | category names | inferred | Categories to offer alongside those your scripts, rules and vendors use, within the policy's scope. |
| `networkBlocker` | `{ rules, enabled?, logBlockedRequests?, onRequestBlocked? }` or `false` | off | Hold matching `fetch` and XHR requests until their category is allowed. See [network blocker](/docs/frameworks/javascript/modules/network-blocker). |
| `iframeBlocker` | `{ disableAutomaticBlocking? }` or `false` | on | Gate `<iframe data-src data-category>`. See [iframe blocker](/docs/frameworks/javascript/modules/iframe-blocker). |
| `clearOnRevocation` | cookies and storage keys per category | off | Delete named browser data when its category is denied. Read once. See [clear on revocation](/docs/frameworks/javascript/clear-on-revocation). |
| `persistence` | `boolean` or `{ storageConfig?, skipHydration?, sync? }` | `true` | Read and write choices in the cookie and localStorage, and follow other tabs. `false` keeps choices in memory only. See [persistence](/docs/frameworks/javascript/modules/persistence). |
| `storageConfig` | `{ storageKey?, crossSubdomain?, defaultDomain?, defaultExpiryDays? }` | key `inth`, 365 days | Cookie and localStorage naming and lifetime. |
| `reloadOnConsentRevoked` | `boolean` | `true` | Reload after an accept, reject or save turns off a category or vendor that was allowed, once the save request finishes. |
| `callbacks` | `{ onChoiceRecorded?, onPermissionsChanged?, onError?, onBeforeConsentRevocationReload? }` | none | See [callbacks](/docs/frameworks/javascript/callbacks). |

| `prefetch` | kernel configuration | none | A server-resolved init answer. With a resolved policy, `start()` skips the `/v1/consent/init` request. A prefetch marked `initialPolicyPending` is provisional, so `start()` still sends it. |
| `i18n` | `{ locale?, messages }` | English | Initial language, and messages that override the bundled or backend copy key by key for the same language. See [translations](/docs/frameworks/javascript/translations). |
| `presentation` | `{ prompt?, preferences? }` | none | Layout and blocking, for UIs that call `resolveConsentPresentation`. |
| `journey` | `'page'`, `'tab'` or `false` | `'page'` | Random id that links each `/v1/consent/init` to the save that follows. See [session reports](/docs/concepts/data-fetching#link-an-init-to-the-save-that-follows). |
| `user` | `{ externalId, identityProvider? }` | none | An identified visitor. |
| `vendors` | `Vendor[]` | none | Vendors offered for vendor-level consent outside IAB. |
| `nonce` | `string` | none | CSP nonce the script loader puts on every `<script>` it creates. A script's own `nonce` wins. |
| `scriptLoader` | `{ onDebug?, sources? }` | none | `onDebug` receives every script loader lifecycle event. `sources` loads a script from another URL, keyed by script `id`, such as a vetted copy on your own host: `{ posthog: { src, integrity, attributes? } }`. Only the URL changes; an integration's setup, attributes and callbacks still run. `integrity` also sets `crossorigin="anonymous"`; an `integrity` with no hash a browser can parse keeps the script from loading, because the browser would run it unchecked. `attributes` sets `data-*` attributes on the tag that the script does not set itself, and removes those set to `null`. | `createIAB` | `createIAB` from `@inth/sdk/iab` | none | The IAB module factory. Without it, `iab` is ignored. |

| `enabled` | `boolean` | `true` | `false` grants every category, skips init and mounts no blocker, persistence or IAB. Scripts load at once. |
| `pkg` | `string` | `'@inth/sdk/engine'` | The package name `window.__inthDebug` reports. |

## Inth script registry (experimental)

With `experimentalScriptRegistry: true`, the runtime loads integrations by
the `scriptRegistry.sources` list that the project's consent manifest carries.
Every `/v1/consent/init` resolved from that manifest copies `scriptRegistry`, whether the
server, the browser or the backend resolves it, so the list costs no extra
request. `sources` lists a source per script `id`:

```json
{
  "scriptRegistry": {
    "sources": {
      "posthog": {
        "src": "https://acme.inth.app/scripts/posthog@0123456789abcdef.js",
        "integrity": "sha384-…"
      },
      "plausible-analytics": {
        "src": "https://acme.inth.app/scripts/plausible-analytics@fedcba9876543210.js",
        "integrity": "sha384-…",
        "attributes": { "data-api": "https://plausible.io/api/event" }
      }
    }
  }
}
```

Inth ignores fields it does not know in `scriptRegistry`. The runtime reads the
list from `snapshot.scriptRegistry.sources`. With a prefetched
init, scripts load by it at once. Otherwise each script an
`@inth/integrations` helper built waits for init, then:

- With an entry, it loads from the entry's `src` with its `integrity` and
  `crossorigin="anonymous"`, and gets the entry's `attributes` as
  `scriptLoader.sources` applies them. In a tag the loader creates, the
  browser refuses bytes that do not match the hash; see below for a tag a
  server start already put on the page. An integration that inserts its own tag, such as HubSpot,
  gets the `src` and `integrity` but not the `attributes`.
- Without an entry, it loads from the vendor's URL, as it did before the
  project enrolled it.
- With an entry Inth cannot use, it does not load at all, from either URL.
  That is `null`, or an entry with no `sha256-`, `sha384-` or `sha512-` hash,
  no https `src`, or an attribute that is not a string or `null`. `onDebug`
  reports an `error` for it.

When init answers without a list, every script loads from its vendor's URL.
A runtime with `enabled: false` or a `consentSource` never calls `/v1/consent/init`, so it
uses only a prefetched list.

#### When init fails

Inth remembers the last list this browser received and loads by it when init
fails, such as during an outage, a rate limit or a blocked request. It does the
same when init answers `"scriptRegistry": { "unavailable": true }`, which the
backend sends when it could not read the project's registry. The remembered
list works exactly as a fresh one, `sources`, `files`, `null` entries and
`refuseIfSet` included, and Inth checks it the same way, so a stored list it
cannot read counts as no list. Without a remembered list, every script loads
from its vendor's URL.

When init fails, optional categories stay denied, so only `necessary` scripts
load and the list applies to those. After an `unavailable` answer the visitor's
choices apply as usual, and the list applies to every script that loads.

- **Stored like the rest of Inth's state.** The list is kept in `localStorage`
  under `inth-script-registry:v1:` followed by the runtime's absolute
  `projectUrl`. It is written only once the visitor has made a choice, when Inth
  stores its own record, and never with `persistence: false`, which turns it
  off entirely. A page whose scripts are all `necessary` gets no choice, so
  nothing is remembered for it.
- **Per backend.** One project's list is never read for another project or
  backend on the same origin. A runtime with no `projectUrl`, or one that never
  calls `/v1/consent/init`, remembers nothing.
- **Replaced by every answer.** Each init that answers replaces the list. An
  answer with no `scriptRegistry` removes it, so turning the registry off for a
  project takes effect on the next visit that reaches `/v1/consent/init`. An `unavailable`
  answer leaves it, even beside empty `sources` and `files`.
- **Seven days at most.** After that the list is dropped, and a failed init
  loads from vendor URLs again. A remembered list can name a version the
  registry has rejected since. The registry then answers that URL with an
  error, and the hash stops any other bytes, so the script does not load.
- **256 KB at most.** A stored value larger than that is refused and removed.
  A list for every integration is about 30 KB.
- **Not a defence against the page.** Any script on your origin can edit
  `localStorage`. The remembered list keeps scripts pinned through honest
  failures; it does not protect against code already running on the page.
- **Storage unavailable.** In private browsing, with storage blocked, or with
  storage full, Inth remembers nothing and a failed init loads from vendor URLs.

The runtime reads the list once, when init first answers or first fails. A later
init, including a retry that succeeds after a failure, replaces the remembered
list but does not move or unload scripts that already loaded, from the
remembered list or from the vendor. A later `null` entry takes effect on the
next page load.

When a script's registry copy fails to load, because the bytes do not match or
the backend answers 423 or 410, Inth calls its `onError` and does not try the
vendor's URL. The registry is holding that version back on purpose.

Your own `scriptLoader.sources` entry for a script wins over the list, and
applies without waiting for init. To pin a version, copy the entry's `src` and
`integrity` there. A hash in your own code is one the backend cannot change. A
script that declares its own `integrity` keeps it too, and loads from the
registry only when the entry lists that hash. A script the runtime starts on
the server starts from the prefetched list the same way.

The hash check covers the tags the loader creates. A tag a server start
already put on the page is kept as it is, so the vendor's setup does not run
twice. `onDebug` reports `already_loaded` with its `serverSrc` when its URL
differs. A server start from the same prefetch uses the same list.

The early start in the deferred framework roots and the script-tag build does
not apply `scriptLoader.sources` yet. For a returning visitor, a plain script
with an entry can start from its own URL there before the engine loads.

The list's hashes come from the same backend that serves the files. They stop a
copy that changed after the registry recorded it, but not a backend that sends
another list. Scripts you write yourself are not affected.

### Files a loader downloads

Some vendor scripts are small loaders that download more code while they run.
Today the registry pins one such file: LogRocket's `LogRocket.min.js` inserts
`https://cdn.logrocket.io/logger-1.min.js`, about 780 KB. `sources` pins only
the loader. `scriptRegistry.files` pins the file it downloads, keyed by the
exact absolute URL the loader requests:

```json
{
  "scriptRegistry": {
    "sources": {
      "logrocket": {
        "src": "https://acme.inth.app/scripts/logrocket@0123456789abcdef.js?logger=fedcba9876543210",
        "integrity": "sha384-…"
      }
    },
    "files": {
      "https://cdn.logrocket.io/logger-1.min.js": {
        "src": "https://acme.inth.app/scripts/logrocket/logger@fedcba9876543210.js",
        "integrity": "sha384-…"
      }
    }
  }
}
```

Once a list that names files has arrived, Inth changes a script element whose
URL `files` lists just before the browser fetches it:

- With an entry, the element loads from the entry's `src` with its `integrity`
  and `crossorigin="anonymous"`. The browser refuses bytes that do not match,
  and Inth does not try the vendor's URL. An element with its own `integrity`
  keeps it, and loads from the registry only when the entry lists that hash.
- With `null`, or an entry with no https `src` or no hash, the element points at
  an empty `data:` script under a hash it does not have. The browser fetches
  nothing from either URL and fires `error`, so the loader's own failure
  handling runs.
- A URL that `files` does not list is not changed.

Inth matches URLs after it resolves a relative URL against the page and drops
the fragment. Everything else must match exactly. The query string is part of
the URL, so `logger-1.min.js?v=2` does not match `logger-1.min.js`.

Inth checks a script element as a page method inserts it, or the node holding
it: `appendChild`, `insertBefore`, `append`, `before`, `replaceWith`,
`insertAdjacentElement`, `Range.insertNode` or a similar method. It also
checks a script already on the page as it gets its first `src` through
`script.src` or `setAttribute`. Scripts that Inth creates go through the same
check. To do this, the script loader patches those DOM methods once the list
names files. On `dispose()` it puts back each method it is still the outermost
wrapper of. Under a wrapper another library added later, its own stays in that
library's chain and does nothing until a list names files again.

Nothing waits for the list. Integrations wait for init as described above, so
LogRocket's loader starts only after the pin is in place. Every other script
loads as it would without Inth. A script that a list names, but that some other
code inserts before init answers, loads from its own URL. When the list names no
files, or init fails, Inth patches nothing. When a prefetched list names files,
a server start leaves integrations for the loader to start.

#### What `files` does not cover

`files` sees only script elements that this realm's DOM methods insert after
the list arrives. These load code without Inth seeing it:

- A listed file that other code inserts before init answers.
- `document.write` of a script tag.
- `eval` or `new Function` on code a loader fetched itself.
- `import()`, and static `import` statements inside a module script, the
  pinned one included.
- Workers, including `importScripts` in a worker.
- Iframes, including `srcdoc` frames, and a script element made with another
  frame's DOM methods.
- Code that kept its own reference to a DOM method, such as
  `const append = Node.prototype.appendChild`, before the pin went on. If such
  code writes that method back while the pin is on, the pin is off for that
  method until a script loader with a list starts again, which puts it back.
- A script inside a shadow root of a node the page inserts. A script the page
  inserts into a shadow root that is already on the page is checked.
- A `src` that a script already on the page gets through `setAttributeNS`,
  `setAttributeNode` or `attributes.setNamedItem`, and a `<script>` inside an
  inline SVG.
- A script tag in your HTML, or one that a deferred root or the script-tag build
  starts before the script loader runs.
- A URL that a page override gives the loader and that the list does not name,
  such as LogRocket's `window.__SDKCONFIG__.loggerURL`, or `window._lrAsyncScript`
  set by your own code.

Pages that enforce Trusted Types for scripts are not supported yet: Inth writes
script URLs as plain strings.

#### Options that move a loader's downloads

Some integration options tell a loader to download its code from another
server, which `files` cannot pin. For LogRocket these are `asyncScriptUrl`,
`initOptions.sdkServer` and `initOptions.enterpriseServer`. For such a loader,
the registry's `sources` entry lists those options in `refuseIfSet`, as dotted
paths into the integration's options:

```json
{
  "logrocket": {
    "src": "https://acme.inth.app/scripts/logrocket@0123456789abcdef.js?logger=fedcba9876543210",
    "integrity": "sha384-…",
    "refuseIfSet": [
      "asyncScriptUrl",
      "initOptions.sdkServer",
      "initOptions.enterpriseServer"
    ]
  }
}
```

When your options set any listed path, the script loads nothing: not from the
registry, and not from the vendor's URL. `onDebug` reports an `error` that names
the path. Inth reads an option as the loader does: `undefined`, `null`, `''`,
`false` and `0` count as unset, and so does a blank `asyncScriptUrl`. For
LogRocket that means a page that moves the logger with `asyncScriptUrl`, or sets
`sdkServer` or `enterpriseServer`, gets no LogRocket at all while the registry
is on: the loader would fetch a file the list does not name. A script that
carries no options to check also loads nothing. A `refuseIfSet` that is not a list of paths makes the entry one
Inth cannot use. To load such a script with that option, give it your own
`scriptLoader.sources` entry, which wins over the list.

Only a Content Security Policy closes these gaps in your page, for files on a
vendor host. Allow the registry and your own origin, and no vendor host:

```http
Content-Security-Policy: script-src 'self' https://acme.inth.app; worker-src blob:
```

- `script-src` lists only the gateway and your own origin. When a vendor host
  is not on the list, the browser blocks every unpinned request to it,
  whichever API makes it.
- Do not add `'strict-dynamic'`. It lets a trusted script load any script, and
  the browser then ignores the host list.
- Do not add `'unsafe-eval'`, which lets code a loader fetched run through
  `eval`.
- `worker-src blob:` lets a loader start a worker from code it already has, as
  LogRocket does. It does not allow worker files from a vendor host.

The policy applies to your page and to `srcdoc` frames, not to a frame loaded
from another origin, which runs under that origin's own policy. Add `frame-src`
to limit which origins your page can frame.

If you add a `'nonce-…'` for inline scripts, keep vendor code out of them. An
inline script with a nonce can `import()` a module from any URL, because the
browser gives the nonce to the import as well.

## What start and dispose do

`runtime.start()` mounts, in order:

1. the `window.__inthDebug` debug object, `{ version, pkg, mode, hosting }`.
   `hosting` reads the current snapshot, so it changes from `null` once
   `/v1/consent/init` reports it;
2. persistence, which reads stored choices;
3. the `/v1/consent/init` request. With a resolved `prefetch` it adopts that answer
   instead: the choice is evaluated at the server's clock, the banner the
   server rendered counts as the first impression, a detected Global Privacy
   Control signal is honoured, and `init:applied` fires as it would for a
   response;
4. the script loader, when `scripts` is not empty;
5. the network blocker, when configured;
6. the iframe blocker, unless `iframeBlocker: false`;
7. the IAB module, when `iab` and `createIAB` are set;
8. data clearing, when `clearOnRevocation` is set.

`start()` does nothing without a `document`, so you can call it from shared
code. A second call does nothing. The callback bridge and the reload watcher
attach at construction, so they hear events from the first `start()`.

In a client-only app, with no server-rendered markup to hydrate, you can call
`start()` before the first render: the `/v1/consent/init` request then runs while the app
mounts, and nothing waits for it. With server-rendered markup, call it after
hydration so the first browser render matches the server's.

The network blocker and data clearing are opt-in, so they load as separate
chunks, and only when configured. Network blocker rules hold matching requests
from construction until the blocker has loaded and decides each one. Data
clearing waits for the policy anyway.

`runtime.dispose()` undoes everything in reverse, then disposes the kernel.
A runtime disposed before it started blocks the requests it was holding.

## Runtime handle

| Member | What it does |
| --- | --- |
| `kernel` | The kernel. Read and change consent through it. |
| `start()`, `dispose()` | Mount and unmount every browser side effect. |
| `started` | Whether `start()` has run and the runtime is not disposed. |
| `identify(user)` | Link the consent record to a user. Failures surface through `onError`, not a rejection. |
| `setOverrides(overrides)` | Merge into the country, region, language and GPC inputs. A key you pass replaces its value, `undefined` clears it, and a key you leave out stays. |
| `reinit()` | Run `/v1/consent/init` again, for example after `setOverrides`. Does nothing while disabled. |
| `setLanguage(code)` | Show the copy in another language. Does nothing for the current language; otherwise runs `/v1/consent/init` again, unless the runtime is disabled or uses `consentSource`. |
| `processIframes()` | Pause gated iframes that consent does not allow and restore the ones it allows. Needed only with `iframeBlocker: { disableAutomaticBlocking: true }`. Does nothing before `start()`, after `dispose()` or with `iframeBlocker: false`. |
| `reconcileStorage()` | Read stored records again and apply changes another runtime or tab made. Returns whether anything changed. |
| `clearRecords()` | Delete stored choices and reset the kernel's records: choice, notice dismissal and vendor choice. The subject keeps its ID and loses its `externalId` and `identityProvider`. Saves still queued for the cleared subject are dropped. |
| `consentCategories` | `necessary` plus the categories in the current choice scope, in the order the preference dialog lists them. |
| `setConsentCategories(categories)` | Replace the configured categories. Discovered ones stay. `undefined` drops the configured list. |
| `experiment` | The experiment the runtime runs: the one a ready `prefetch` carries, otherwise the `experiment` option. Resolve presentation and theme against it. |
| `iab` | The CMP handle under IAB, or `null`. |
| `subscribe(listener)` | Called when `iab` is mounted, replaced or removed; read it again in the listener. Returns an unsubscribe function. A provider runtime also calls it when `kernel` or `enabled` changes. |

## Runtime for a framework provider

`createConsentRuntime` is for a page that configures consent once. A framework
provider whose options follow its props uses
`createConsentProviderRuntime(options, modules)` instead. It has every member
above, plus:

| Member | What it does |
| --- | --- |
| `update(options)` | Apply the provider's new options. Pass the whole option set each time; the runtime compares it with the previous one and applies only what changed. Returns a promise that settles once every change has applied. |
| `setEnabled(enabled)` | Turn consent management off or on. Off renders a separate permissive kernel that grants every category and shows no UI; only the script loader runs, and no request waits for the network blocker. On renders the visitor's kernel again, with their records, and adopts the prefetch again. It runs `/v1/consent/init` instead when there is no prefetch, or when overrides or the language changed while it was off. |
| `enabled` | Whether consent management is on. |
| `kernel` | The kernel to render. It changes when `enabled` changes. |
| `subscribe(listener)` | Called when `kernel`, `iab` or `enabled` changes. Read them again in the listener. Returns an unsubscribe function. |

`update()` applies these options to a running runtime:

| Option | On change |
| --- | --- |
| `enabled` | Same as `setEnabled()`. |
| `user` | The new user is identified. The user the runtime was created with is sent with `/v1/consent/init` and every save, and is not identified separately. |
| `overrides` | The overrides are set and `/v1/consent/init` runs again. Key order does not count as a change. Before `start()` or while disabled, the next start sends `/v1/consent/init` instead of adopting the prefetch. |
| `consentCategories` | The configured categories are replaced. |
| `vendors`, `scripts`, network blocker `rules` | Vendors are declared again. Scripts go to the script loader, rules to the network blocker. A loader starts when scripts first appear. |
| `networkBlocker` | New `rules` and `enabled` apply; leaving `enabled` out turns the blocker on. Requests new rules match wait until the blocker has them, including while an on-demand blocker loads. `false` removes the blocker; options where there were none add one. |
| `iframeBlocker` | `false` removes the blocker. A new `disableAutomaticBlocking` rebuilds it. |
| `callbacks`, `reloadOnConsentRevoked` | Read when an event fires, so the latest values apply. |

`enabled`, `overrides` and `consentCategories` apply before `update()`
returns. The rest of the comparison loads with the first `update()` in which
some option is a new value. Calling `update()` with the option values the
runtime already has, as a mount-time effect does, downloads nothing. Those
changes apply once it has loaded, and the returned promise settles then. Until
the network blocker has new or wider rules, requests they match are held, the
way the runtime holds requests from construction until the blocker loads, so
none goes out unchecked.

`nonce`, `scriptLoader.onDebug` and the network blocker's `logBlockedRequests`
and `onRequestBlocked` are read when their module starts. Every other option is
read once. Storage counts among them: persistence keeps reading and writing
where it started, and data clearing keeps protecting that location. Outside
production, a change to `mode`, `i18n`, `experiment`, `persistence` or
`storageConfig` logs a warning; create a new runtime to change them.

`prefetch` may also be a promise, for example the result of a server helper
that a framework streams to the browser, when `modules` includes
`streamPrefetch` from `@inth/sdk/runtime`, or `lazyStreamPrefetch` from
`@inth/sdk/runtime/provider`, which loads that code only for a runtime whose prefetch
is a promise. Without either, a pending prefetch is ignored with a warning
outside production, and the runtime requests the policy itself. That keeps the
code out of providers that never stream. The runtime starts with a provisional
policy, so no consent surface shows, and its first `/v1/consent/init` waits for the
promise and applies the result instead of sending a request. A result without
a policy is applied as a baseline (records, location, language) and the
request is sent with those overrides. A rejected promise sends the request as
if there were no prefetch. Records cleared while the promise is pending stay
cleared. An experiment in a streamed result arrives too late to run.

`modules` decides how each module loads. Pass `defaultRuntimeModules` to load
them the way `createConsentRuntime` does. To keep a module out of the first
chunk, replace its factory with `lazyRuntimeModule(() => import(...))`: calls
made before the module has loaded are queued and replayed. A module that
fails to load stays inactive and, outside production, logs a warning. Keep
`watchRevocationReload` static, because it has to see the first save, and
prefer a static `createPersistence`, because a lazy one shows a returning
visitor the banner until it has loaded. When the script loader is lazy, data
clearing subscribes once it has loaded, so revocation callbacks still run before
browser data is removed. IAB mounts through the `mountIAB` module
(`mountRuntimeIAB`, included in `defaultRuntimeModules`); without it `iab` is
ignored.

`onDemandRuntimeModules` loads the script loader, the network blocker, data
clearing and a `consentSource` connection on demand, in chunks that import
nothing your first chunk has. The script loader and the network blocker share
one chunk, so a page with scripts and blocker rules downloads, or preloads, one
file. Spread it into `modules` next to the modules you import statically:

{/* example: fragment */}

```ts
import { watchRevocationReload } from '@inth/sdk/engine';
import { createIframeBlocker } from '@inth/sdk/modules/iframe-blocker';
import { createPersistence } from '@inth/sdk/modules/persistence';
import { createWindowDebug } from '@inth/sdk/modules/window-debug';
import { onDemandRuntimeModules } from '@inth/sdk/runtime/on-demand';
import { createConsentProviderRuntime } from '@inth/sdk/runtime/provider';

const runtime = createConsentProviderRuntime(options, {
	...onDemandRuntimeModules,
	createIframeBlocker,
	createPersistence,
	createWindowDebug,
	watchRevocationReload,
});
```

A page that configures none of those modules never downloads them. A page
with only scripts, or only blocker rules, downloads both. Consented scripts
mount, and matching requests stay held, until the shared chunk has loaded.
Optional categories stay denied until a `consentSource` connects. A module
whose chunk fails to load is tried again when the browser comes back online.
Until then a failed network blocker blocks every request its rules match
instead of holding it. A module you load yourself with `lazyRuntimeModule`
works the same way, but if it imports code your first chunk also uses,
bundlers that split shared code (Vite, esbuild) move that code into extra
chunks the first load then fetches.

Import from `@inth/sdk/runtime/provider` when your provider loads modules on
demand. It exports `createConsentProviderRuntime`, `lazyRuntimeModule` and
`lazyStreamPrefetch`, and none of the modules `defaultRuntimeModules` imports
statically. Some bundlers, esbuild among them, keep a module in the first chunk
when it is imported statically anywhere in the graph, even unused, and also
through `import()`.

`@inth/sdk/runtime/on-demand` exports `onDemandRuntimeModules`,
`createConsentRuntimeWith` and `mountRuntimeIAB`.
`createConsentRuntimeWith(options, modules)` is `createConsentRuntime` with the
modules you choose, for a page that configures once (a script tag, an Astro
page) and loads some modules on demand. The same lifecycle and handle apply.
The two entries are separate because esbuild emits a chunk for every
`import()` in the files it reaches, used or not. A provider that loads modules
through its own `import()` calls would get the on-demand chunks as well, plus
an extra chunk for each module both load, and a page that configures once
would get the provider runtime's update and streamed-prefetch chunks.

`@inth/sdk/runtime/on-demand-factories` exports each on-demand factory on its own:
`scriptLoaderOnDemand`, `networkBlockerOnDemand`, `clearOnRevocationOnDemand`
and `connectConsentSourceOnDemand`. `scriptLoaderOnDemand` and
`networkBlockerOnDemand` each load a chunk with only their module. Use them
when you import some of those modules statically and load the rest on demand.
Spreading `onDemandRuntimeModules` instead would load the module you import
statically a second time, in the shared chunk, and a bundler then moves that
module into a chunk of its own. The factories have their own entry because
esbuild emits a chunk for every `import()` in the files it reaches, used or
not, which would split the shared chunk apart:

{/* example: fragment */}

```ts
import { watchRevocationReload } from '@inth/sdk/engine';
import { createIframeBlocker } from '@inth/sdk/modules/iframe-blocker';
import { createPersistence } from '@inth/sdk/modules/persistence';
import { createScriptLoader } from '@inth/sdk/modules/script-loader';
import { createWindowDebug } from '@inth/sdk/modules/window-debug';
import { createConsentRuntimeWith } from '@inth/sdk/runtime/on-demand';
import {
	clearOnRevocationOnDemand,
	connectConsentSourceOnDemand,
	networkBlockerOnDemand,
} from '@inth/sdk/runtime/on-demand-factories';

const runtime = createConsentRuntimeWith(options, {
	connectConsentSource: connectConsentSourceOnDemand,
	createClearOnRevocation: clearOnRevocationOnDemand,
	createIframeBlocker,
	createNetworkBlocker: networkBlockerOnDemand,
	createPersistence,
	createScriptLoader,
	createWindowDebug,
	watchRevocationReload,
});
runtime.start();
```

## Other exports

| Export from `@inth/sdk/runtime` | What it does |
| --- | --- |
| `createLazyIABFactory(loader)` | Wrap a dynamic `import('@inth/sdk/iab')` so the IAB code loads as a separate chunk when the runtime mounts IAB. Pass its `create` as `createIAB`. |
| `isIABConfigured(iab)` | Whether an `iab` option turns IAB on. |
| `wireRuntimeCallbacks({ kernel, callbacks })` | Attach the four callbacks to a kernel you own. Returns a disposer. |
| `createConsentProviderRuntime(options, modules)` | The runtime for a framework provider. See [runtime for a framework provider](#runtime-for-a-framework-provider). |
| `defaultRuntimeModules` | The module factories `createConsentRuntime` mounts. |
| `lazyRuntimeModule(load)` | Wrap a module factory so its module loads through a dynamic `import()` on first use. |
| `streamPrefetch` | Add to the provider runtime's modules to accept a `prefetch` promise. |
| `mountRuntimeIAB` | The `mountIAB` module: mounts the CMP once the kernel knows its `cmpId`. |

## Check it works

1. Create the runtime and subscribe to `runtime.kernel` before `start()`.
2. Call `start()` in the browser. The Network tab shows one `/v1/consent/init` request,
   and your subscriber receives a snapshot whose `resolution.status` is
   `matched`.
3. Call `runtime.kernel.commands.save('none')` from a button. A `/v1/consent/records`
   request follows and reloading keeps the choice.
4. Call `runtime.dispose()`. Scripts the loader added are removed.
