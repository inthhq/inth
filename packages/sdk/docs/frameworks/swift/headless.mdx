Build your own consent screens from the headless blocks in `InthConsentUI`.
They decide when a prompt is owed, hold the draft, save it, supply the
translated copy and handle VoiceOver. They draw nothing, so layout, type,
colour and motion are yours. The stock screens run on the same blocks.

Link `InthCore`, `InthApple` and `InthConsentUI`. Install with
`InthApple.install(_:)` during launch, using the same `InthAppleConfiguration`
as the [quickstart](/docs/frameworks/swift/quickstart), and leave out its
`.inthConsent` modifier. Your app owns the layout, the privacy-policy link and
a standing Privacy settings action.

## Gate content on a permission

`ConsentGate` shows its content only while the committed decision allows it. An
unresolved policy counts as not allowed.

{/* example: fragment */}

```swift
ConsentGate(.marketing) { AdBanner() } fallback: { AdPlaceholder() }
ConsentGate(vendorId: 755, purposeId: 1) { GoogleAds() }
ConsentGate(allowed: { $0.isCustomVendorAllowed("internal-ads") }) { HouseAds() }
```

The first form takes a category. The second takes an IAB vendor and purpose,
with `basis:` for legitimate interest. The third takes any check against the
core, for a purpose alone, a custom partner or an Additional Consent provider.
`ConsentReady` shows its content once a policy has resolved.

## Show your own first prompt

Create one `ConsentDraft` and hand it to both blocks. `HeadlessConsentPrompt`
calls its content only while the resolved policy owes a prompt:

<include src="../../shared/examples/native/core-swift/custom-consent/swift-headless-prompt.mdx" />

The content receives a `ConsentPromptScope` with what to place and what to
wire:

| Member | Use |
| --- | --- |
| `isNotice` | `true` for a notice to acknowledge, `false` for a consent choice. |
| `title`, `description`, `detail`, `reason` | The copy, in the policy's language. `reason` says why a prompt is back. |
| `iab` | The IAB first layer's required text under a TCF policy. |
| `acceptAll()`, `rejectAll()`, `acknowledge()` | One-tap saves. The prompt leaves once the choice is stored. |
| `openPreferences()` | Calls your `onOpenPreferences`. |
| `isStale`, `reload()` | A decision landed elsewhere after the prompt read the record, so its actions do nothing. Show `iabCopy.appSettingsChanged` and wire a control to `reload()`. |
| `listUnavailable`, `listOutdated`, `refresh()` | The IAB vendor list is stale or offline. Show `listOutdated`, keep Reject all, leave Accept all out and wire a control to `refresh()`. `acceptAll()` does nothing until the list is back. |
| `acceptAllLabel`, `rejectAllLabel`, `customizeLabel`, `acknowledgeLabel`, `privacyPolicyLabel` | Button and link labels. |

Keep the draft in a `@StateObject`, as the example does, so unsaved edits
survive view updates.

## Build a preferences screen with a draft

`HeadlessConsentPreferences` wraps your screen while it is open. Its
`categories` are rows with a title, a description, a lock and a `binding` for
your switch:

<include src="../../shared/examples/native/core-swift/custom-consent/swift-headless-preferences.mdx" />

A row with `locked` set takes no switch. Show `lockedLabel` in its place:
"Always on" for `necessary`, "Off" with a `note` for a category that Global
Privacy Control or a strict scope holds off. `isEnabled` turns false while a
save runs, while the draft is stale and while an IAB list cannot be edited.

Edits stay in the draft until `save()`. The draft seeds from the recorded
choice, never from effective permissions, and follows the record while it has
no edits. These are the save rules:

| State | What happened | What to show |
| --- | --- | --- |
| `draft.isSaving` | A save is running. | Disable controls and dismissal. `savingAction` names the pressed one and `showProgress` turns true after 400 ms. |
| `draft.errorMessage` | Storage refused the write. The edits are kept. | The message, and a control wired to `retry()`. Leave the retry out while `listUnavailable` is true: only `refresh()` helps then. |
| `draft.isStale` | Another surface recorded a decision after this draft was read, so the core refused the save. | `iabCopy.appSettingsChanged`, and a control wired to `draft.reset()`. |
| `draft.listUnavailable` | The IAB vendor list is stale or offline. | `iabCopy.appListOutdated`, and a control wired to `draft.refresh()`. |
| `confirmDiscard` | The person tried to leave with unsaved edits. | Your confirmation, wired to `discard()` and `keepEditing()`. |

A save names the snapshot revision the draft was read at. The core refuses it
with `concurrent-change` when that revision has moved, and the draft keeps the
edits visible so the person can review them against the new settings. This is
stricter than React Native, whose draft retries once when no staged category
was overtaken. Native asks for a reset after any move, as the stock screens do. A
successful save means the choice is stored on the device and queued for
delivery, not that the backend has it. `save(_:)` also has an `async` form that
returns whether the choice was stored.

## Build your own IAB screen

Under a TCF policy `iab` on the scope, or `draft.iab`, is an `IABDraftHandle`.
It has the commands `useIAB()` has on the web and in React Native, and the
core's disclosure as rows:

<include src="../../shared/examples/native/core-swift/custom-consent/swift-headless-iab.mdx" />

| Member | What it gives you |
| --- | --- |
| `firstLayer` | The first layer's description with the partner count, the partner link text, the purpose and stack summary, and the legitimate-interest, scope and withdrawal sentences. |
| `purposes` | Declared purposes with name, description, legal text, illustrations, partner counts, a consent switch and, where a partner relies on it, a legitimate-interest switch. |
| `specialFeatures` | Declared special features, each with an opt-in. |
| `specialPurposes`, `features` | What partners use with no choice. Show `specialPurposesExplanation` and `featuresExplanation` with them. Show the features text on a partner's own page too. |
| `stacks` | Every stack in the vendor list with its purposes and special features. |
| `vendors`, `vendors(purposeId:)`, `vendor(_:)` | Registered partners with their bases after publisher restrictions, switches, status and `details`, sorted by name. |
| `customVendors` | Partners outside the vendor list, with `customVendorsHeading` and `customVendorsNotice`. |
| `adTechProviders` | Google Additional Consent providers, with `adTechProvidersHeading` and `adTechProvidersNotice`. |
| `publisherRestrictions` | The restrictions your policy declares. The vendor rows already apply them. |
| `consentStorage` | How long the TC String stays on the device. |

A vendor's `consent` is `nil` when a publisher restriction left it no consent
purpose, and `legitimateInterest` is `nil` when it has no such purpose. Offer a
switch only for a value that is not `nil`. The core refuses a save that turns
either on for a vendor whose bases are empty. Setting a legitimate-interest
switch to `false` records an objection. Purposes 1 and 3 to 6 never take
legitimate interest.

`acceptAll()` stages exactly what the stock Accept all saves. `rejectAll()`
stages withdrawal of every consent and leaves legitimate interest alone. Both
save nothing until `save()`. The one-tap actions on the scopes save at once.
A first decision opens with every consent off and registered vendors'
legitimate interests not objected to. A custom partner's legitimate interest
starts off, as on the stock screens.

The core checks every ID and legal basis, encodes the TC String and the
Additional Consent string, and writes the `IABTCF_*` keys exactly as it does
for the stock screens. Gate vendors on the committed decision with
`ConsentGate` or the core's `isIABAllowed`, never on the staged rows.

### What your IAB screens must show

IAB Europe checks a mobile CMP against the list in
`packages/native-protocol/iab/tcf-policy-checks.json`. The core meets the signal checks
for any screen: T1 (a TC String only after a save), T3, T4, T6 to T13, P13 and
P29 (it never sets the non-standard-texts flags), and P21 (a first decision
opens with every consent off). T5, CMP registration, is yours to complete with
IAB Europe. A custom screen must render the rest.

| Check | What to render |
| --- | --- |
| P1, P2 | Show the first layer over most of the screen, apart from terms and your privacy policy. |
| P3, P4, P5, P12 | `firstLayer.description`, which carries the partner count. |
| P6 | Draw `firstLayer.partnersLink` as a link that opens your partner list. |
| P7 | Every item of `firstLayer.summary`. |
| P8, P9 | `firstLayer.scope` and `firstLayer.withdraw`. |
| P10, P11, P32 | Accept all and Reject all with the same styling and at least 5:1 contrast, plus Customize. `ConsentActions` keeps their widths equal. |
| T2 | Reject all through `rejectAll()` on either scope, which turns every consent off. |
| P14, P15 | Names, descriptions and illustrations from the purpose and feature rows, unchanged, with no switch on features. |
| P16 | `adTechProviders` and `customVendors` in their own sections with their headings and notices. |
| P17, P22 | `firstLayer.legitimateInterestNotice`, `legitimateInterestExplanation` and each vendor's legitimate-interest purposes in `details`. |
| P18, P23 | `rightToObject` and the legitimate-interest switch on each purpose and each vendor. |
| P19 | Per vendor, from `details`: the privacy-policy link, both lists of purposes, special purposes, features and special features, with the consent switches. |
| P20 | A switch per row of `specialFeatures`. |
| P25 | `partnersNote` or the two partner counts on each purpose. |
| P26 | The legitimate-interest claim link in `details`. |
| P27, P28 | Retention and data categories in `details`. |
| P30 | `consentStorage`. |
| P31 | An entry in your app's settings that opens the preferences screen again. |

## Keep the screens accessible

The two blocks send each save result and error to VoiceOver, once, however many
blocks share the draft. The preferences block also routes the VoiceOver escape
gesture through `requestClose()`. The rest is one call each:

| API | What it does |
| --- | --- |
| `.consentPane(_:)` | Tells VoiceOver a new screen appeared, so focus moves into it. |
| `.consentInitialFocus()` | Puts VoiceOver focus on the heading or first control when the surface opens. |
| `ConsentActions { }` | Lays paired actions out at equal width, and stacks them when a label does not fit or at accessibility Dynamic Type sizes. |

Use text styles that scale with Dynamic Type and let rows grow. Test at the
largest accessibility size.

## Run the custom example

`packages/swift/Examples/custom-consent` is a complete custom UI built only
from the blocks. Follow its README to generate the project and run it. Its
launch arguments open any screen directly, with `--stock` for the stock
screens beside it.

The rest of this page covers the engine APIs the blocks are built on. Use them
for SDK gates outside SwiftUI and for a form that changes one category.

## Keep SDK gates current

`isAllowed(.measurement)` is a cached Boolean read. Use
`decision(for: .measurement)` when you need to distinguish `.pending` from
`.denied`. Both keep optional work off until it is permitted.

For a service that must start and stop as permission changes, retain a decision
gate for the service's lifetime. This is the registration used by the runnable
SwiftUI example:

<include src="../../shared/examples/native/core-swift/swiftui-consent/swiftui-observe.mdx" />

The example's `measurement` property is a thread-safe `MeasurementService`.
It starts collecting only on `.granted` and stops on `.pending` or `.denied`.
The gate delivers the current decision when it registers and then delivers
changes. The `ConsentSubscription` it returns owns the callback: retain it for
as long as you want updates. Calling `cancel()` or releasing the handle ends the
registration. `onChange` follows the same rule. A closure that captures its
owner should capture it weakly, as the example does, so the owner can still be
released.

Gate callbacks can run on any queue, so the service guards its own state. UI
state should come from `PublishedConsent`, or `ObservableConsent` on iOS 17
and later, which update on the main actor. The sample republishes the snapshot
with a Combine sink that needs no hop:

<include src="../../shared/examples/native/core-swift/swiftui-consent/swiftui-snapshot.mdx" />

A UIKit controller can subscribe to `decisionPublisher(for:)`, which delivers
the current decision and then each change on the main thread.

Use your vendor's supported disable, stop or reset API on withdrawal. The
sample counter is local and makes no network requests; adapt the gate to the
real SDK you use. Disable that SDK's own automatic initializer before relying
on a consent gate.

## Start a draft from recorded choices

The current permission can differ from a recorded choice under a regional
policy. Seed a form from `snapshot.explicitChoice`, then capture the snapshot
revision your form is editing:

<include src="../../shared/examples/native/core-swift/swiftui-consent/swiftui-draft.mdx" />

The sample form's Measurement switch edits `draft.measurement`. Changing the
switch changes only the draft. No native choice is recorded until Save or
Reject is pressed.

Enable editing only after the core is ready, the category is in the resolved
scope and restrictions allow it. The sample also refuses IAB editing because
a category switch cannot represent a complete vendor decision.

## Save without losing refused drafts

The runnable form commits on a worker and keeps the form open unless the
native result is `.committed`:

<include src="../../shared/examples/native/core-swift/swiftui-consent/swiftui-save.mdx" />

`expectedRevision` prevents an older draft from overwriting a newer choice or
policy. On `concurrent-change`, keep the edits visible and ask the person to
reload current settings. On a storage error, retain the draft and show Retry.
Disable duplicate saves and dismissal while a save is running.

A committed result means durable local success. Observe `eventStream` for
`.saveDelivered` or `.saveReplayed` when your app needs to report backend
delivery separately. A network failure does not reverse a stored withdrawal.

## Run the complete custom form

Open `packages/swift/Examples/swiftui-consent` using its README, add
`--headless` to the scheme's Run arguments, and launch it. This mode creates
no `ConsentPresenter` and mounts no `.inthConsent` modifier. Its
`Sources/headless-preferences.swift` contains the complete form behind the
snippets above, including readiness, restrictions, retry and reload handling.

The example project links the UI product to support its separate stock mode.
An app that ships only its own UI can remove that product and its imports.
Its engine and platform services remain the same.

## Own the complete consent flow

Your custom UI also owns policy-specific disclosures, accept and reject
actions, accessible save errors, localization and unsaved-edit confirmation.
Keep a standing Privacy settings action after the initial choice.

Verify refusal, grant, withdrawal, concurrent changes and relaunch with your
real optional SDKs. [Mobile verification](/docs/guides/mobile-verify) gives the
remaining app checks.
