Pick the Next.js rendering path that matches your router, caching strategy and
hosting. Server deployments use a
[build-time manifest](/docs/frameworks/next/optimization#bundle-the-manifest-during-builds)
by default so fresh instances resolve locally without fetching `/v1/consent/init`.

## Pick your rendering path

| Your app | Where consent resolves | Banner in server HTML | Recipe |
| --- | --- | --- | --- |
| App Router with a Next.js server (default) | Root layout starts `resolveConsent` and streams the result | Yes, in a later chunk before hydration | [Stream consent](/docs/frameworks/next/app-router#start-consent-resolution-in-the-root-layout) |
| App Router requiring banner in initial HTML | Root layout awaits `resolveConsent` inside `Suspense` | Yes, page waits for consent | [Await consent](/docs/frameworks/next/app-router#render-the-banner-in-the-server-html) |
| App Router with `cacheComponents: true` | Either layout above (never await directly in the layout) | Yes | [Cache Components](#use-cache-components) |
| Static, ISR or `'use cache'` pages | Browser (`InthProvider` without `state`) | No | [Static, ISR and cached pages](#render-static-isr-and-cached-pages) |
| Routes using `ensureStatic` | `'shell'`/`'prefetch'`: either server layout. `'navigation'`: browser layout | Matches chosen layout | [Keep pages static with `ensureStatic`](#keep-pages-static-with-ensurestatic) |
| Pages Router with `getServerSideProps` | `withConsentProps` from `@inth/nextjs/pages` | Yes | [Pages Router](/docs/frameworks/next/pages-router#resolve-consent-in-getserversideprops) |
| Pages Router without `getServerSideProps` | Browser via `_app.tsx` and consent route | No | [Pages Router](/docs/frameworks/next/pages-router#mount-one-root-for-every-page) |
| `output: 'export'` | Browser calling Inth directly | No | [Static export](/docs/frameworks/next/static-export) |
| Server app skipping server work and routes | Browser calling `/v1/consent/init` with `mode: hosted()` | No | [Client-side initialization](/docs/frameworks/next/client-side) |
| Edge runtime | Untested | Untested | [Edge runtime](#edge-runtime) |

Server resolution puts the visitor's policy in the initial response and starts
permitted scripts before hydration. Browser resolution sends identical HTML to
every visitor and resolves after hydration. Either way, optional categories
stay denied and the banner stays hidden until a policy resolves. See
[Choose your setup](/docs/concepts/choose-your-setup) for other frameworks.

## Stream or await consent in the App Router

Both App Router layouts call `resolveConsent()` from `@inth/nextjs/server`,
differing only in whether page content waits for it:

| Layout | Behavior | Tradeoff |
| --- | --- | --- |
| Streamed (default) | Page renders immediately; banner and permitted scripts follow in a later chunk before hydration. | React can throttle a separate streamed reveal by up to 300 ms after an earlier boundary. |
| Awaited inside `Suspense` | Banner arrives in the initial HTML and never shifts after hydration. | Page content waits for consent (up to `timeoutMs`, 500 ms default, on runtime fetches) and can also hit React's 300 ms reveal throttle when paired with boundaries like `@vercel/speed-insights`. |

Start with the streamed layout so a slow manifest fetch never blocks page
paint. Load Speed Insights through
[`vercelSpeedInsights`](/docs/integrations/vercel-speed-insights) instead of
`<SpeedInsights />` so it respects consent and does not add an extra `Suspense`
boundary. Without `cacheComponents`, you can also `await resolveConsent()`
directly in an async root layout, which delays the start of the response until
consent resolves.

## Start allowed scripts before hydration

When `resolveConsent()` shows that a visitor's stored choice or policy already
allows `scripts` entries (or an entry sets `alwaysLoad` and no prompt is owed),
`InthProvider` emits an inline script after page content that runs setup and
inserts those tags after first paint, before hydration. The script loader
adopts those tags so they never load twice.

All `@inth/integrations` helpers support pre-hydration start except Cloudflare
Zaraz and Sentry, which start after hydration alongside custom `scripts`.
Pages without `state` emit no inline script. The inline script uses
`options.nonce` (see
[Content Security Policy](/docs/frameworks/next/content-security-policy)). Set
`scriptLoader: { serverStart: false }` in `inth.config.ts` or on `InthProvider`
to start all scripts after hydration instead.

## Use Cache Components

With `cacheComponents: true`, Next.js prerenders a static shell and fills
request-time holes per request:

- **Streamed layout:** stays synchronous; page content stays in the static
  shell while consent resolves per request.
- **Awaited layout:** requires a `Suspense` boundary around the async consent
  component, or builds fail with `blocking-prerender-dynamic`. Never use
  `export const instant = false` to silence that error, because it disables the
  static shell for every route.

With `partialPrefetching: true`, `resolveConsent` calls `connection()` before
reading headers or the clock, so prefetches never resolve consent and
`ConsentGate` stays in the static shell without its own `Suspense` boundary.
Replace `export const revalidate` with `'use cache'` and `cacheLife`, and
resolve consent in the browser for cached pages.

A per-request CSP nonce cannot be paired with a prerendered shell (see
[Content Security Policy](/docs/frameworks/next/content-security-policy)). If
`next dev` reports an unstable `Date.now()` error, see
[troubleshooting](/docs/frameworks/next/troubleshooting#nextjs-encountered-the-unstable-value-datenow-while-prerendering).

## Render static, ISR and cached pages

Because `resolveConsent` reads cookies and headers, calling it makes routes
dynamic. For shared static, ISR (`export const revalidate`) or `'use cache'`
pages, render `InthProvider` without `state`:

Set `routePrefix: '/api/inth'` in `inth.config.ts` and mount the consent route
from the
[App Router guide](/docs/frameworks/next/app-router#initialize-in-the-browser)
so the browser resolves the bundled manifest on your server with location
headers. Without `routePrefix`, it calls `${projectUrl}/v1/consent/init`.

To mix static and dynamic routes, split them into route groups with separate
root layouts (for example `app/(site)/layout.tsx` and
`app/(static)/layout.tsx`). Navigating between root layouts does a full reload,
and choices persist in cookies and `localStorage`. To resolve the manifest in
the browser instead, use `mode: manifest({ resolve: 'browser' })` (requires
`geoUrl` for location-based policies; see
[consent modes](/docs/concepts/modes#manifest)).

## Keep pages static with `ensureStatic`

Next.js 16.4's
[`ensureStatic`](https://nextjs.org/docs/app/api-reference/file-conventions/route-segment-config/ensureStatic)
requires `cacheComponents: true` (and `partialPrefetching: true` for `'shell'`
and `'prefetch'`):

| `ensureStatic` | Streamed layout | Awaited layout | Browser layout |
| --- | --- | --- | --- |
| `'shell'` | Works | Works (links prefetch only the `Suspense` fallback) | Works |
| `'prefetch'` | Works | Works (links prefetch only the `Suspense` fallback) | Works |
| `'navigation'` | Build fails | Build fails | Works |

`'navigation'` requires the entire route including the root layout to be
static. Move those pages into a route group using the browser layout above, and
never wrap `resolveConsent` in `'use cache'`, which would leak one visitor's
consent cookies to other visitors.

## Policy source, location and project layout

- **Policy source.** Pick `manifest()` (default build snapshot),
  `manifest({ source: 'runtime' })` (cached runtime fetch), `hosted()`
  (per-request `/v1/consent/init`) or `testing()` from `@inth/nextjs/testing`
  ([testing configuration](/docs/frameworks/next/data-fetching-reference#testing-configuration)).
  See [mode combinations](/docs/frameworks/next/data-fetching-reference#mode-combinations).
- **Geography headers.** Hosts that strip geo headers before Server Components
  need `inthProxy`; see
  [Geography headers](/docs/frameworks/next/geography-headers).
- **Same-origin saves.** Enable `proxy: true` with a consent route to keep
  browser saves on your origin; see
  [Performance](/docs/frameworks/next/optimization#keep-browser-consent-requests-on-your-origin).
- **`src/` directory.** Keep `inth.config.ts` at the project root next to
  `next.config.ts`, and place `proxy.ts` under `src/`.

## Edge runtime

Inth does not test the Edge runtime. `@inth/nextjs/pages` requires Node.js
`req`/`res`, and all App Router helpers are tested on the default Node.js
runtime. Keep the default runtime on layouts, pages and consent route handlers.

## Hydration, early taps and caching rules

- **Keep state unchanged.** Pass `resolveConsent()` straight to `InthProvider`
  and keep one root mounted across navigation. If server resolution fails or
  times out, `resolveConsent` returns a baseline state so the page renders with
  optional categories denied and the browser retries after hydration (see
  [troubleshooting](/docs/frameworks/next/troubleshooting)).
- **`ConsentGate` and subject IDs.** With server state, `ConsentGate` renders
  the placeholder for denied categories and an empty wrapper for granted
  categories, mounting the iframe after hydration so streamed embeds load once
  ([ConsentGate](/docs/frameworks/next/components/consent-gate)). Subject IDs
  are read from the visitor's saved cookie; before the first save, the server
  sets no cookie.
- **Taps before hydration.** Stock `ConsentBanner` emits an inline script
  (nonced via `options.nonce`) that holds Accept, Reject, Dismiss and Customize
  taps made before hydration and blocks early press events from bubbling while
  the engine loads. Custom hook banners, pages with two stock banners, and
  composed buttons with custom `onClick`, `asChild`, `type="submit"` or
  `performDefaultAction={false}` do not buffer early taps.
- **Never cache visitor state.** Cache public manifests in your server or CDN,
  never `resolveConsent` results or HTML rendered with visitor consent.

## Verify your rendering path

1. Run `next build` and check the route table: routes under `resolveConsent` are
   dynamic (or partial with Cache Components), while browser-layout routes stay
   static.
2. View page source in a private window: awaited layouts and Pages Router
   `getServerSideProps` pages contain `data-testid="consent-banner-root"`;
   streamed and browser layouts do not.
3. Confirm in DevTools Network that no vendor request runs before consent and
   server-rendered manifest pages make no `/v1/consent/init` request.
4. Reject, reload and reopen **Privacy settings** to verify the choice holds,
   then test two regions if policies differ. See
   [Verify consent](/docs/guides/verify-consent).
