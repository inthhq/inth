## Reuse cached policy data

Use runtime manifest caching when policy edits must apply without a rebuild:

{/* example: fragment */}

```ts title="inth.config.ts"
import { defineConsentConfig, manifest } from '@inth/nextjs';

export default defineConsentConfig({ mode: manifest({ source: 'runtime' }) });
```

Keep `withConsentManifest` in `next.config.ts` so the SDK still finds
`inth.config.ts`. Each server reuses the public manifest across requests while
resolving every visitor's consent individually. Cold instances fetch
`/v1/consent/manifest` once, saves still post to Inth, and IAB policies can still fetch a
Global Vendor List. For browser initialization that needs request geography,
mount the
[consent route](/docs/frameworks/next/data-fetching-reference#do-i-need-the-consent-route).

| Fetching path | Work during initialization |
| --- | --- |
| Build-time manifest (default) | Resolves locally from the bundled snapshot, even on cold instances. |
| Warm runtime manifest cache | Reuses cached policy and resolves locally. |
| Cold runtime manifest cache | Fetches `/v1/consent/manifest` from Inth, caches it, then resolves locally. |
| Backend `/v1/consent/init` (`hosted()`) | Waits for Inth to resolve and return the visitor's policy per request. |

In our benchmarks, a warm manifest cache cut median new-visitor server response
time from 158 ms to 7 ms under 150 ms backend latency, and the streamed layout
painted in ~90 ms versus ~390 ms for an awaited layout under 4x CPU throttling.
Measure your own deployment before trading streaming for an awaited banner.

## Keep browser consent requests on your origin

By default, browsers post consent choices directly to `${projectUrl}/v1/consent/records`.
Routing those saves through your own Next.js app avoids a second DNS/TLS
connection and lets `connect-src 'self'` cover every Inth request, at the cost
of an extra server hop per save. Vendor scripts and iframes keep their own
origins.

Enable `proxy: true` and `routePrefix` in `inth.config.ts` while keeping
`projectUrl` absolute:

{/* example: fragment */}

```ts title="inth.config.ts"
import { defineConsentConfig } from '@inth/nextjs';

export default defineConsentConfig({ proxy: true, routePrefix: '/api/inth' });
```

Mount the consent route with `proxy: true`. In the App Router:

{/* example: fragment */}

```ts title="app/api/inth/[...inth]/route.ts"
import { createConsentRoute } from '@inth/nextjs/api';

export const { DELETE, GET, OPTIONS, PATCH, POST, PUT } = createConsentRoute({
	proxy: true,
});
```

In the Pages Router:

{/* example: fragment */}

```ts title="pages/api/inth/[...inth].ts"
import { createPagesConsentRoute } from '@inth/nextjs/pages';

export default createPagesConsentRoute({ proxy: true });
```

| Request | Handled by |
| --- | --- |
| `GET /api/inth/v1/consent/init` | Route handler using the bundled or cached manifest and request headers |
| `GET /api/inth/v1/consent/manifest` | Route handler serving the manifest |
| `POST /api/inth/v1/consent/records` and other consent paths | Forwarded to Inth because `proxy: true` |
| Any other path | `404` (never an open proxy) |

Keep these rules in mind:

- Set `proxy: true` in both `inth.config.ts` and the route handler, or browser
  saves hit a 404/405. Drop `proxy` from both to proxy `/v1/consent/init` only.
- `proxy: true` requires `routePrefix`; without it, `defineConsentConfig`
  throws. Server helpers keep the absolute `projectUrl` so the server never
  fetches itself.
- Pass `trustForwardedHeaders: true` on the route only when your host
  overwrites `x-forwarded-for` (such as Vercel or Cloudflare), so clients
  cannot spoof IPs.
- A [static export](/docs/frameworks/next/static-export) has no API routes; use
  a host-level proxy or the direct Inth URL instead.

## Configure manifest cache refresh

This section applies to `manifest({ source: 'runtime' })`. Build-time snapshots
stay fixed until your next build.

In the App Router, `resolveConsent` and `createConsentRoute` pass
`next: { revalidate: 300 }` so Next.js's Data Cache can share cached policy
across instances. Pass `manifestRevalidateSeconds` (`false` or `0` to disable)
to tune that TTL on route handlers. Both routers also maintain an in-process
cache that supports ETag revalidation and honors upstream `s-maxage` and
`stale-while-revalidate` (Inth sends `s-maxage=300` and 24 hours of
`stale-while-revalidate`). Visitor-specific `/v1/consent/init` calls always use
`cache: 'no-store'`.

Background refreshes and server-to-server `POST /v1/consent/sessions` reports run detached
from the response. On serverless runtimes, wire `onBackgroundRevalidate` (on
the route) and `waitUntil` (on `resolveConsent`) to `after` from `next/server`
(Next 15.1+; `unstable_after` on 15.0) or your platform's `waitUntil`:

{/* example: fragment */}

```ts title="app/api/inth/[...inth]/route.ts"
import { createConsentRoute } from '@inth/nextjs/api';
import { after } from 'next/server';

export const { GET } = createConsentRoute({
	onBackgroundRevalidate: (refresh) => after(() => refresh),
});
```

Even with build-time snapshots, `onBackgroundRevalidate` keeps the detached session report alive on serverless hosts.

## Avoid repeating startup work

Mount one `InthProvider` in the root layout (`app/layout.tsx`) or
`pages/_app.tsx` so navigation never remounts the runtime. See
[Rendering and deployment](/docs/frameworks/next/rendering) for choosing when
consent resolves.

## Know when InthProvider loads its engine

`InthProvider` keeps the consent engine out of first-load JavaScript while still
server-rendering the banner, its styles and any
[pre-hydration scripts](/docs/frameworks/next/rendering#start-allowed-scripts-before-hydration).
Your page hydrates immediately, hooks read the server state, and deferred
actions run once the engine arrives.

Taps before the engine loads still respond immediately:

- **Accept or Reject** hides the banner, applies the choice and inserts plain
  permitted `scripts` on the tap (for new visitors without GPC or notice-only
  policies). A ~9 KB compressed chunk then persists the choice, queues the save
  and fires `onChoiceRecorded` and `onPermissionsChanged` before the full
  engine loads.
- **Customize** prefetches the dialog chunk on pointer down, hides the banner
  and opens the dialog without waiting for the engine. The floating trigger
  loads separately.

| Visitor | When the engine loads |
| --- | --- |
| New visitor shown a banner with no optional categories allowed | After every `<img fetchpriority="high">` loads (or the `load` event if none), on first pointer/key/scroll interaction outside the banner, after a banner tap, or after 10 s. |
| Returning visitor who already chose and sees no banner | Same triggers as above. Plain permitted `scripts` start during hydration while the engine waits. |
| Any other visitor (IAB policy, newer browser choice or expired stored choice) | Immediately when `InthProvider`'s first-load chunk runs, before hydration. |

Deferring the engine avoids competing with your Largest Contentful Paint image
on slow connections. For returning visitors, a small inline script verifies
browser storage against server state and triggers immediate engine loading if
storage holds a newer denial, active GPC or expired record.

`InthProvider` also loads the engine immediately when:

- a permitted or `alwaysLoad` script needs the script loader (has callbacks,
  vendor/IAB fields, `persistence: false` or `options.consentSource`);
- a server-started script defines `onLoad`, `onError`, `onDispose` or
  `persistAfterDispose`;
- a denied script sets both `observeConsentBeforeLoad` and `onConsentChange`,
  or `useScriptLoader()` registers such a script;
- `InthProvider` has no `state`, `options.enabled: false`, an experiment,
  `networkBlocker`, `clearOnRevocation`, an IAB policy or an `IABProvider`.

`useNetworkBlocker()` and `useIframeBlocker()` work before the engine loads,
and `useEventDispatcher()` queues events until it arrives.

## Start returning visitors' scripts sooner

Pages without `scripts` never download the script loader chunk. When a page has
`scripts` and the engine loads immediately for a visitor whose consent already
allows a script (returning grant, opt-out policy, `alwaysLoad` or
`enabled: false`), `InthProvider` starts downloading the script loader during
its first browser render instead of waiting for hydration to finish. When the
engine is deferred for a returning visitor, `InthProvider` inserts plain
permitted scripts itself at hydration start and hands them off once the loader
arrives.

Because Next.js assigns browser chunk filenames at build time, the browser
caches the engine's `/_next/static/` chunk URLs in `localStorage` under
`inth-engine-chunks` (scoped to the current build) on its first load. On later
visits that require immediate engine loading, a small inline script preloads
those chunks while HTML is still parsing.
