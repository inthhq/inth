Hold browser `fetch` and `XMLHttpRequest` calls matching a rule until their
consent category is allowed, as a backstop alongside registered vendor
scripts.

## Add rules

Register vendor SDKs through [`scripts`](/docs/frameworks/nuxt/scripts) first
so they never run before consent. Use the network blocker for tracking calls
made by your own code or third-party modules.

Put serializable rules under `inth` in `nuxt.config.ts`:

{/* example: fragment */}

```ts title="nuxt.config.ts"
export default defineNuxtConfig({
	inth: {
		networkBlocker: {
			rules: [{ category: 'measurement', domain: 'google-analytics.com' }],
		},
	},
});
```

Put `onRequestBlocked` under `inth` in `app/app.config.ts`, because module
options serialize to JSON and drop functions. Rules defined there append to
rules from `nuxt.config.ts`:

{/* example: fragment */}

```ts title="app/app.config.ts"
export default defineAppConfig({
	inth: {
		networkBlocker: {
			onRequestBlocked: (info) => console.info('Blocked', info.url),
			rules: [],
		},
	},
});
```

## Match requests with rules

Each rule specifies a `domain` (including subdomains, so `google-analytics.com`
matches `www.google-analytics.com`) and a `category`. Narrow rules with
`pathIncludes` and `methods`, or pass category expressions such as
`{ and: ['measurement', 'marketing'] }`.

Add `vendor` with a vendor ID to block requests when a visitor switches that
vendor off. For IAB TCF vendors, use `vendorId` and `iabPurposes`.

| Option | Default | Purpose |
| --- | --- | --- |
| `rules` | Required | Array of matching rules. |
| `enabled` | `true` | Set `false` to keep rules configured without blocking. |
| `logBlockedRequests` | `true` | Logs blocked requests via `console.warn`. |
| `onRequestBlocked` | Unset | `app.config.ts` only. Receives `{ method, url, rule }` for each blocked request. |

## What a blocked request looks like

Blocked `fetch` calls resolve to a `451` response (`Request blocked by
consent`) without sending a network request. Blocked `XMLHttpRequest` calls
abort and fire an `error` event. Unmatched requests pass through unchanged.

## When blocking starts

The blocker runs in the browser only, activating when the Inth plugin runs
before hydration. Matching requests wait while consent resolves, then proceed
or get blocked once the policy and stored choice apply. When SSR resolves the
policy (default `manifest()` or `hosted()`), queued requests resolve as soon
as the app mounts.

Server-side requests such as `useFetch` during SSR are not intercepted. Check
`useConsent()` before calling vendors from server code.

## What it cannot stop

The blocker intercepts only browser `fetch` and `XMLHttpRequest` calls made
after the Inth plugin runs. It cannot stop:

- Scripts injected via `useHead` or `app.head`, or Nuxt plugins running before
  the Inth plugin.
- Code that cached a reference to `fetch` beforehand.
- `navigator.sendBeacon`, `WebSocket`, `EventSource`, `<img>`, `<script>`,
  `<iframe>`, web workers, and service workers.

## Verify

Clear site data, open the Network tab, and reload. Confirm matching requests
stay absent until you allow their category and log warnings when blocked.
Reject, reload, and confirm they stay blocked.
