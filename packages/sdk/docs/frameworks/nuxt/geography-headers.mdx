`@inth/nuxt` reads visitor geography from request headers supplied by your
host or CDN so server renders and `/api/inth/v1/consent/init` match regional policies.

## How Nuxt finds the visitor's location

The Nuxt server never runs IP geolocation itself. It reads location headers in
three places:

- During SSR, the Inth plugin reads them from the incoming page request.
- In default `manifest()` mode, `/api/inth/v1/consent/init` reads them from browser
  requests on prerendered or cached routes.
- In `hosted()` mode, the plugin forwards them to Inth's `/v1/consent/init`.

With `manifest({ resolve: 'browser' })`, no request hits your server, so pass
`geoUrl` or let the browser fall back to `/v1/consent/init` on first visit. See
[deploy to static hosting](/docs/frameworks/nuxt/rendering#deploy-to-static-hosting).

When no location header is present, your unknown-location policy rule applies.
If a country arrives without a region (such as Cloudflare without visitor
location headers enabled) and your policy has state-level rules like
California, Inth applies any matching `regionFallbacks` rule before falling
back to the unknown-location rule.

## Which headers are read?

Within each row, the first non-empty header wins:

| Input | Headers (highest precedence first) | Source |
| --- | --- | --- |
| Country | `x-inth-country`, `cf-ipcountry`, `x-vercel-ip-country`, `x-amz-cf-ipcountry`, `x-country-code`, `x-country` | Override, Cloudflare, Vercel, CloudFront, generic |
| Region | `x-inth-region`, `cf-region-code`, `x-vercel-ip-country-region`, `x-region-code` | Override, Cloudflare, Vercel, generic |
| Global Privacy Control | `x-inth-gpc`, `sec-gpc` | Override, browser signal |
| Language | `accept-language` | Browser |

Vercel sends its headers automatically. Cloudflare sends `cf-region-code` only
when its visitor location headers setting is enabled. Map CloudFront's
`CloudFront-Viewer-Country` and `CloudFront-Viewer-Country-Region` headers to
`x-inth-country` and `x-inth-region` at the edge (see
[AWS's viewer-request example](https://github.com/aws-samples/amazon-cloudfront-functions/tree/main/redirect-based-on-country)).

`/api/inth/v1/consent/init` always responds with `Cache-Control: private, no-store`.

## Trust only your own infrastructure

Because `x-inth-*` override headers take highest precedence, configure your
edge CDN or load balancer to strip incoming `x-inth-country`, `x-inth-region`,
and `x-inth-gpc` headers before setting trusted values. Also block direct
origin access so clients cannot spoof platform headers such as `cf-ipcountry`.

Stripping `x-inth-*` at the edge disables `<InthProvider country="..." />`
overrides in production, because those props send `x-inth-country` and
`x-inth-region` to `/api/inth/v1/consent/init`.

Do not strip location headers in a Nitro server middleware. During SSR, the
Inth plugin forwards location headers to `/api/inth/v1/consent/init` internally, and
Nitro middleware runs on that internal request too.

## Test another region

Use these methods during development only:

- Pass `<InthProvider country="DE" />` (and optionally `region`), when the edge
  does not strip `x-inth-*`.
- Query `curl -H 'x-inth-country: DE' http://localhost:3000/api/inth/v1/consent/init`.
- Test a deployed environment through a VPN or your host's geo testing tools.

## Verify

Load your deployed site from two regions with different policies (for example
via VPN) and inspect the HTML source: an opt-in region includes
`data-testid="consent-banner-root"`, while a no-prompt region does not. Run
`curl -H 'x-inth-country: US' https://<your-domain>/api/inth/v1/consent/init` and confirm
production ignores the spoofed header.
