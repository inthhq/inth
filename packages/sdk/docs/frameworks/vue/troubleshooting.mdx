Diagnose and fix Vue-specific setup, bundling, theming, and runtime errors
with `@inth/vue`.

## Vite fails to pre-bundle `.vue` files or throws "has no backend URL"

**Check.** `vite dev` fails during dependency optimization on a `.vue` file
inside `@inth/vue`, or `hosted()` throws `inth: hosted() has no backend URL`.
`consentManifest()` is missing from `vite.config.ts`.

**Fix.** Add `consentManifest()` from `@inth/vue/vite` next to `vue()` in
`vite.config.ts`, and set `VITE_INTH_PROJECT_URL` (falling back to
`VITE_C15T_BACKEND_URL` if unset).
See [add the Vite plugin](/docs/frameworks/vue/quickstart#add-the-vite-plugin).

## app.use() throws "pass `mode`"

**Check.** `inth` options omit `mode`.

**Fix.** Pass `mode: hosted()`, `manifest()`, or `testing()` from
`@inth/vue/vue-plugin` (or `@inth/vue/testing`). Pass `projectUrl` to the mode
factory if you do not use `consentManifest()`.

## A composable throws "Kernel not found"

**Check.** The component renders outside the `createApp()` instance that
installed `inth`, or the composable ran outside `setup`.

**Fix.** Install `inth` on the same app instance and call composables
inside `setup`.

## Why is there no banner?

**Check.** Open [DevTools](/docs/frameworks/vue/components/dev-tools) to
inspect the matched policy, and check `/v1/consent/init` (`hosted()`) or `/v1/consent/manifest`
(`manifest({ source: 'runtime' })`) in the Network tab.

**Fix.** Check these causes in order:

1. **The matched policy requires no banner.** Policies with `prompt: 'none'`
   (common in opt-out regions) show no banner. See
   [why the banner may be absent](/docs/concepts/policies#why-the-banner-may-be-absent).
2. **`manifest()` resolved the unknown-location rule.** With
   `initFallback: false` and no `inputs` or `geoUrl`, every visitor gets your
   unknown-location policy. Switch to `hosted()` or configure location inputs.
3. **`InthProvider` unmounts on navigation.** Move `<InthProvider />` to
   `src/App.vue`.
4. **The policy request failed.** Confirm `/v1/consent/init` or `/v1/consent/manifest` returns 200.
   A CORS error means your site's origin is missing from your Inth project's
   trusted origins. While resolution fails, Inth hides the UI and denies
   optional categories.
5. **A choice is already stored.** Clear the `inth` cookie and localStorage
   key, or test in a private window.

## The app throws IABUnavailableError

**Check.** The console shows `INTH_IAB_UNAVAILABLE` ("inth: this visitor's
policy uses IAB TCF, but `iab` is not set."). The matched policy uses the
`iab` model with a vendor list, but `iab` is unset, `false`, or
`{ enabled: false }`.

**Fix.** Pass `iab: {}` to `inth` (`app.use(inth, { iab: {} })`) if
your site uses IAB TCF. See [IAB TCF](/docs/frameworks/vue/iab). Otherwise,
remove the `iab` model from that regional policy in Inth.

## Tokens in my CSS do not apply

**Check.** `inth` appends `<style id="inth-css-vars">` to `<head>` with
every token, including defaults. A `:root` rule in your stylesheet can lose on
cascade order.

**Fix.** Pass custom values through `inth`'s `tokens` option instead. See
[set theme tokens](/docs/frameworks/vue/customize#set-theme-tokens).

## A script loads twice, or before consent

**Check.** Look for duplicate vendor registration in both `inth`'s
`scripts` and a manual `createScriptLoader()` call, or a leftover `<script>`
tag in `index.html`.

**Fix.** Remove manual loaders and keep only `scripts` on `inth`.

## The page flashes without the banner on a server-rendered Vue app

**Check.** Plain `@inth/vue` resolves consent in the browser only and renders
the banner after hydration.

**Fix.** Use `@inth/nuxt` for server-rendered banners, or inline theme tokens
as shown in
[server rendering without Nuxt](/docs/frameworks/vue/rendering#server-rendering-without-nuxt).

## Renamed exports fail to resolve

**Check.** Imports such as `@inth/vue/consent-root`, `ConsentPreferencesLink`,
`ConsentFrame`, or the default export of `@inth/vue/vite` fail to resolve.

**Fix.** Update to the current names:

| Old name | Current name |
| --- | --- |
| Plugin options `projectUrl`, `manifest`, `manifestSnapshot`, `manifestUrl`, `customFetch`, `domain` | `mode` factory from `@inth/vue/vue-plugin` |
| Default `inth` export of `@inth/vue/vite` | `consentManifest` from `@inth/vue/vite` (`inth` remains the Vue plugin export) |
| `@inth/vue/consent-root`, `@inth/vue/consent-widget` | Named exports from `@inth/vue/vue-plugin` |
| `ConsentPreferencesLink`, `runtime/components/consent-preferences-link.vue` | `ConsentDialogLink`, `consent-dialog-link.vue` |
| `ConsentFrame` | `ConsentGate` |
| `hosted({ url })` | `hosted({ projectUrl })`, or `VITE_INTH_PROJECT_URL` |

For shared package and API renames, see [migrate from c15t](/docs/migrate-from-c15t).

## The banner or dialog fails to load

**Check.** Open the console. A warning or error from Inth that says the banner, the dialog or the engine failed to load means the browser could not download one of Inth's chunks, for example during a dropped connection or a deploy that removed old files.

After a failure the page stays as it is: Inth never reloads it, because a reload would discard what the visitor typed into your page. Nothing is recorded, and the banner stays or shows again. The next tap, open or snapshot tries the download again. Your bundler loads chunks with native `import()`. Firefox 155 or later, Chrome 156 or later, and Safari send a new request for a chunk that failed. Earlier Chromium and Firefox keep the failure for the life of the page; there Inth loads the chunk again from its URL with `inth-retry=<n>` added, which works unless another chunk imports it by its plain URL. A chunk whose own dependency failed stays failed in every browser.

**Fix.** Nothing on the page. The next page load downloads the chunk again. If the failures follow a deploy, keep the previous build's chunk files available until cached pages that link to them expire. See [a consent chunk fails to load](/docs/guides/troubleshooting#a-consent-chunk-fails-to-load) for which browsers and builds can retry on the same page.
