Hold `fetch` and `XMLHttpRequest` requests matching a rule until their consent
category is allowed, as a backstop alongside registered vendor scripts.

## Add rules

Register vendor SDKs through [`scripts`](/docs/frameworks/vue/scripts) first
so they never execute before consent. Use the network blocker to catch
tracking calls from your own code or third-party modules.

Define rules in a dedicated file:

<include src="../../shared/examples/vue/network-blocker.mdx" />

Pass `networkBlocker` to `inth` in `src/main.ts`:

{/* example: fragment */}

```ts title="src/main.ts"
app.use(inth, { mode: hosted(), networkBlocker, scripts });
```

## Match requests with rules

Each rule specifies a `domain` (including subdomains, so `google-analytics.com`
matches `www.google-analytics.com`) and a `category`. Narrow rules with
`pathIncludes` and `methods`, or pass category expressions such as
`{ and: ['measurement', 'marketing'] }`.

Add `vendor` with a vendor ID to block requests when a visitor turns that
vendor off. For IAB TCF vendors, use `vendorId` and `iabPurposes`.

| Option | Default | Purpose |
| --- | --- | --- |
| `rules` | Required | Array of matching rules. |
| `enabled` | `true` | Set `false` to keep rules configured without blocking. |
| `logBlockedRequests` | `true` | Logs blocked requests via `console.warn`. |
| `onRequestBlocked` | Unset | Callback receiving `{ method, url, rule }` for each blocked request. |

## What a blocked request looks like

Blocked `fetch` calls resolve with a `451` response (`Request blocked by
consent`) without sending a network request. Blocked `XMLHttpRequest` calls
abort and emit an `error` event. Unmatched requests pass through unchanged.

## When blocking starts

`app.use(inth, ...)` activates the blocker before the app mounts. While
consent is still resolving, matching requests wait rather than failing. Once
the policy and stored choice load, queued requests either proceed or get
blocked. If policy loading fails, optional categories stay denied and queued
requests are blocked.

## What it cannot stop

The blocker only intercepts `fetch` and `XMLHttpRequest` calls made after
`app.use()` runs. It cannot block:

- Scripts in `index.html` or modules executing before `src/main.ts`.
- Code that cached a reference to `fetch` before the plugin installed.
- `navigator.sendBeacon`, `WebSocket`, `EventSource`, `<img>`, `<script>`,
  `<iframe>`, web workers, and service workers.

Check `useConsent()` before calling vendor APIs in your own code and use the
network blocker as a safety net.

## Verify

Clear site data, open the Network tab, and reload. Confirm matching requests
stay absent until you allow their category and appear as console warnings when
blocked. Reject, reload, and confirm they remain blocked.
