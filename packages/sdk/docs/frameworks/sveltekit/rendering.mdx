## Pick a rendering path

`inthHandle()` in `src/hooks.server.ts` holds the config for the whole app.
Its `mode` option decides where each visitor's policy comes from. Import the
modes from `@inth/svelte/kit`: they are plain data, which `loadConsent`
sends to the browser.

| Your app | Where consent resolves | `inthHandle()` options |
| --- | --- | --- |
| Server-rendered pages, recommended | Root layout load, from a build-time manifest | None. See the [quickstart](/docs/frameworks/sveltekit/quickstart). |
| Policy changes must apply without a rebuild | Root layout load, from a manifest fetched at runtime | `mode: manifest({ source: 'runtime' })`. See [fetch the manifest at runtime](#fetch-the-manifest-at-runtime). |
| Backend resolves every visit | Root layout load calls the backend's `/v1/consent/init` | `mode: hosted()`. See [ask the backend on every request](#ask-the-backend-on-every-request). |
| A server app with some prerendered pages | Server for most pages, the browser on prerendered ones | `routePrefix: '/api/inth'` and a consent route. See [prerender some pages](#prerender-some-pages). |
| A fully static site with `adapter-static` | The browser | `mode: hosted()`. See [build a static site](#build-a-static-site). |
| SPA mode, `ssr = false` | The browser | See [use SPA mode](#use-spa-mode). |

Every path uses the same root layout: `loadConsent` as the server load and
`InthProvider` with `state={data.consent}`. The quickstart matches the
SvelteKit [example app](/docs/examples).
[Data fetching](/docs/concepts/data-fetching) compares `/v1/consent/init`, the manifest
and browser resolution in general.

## Fetch the manifest at runtime

Use runtime manifest fetching when policy updates must apply without a
rebuild. Your server downloads the project's public policy manifest, caches
it, and resolves each visitor locally. Consent saves still go to the backend,
directly or through the
[consent proxy](#save-consent-through-your-own-origin).

{/* example: fragment */}

```ts title="src/hooks.server.ts"
import { inthHandle, manifest } from '@inth/svelte/kit';

export const handle = inthHandle({ mode: manifest({ source: 'runtime' }) });
```

Keep `consentManifest` in `vite.config.ts`: it supplies the project URL. Set
`consentManifest({ source: 'runtime' })` so a build skips the manifest
download, or pass `inthHandle({ projectUrl })`. `loadConsent` fetches
`${projectUrl}/v1/consent/manifest`, or the URL in `manifest({ manifestUrl })`.

The server caches the manifest in memory for as long as its `s-maxage`
allows. After that, within the backend's `stale-while-revalidate` window, it
serves the stale copy while it refreshes in the background. Past that window,
the next request waits for a fresh copy, up to the 500 ms budget of
`loadConsent`. It also reports each resolved visit to the backend so Inth
still counts visitors it never served `/v1/consent/init` to.

Pass the absolute Inth URL as `projectUrl`. A relative URL, such as
`/api/consent-proxy` for a proxy route mounted in your app, is fetched with
`event.fetch` inside the app and is never resolved against the request's
`Host` header. One that points back at the consent route makes the route
fetch itself.

## Ask the backend on every request

`mode: hosted()` sends every server render to the backend's `/v1/consent/init`, which
resolves the visitor's location itself. The browser asks the same `/v1/consent/init` on
pages the server did not resolve:

{/* example: fragment */}

```ts title="src/hooks.server.ts"
import { inthHandle, hosted } from '@inth/svelte/kit';

export const handle = inthHandle({ mode: hosted() });
```

`hosted()` reads the project URL from `consentManifest`, or from the hook's
`projectUrl` option. The request to `/v1/consent/init` carries the resolved
location, language and GPC, the `user-agent` and, over `https` or to a
loopback host, the consent cookie alone. Every render waits on the backend,
up to 500 ms. `consentManifest` still downloads the manifest during the
build (warning by default on failure); pass `source: 'runtime'` to skip the
download.

## Serve the consent route

A page the server resolved needs no route. The browser needs one only when it
resolves consent itself, such as on a prerendered page, and you want it to
ask your own origin instead of the backend. Add a catch-all route at
`src/routes/api/inth/[...path]/+server.ts`:

<include src="../../shared/examples/sveltekit/route-handlers.mdx" />

Tell the handle where it is, so `loadConsent` passes the prefix to the
browser:

{/* example: fragment */}

```ts title="src/hooks.server.ts"
import { inthHandle } from '@inth/svelte/kit';

export const handle = inthHandle({ routePrefix: '/api/inth' });
```

`createConsentRoute()` returns `GET`, which serves two paths:

| Request | Response |
| --- | --- |
| `GET /api/inth/v1/consent/init` | The visitor's resolved policy, like the backend's `/v1/consent/init`. `Cache-Control: private, no-store`. |
| `GET /api/inth/v1/consent/manifest` | The manifest, with the backend's `Cache-Control` and `ETag`. Answers `If-None-Match` with `304`. |

The route resolves from the snapshot `consentManifest` downloaded and reads
the project URL from it, so it needs no options. It also reads what you pass
to `inthHandle()`: a `snapshot`, a `projectUrl`, and the mode's own
`projectUrl` or `manifestUrl`. Set them once, on the handle. Options you pass
to `createConsentRoute()` win.

This route file exports `GET` only, so a `POST` or `PATCH` to `/api/inth`
gets a `405`. Consent saves go to the project URL directly, unless you turn
on the proxy described in
[save consent through your own origin](#save-consent-through-your-own-origin).

### Save consent through your own origin

To keep every consent request on your site's origin, pass `proxy: true` and
export the write handlers from the same catch-all route:

{/* example: fragment */}

```ts title="src/routes/api/inth/[...path]/+server.ts"
import { createConsentRoute } from '@inth/svelte/kit';

export const { GET, POST, PATCH, PUT, DELETE, OPTIONS } = createConsentRoute({
	proxy: true,
});
```

Then point saves at the route:

{/* example: fragment */}

```ts title="src/hooks.server.ts"
import { inthHandle } from '@inth/svelte/kit';

export const handle = inthHandle({
	projectUrl: '/api/inth',
	routePrefix: '/api/inth',
});
```

The route skips a handle `projectUrl` that points at itself, and forwards to
the project URL `consentManifest` read from `PUBLIC_INTH_PROJECT_URL` (falling
back to `PUBLIC_C15T_BACKEND_URL` if unset). To
forward somewhere else, pass `createConsentRoute({ projectUrl, proxy: true })`.
With the proxy on, `GET`
still resolves `init` and `manifest` in the process, and the handlers forward
other requests to `projectUrl`. They forward only
`subjects`, `subjects/:id`, `init`, `manifest`, `health`, `status` and any
extra paths you list in `proxy: { paths }`, and answer anything else with
`404`. Cookies go upstream only when `proxy: { cookieNames }` names them. The visitor's address comes from
`event.getClientAddress()`, and `x-forwarded-host` and `x-forwarded-proto`
come from `event.url`, so configure your adapter's address header if it runs
behind a proxy. The proxy forwards to `projectUrl`, never to a `manifestUrl`.
An absolute URL is fetched over the network. A relative one, such as a route
elsewhere in your app, is fetched with `event.fetch` inside the app and is
never resolved against the request's `Host` header.

### Keep background work alive after the response

The route and `loadConsent` use only `fetch`, so they run on Node and edge
adapters alike. Some runtimes stop work once a response is sent, which would
cut off the background manifest refresh and the visit report. When the
adapter exposes `event.platform.context.waitUntil`, Inth registers that work
there automatically. Netlify does, as do Cloudflare and Vercel edge on
SvelteKit 2.

SvelteKit 3's Cloudflare adapter no longer puts `waitUntil` on
`event.platform`, and its Vercel adapter has no edge runtime. On those, pass
the platform's own `waitUntil` as `onBackgroundRevalidate`:

{/* example: fragment */}

```ts title="src/routes/api/inth/[...path]/+server.ts (partial)"
import { createConsentRoute } from '@inth/svelte/kit';
import { waitUntil } from 'cloudflare:workers'; // Vercel: '@vercel/functions'

export const { GET } = createConsentRoute({
	onBackgroundRevalidate: (promise) => waitUntil(promise),
});
```

Without it, those runtimes can cut the refresh and the visit report short.
Requests keep getting the cached manifest, but it can stay stale for longer,
and the backend misses those visits.

`loadConsent` takes the same option when you call it from your own `load`
instead of exporting it directly:

{/* example: fragment */}

```ts title="src/routes/+layout.server.ts"
import { loadConsent } from '@inth/svelte/kit';
import { waitUntil } from 'cloudflare:workers';

export const load = (event) =>
	loadConsent(event, {
		onBackgroundRevalidate: (promise) => waitUntil(promise),
	});
```

`loadConsent` uses `event.platform.context.waitUntil` when available and
this callback otherwise. The framework-free `resolveConsent` helper also
accepts `onBackgroundRevalidate`; it has no event from which to find a
platform hook.

## Resolve request context once with inthHandle

The quickstart installs `inthHandle` in `src/hooks.server.ts`. It holds the
consent config for the app and reads the consent cookie and headers once per
request for every load and endpoint:

<include src="../../shared/examples/sveltekit/hooks.mdx" />

It stores the result on `event.locals.inth`, which `loadConsent` reuses, and
rewrites the location headers into one normalized form. Compose it with your
own handles through `sequence(inthHandle(), yourHandle)` from
`@sveltejs/kit/hooks`.

| Option | Default | What it does |
| --- | --- | --- |
| `mode` | `manifest()` | How `loadConsent` resolves the visitor: `manifest()`, `hosted()` or `testing()` from `@inth/svelte/kit`. |
| `routePrefix` | none | Where [`createConsentRoute()`](#serve-the-consent-route) is mounted, such as `/api/inth`. Without it, the browser asks the backend's `/v1/consent/init` when it resolves consent itself. |
| `projectUrl` | The URL `consentManifest` read from `PUBLIC_INTH_PROJECT_URL` (falling back to `PUBLIC_C15T_BACKEND_URL`) | Your Inth project URL. |
| `snapshot` | The manifest `consentManifest` downloaded | A manifest of your own to resolve with. |
| `cookieName` | `inth` | The consent cookie. Match the provider's `storageConfig.storageKey`. |
| `country`, `region`, `language` | from headers | Forces one input for every request. |

`inthHandle` sets no cookie. The visitor's subject ID (`sub_…`) lives in
the consent records their first save writes, and `loadConsent` reads it from
those cookies.

Server-rendered pages that call `loadConsent` hold the visitor's consent, so
keep them out of shared caches. Prerendered pages hold none:
`loadConsent` returns no visitor state while SvelteKit prerenders.

`inthHandle` also writes a server-rendered banner's rules into the HTML
`<head>` as `<style>` elements, so the banner is styled before hydration. A
first visit's page holds only the banner's rules and the theme tokens, not the
trigger's, `ConsentGate`'s or the dialog's. The
browser's JavaScript does not carry those rules again: the components find
them in the page. Without the handle, the components load the rules in the
browser and stay hidden until they arrive, unless `InthProvider` sets
`styles={false}` and the app imports `@inth/svelte/styles.css`.

When the visitor's consent already allows some `scripts` entries, through a
stored choice or a policy that asks for none, `inthHandle` adds an inline script
at the end of `<body>`. After first paint, it runs those entries' setup and
inserts their tags, so they start loading before the page hydrates. Entries with
`alwaysLoad` start this way whatever the visitor chose. The script loader adopts
those tags instead of inserting its own. Nothing starts from the HTML while the
policy asks the visitor to choose, not even `alwaysLoad` entries, and a
prerendered page starts nothing.

The vendor helpers from `@inth/integrations` start this way, except Cloudflare
Zaraz and Sentry. Those two helpers, and `scripts` entries you write yourself,
start after hydration. An `InthProvider` given a `runtime` starts nothing
from the HTML: its scripts start after hydration.

To start every `scripts` entry after hydration instead, pass
`scriptLoader={{ serverStart: false }}` to `InthProvider`.

Type `event.locals.inth` in `src/app.d.ts`:

<include src="../../shared/examples/sveltekit/app-locals.mdx" />

Options passed to one `loadConsent` call, such as `country`, override the
handle's values for that call. Without the handle, `loadConsent` resolves
with `manifest()` and reads the request itself.

## Cache policy, never visitor state

A manifest is public policy configuration, so your server and CDN can cache it.
A resolved state, a stored record and HTML rendered with them belong to one
visitor. Keep them out of shared caches: don't send a public `Cache-Control`
with `setHeaders` on a server-rendered page under `loadConsent`, and don't
store `loadConsent` results under a shared key. That HTML also starts the
scripts the visitor's consent allows, so a cached copy would start them for
the next visitor. A prerendered page holds no visitor state, so it can be
cached.

## Prerender some pages

A prerendered page is built once and sent to every visitor, so it cannot
contain one visitor's consent. SvelteKit runs the root layout load while it
builds those pages. `loadConsent` and `inthHandle` read SvelteKit's
`building` flag, so they return no visitor's consent and no policy then, and
make no backend request. Prerendering a page needs only the page option:

<include src="../../shared/examples/sveltekit/prerender.mdx" />

On a prerendered page the HTML has no banner. After hydration the browser
resolves the policy, then shows the banner or applies the stored choice.
Optional categories stay denied until then. Server-rendered pages in the same
app keep the banner in their HTML.

Where the browser asks depends on the handle:

- With [`routePrefix` and the consent route](#serve-the-consent-route), it
  asks your own `/api/inth/v1/consent/init`, which resolves from the bundled snapshot.
- Without them, it asks the backend's `/v1/consent/init`.

## Build a static site

With `adapter-static`, every page is prerendered and no server runs after the
build. Set the option in the root layout:

{/* example: fragment */}

```ts title="src/routes/+layout.ts"
export const prerender = true;
```

The browser resolves consent on every page. Server routes such as
`/api/inth` do not exist after a static build, so it has to ask the backend
directly. Starting from the quickstart, set `hosted()` as the mode and keep
the rest:

{/* example: fragment */}

```ts title="src/hooks.server.ts"
import { inthHandle, hosted } from '@inth/svelte/kit';

export const handle = inthHandle({ mode: hosted() });
```

The hook and `loadConsent` still run while SvelteKit prerenders, and return
no visitor's consent. The browser then calls the backend's `/v1/consent/init`, and the
backend resolves the visitor's location. Leave out `routePrefix` and the
consent route. On a static host, the project URL must be the absolute Inth
URL, and the backend must allow your site's origin.

## Use SPA mode

With `export const ssr = false` in the root `+layout.ts` and a server
adapter, the quickstart works unchanged. The root layout's server load still
runs for each navigation, so `InthProvider` starts from a resolved policy.
There is no server HTML to start from, so `InthProvider` renders its children
once the consent engine has loaded, and the banner appears with them.

With a static SPA fallback page and no server, no server load runs. Delete
`+layout.server.ts` and `inthHandle`, and render `InthProvider` with a
browser mode in `+layout.svelte`:

{/* example: fragment */}

```svelte title="src/routes/+layout.svelte (partial)"
<script lang="ts">
	import { InthProvider, hosted } from '@inth/svelte';
	import { PUBLIC_INTH_PROJECT_URL } from '$env/static/public';
</script>

<InthProvider projectUrl={PUBLIC_INTH_PROJECT_URL} mode={hosted()} {scripts}>
```

The browser resolves consent through the backend's `/v1/consent/init`.
`@inth/svelte`'s `InthProvider` takes the same props as `@inth/svelte/kit`'s
`InthProvider`, with `mode` in place of `state`.

## Taps before hydration

A banner in the server HTML shows before the page's JavaScript runs. The
banner puts a small inline `<script>` ahead of its markup that holds a tap on
Accept all, Reject all, Customize or the notice's acknowledge button in that
gap. Accept and Reject hide the banner at once. When the banner hydrates, it
records the held choice at the time of the tap, through the same path as a tap
after hydration: before the consent engine loads, the allowed `scripts` start
and the record is stored at once. A held Customize opens the dialog. If the
policy that resolves is not the one the banner showed, the tap is dropped and
the banner shows again. The React and Vue banners do the same.

The script needs no configuration; see the
[Content Security Policy guide](./content-security-policy#allow-the-banners-tap-script)
for a nonce-based policy.

## When the consent engine loads

For a visitor the server render asks to choose, the browser's first load
holds no consent engine. The server render of `InthProvider` leaves the consent
state it rendered with in the HTML, after the page's content. The browser
hydrates from it, so `getConsentKernel()`, `getSnapshot()` and the other
getters return it at once. The engine loads at the first of these:

- every `<img fetchpriority="high">` on the page has loaded or failed (the
  window `load` event when there is none)
- the first pointer press, key press or scroll outside the banner
- page code calls something only the engine answers, such as
  `kernel.set.overrides()` or `clearRecords()`
- 10 seconds after hydration

The page then preloads neither the engine nor the script loader. An Accept all
or Reject all tapped before the engine loads takes effect in the tap's own
task: the consent state the getters return changes, and the `scripts` entries
the choice allows start, if they are a plain `src` with element attributes. A
moment later Inth stores the consent record, queues the save and calls
`onChoiceRecorded` and `onPermissionsChanged`. The engine then loads, starts
from that record and sends the save. It records nothing a second time.
Customize opens the dialog without the engine, and a save from the dialog
takes the same path. Once the engine has loaded, the code that stores and
sends a choice loads in idle time, so a later tap downloads only the scripts
it allows.

The browser loads the engine as the page starts, and the server render
preloads it, for everyone else: a returning visitor, a policy with a notice
prompt or a privacy signal, IAB, an experiment, a `consentSource`, `gpp`, a
`networkBlocker`, `enabled: false`, `persistence: false`, or a `scripts` entry
that may run now and does not start from the HTML. Prerendered pages load it
as the page starts too, since their HTML is no one visitor's.

`@inth/svelte`'s `InthProvider` loads its engine with the page, as before. Use
`InthProvider` from `@inth/svelte/kit` in a SvelteKit root layout to get the
deferred start.

## Resolve consent in other server code

`resolveRequestConsent` from `@inth/sdk/server` resolves consent without a
SvelteKit event, for endpoints or code outside a load:

{/* example: fragment */}

```ts
import { resolveRequestConsent } from '@inth/sdk/server';

const state = await resolveRequestConsent({
	projectUrl: 'https://your-project.inth.app',
	request: { headers: request.headers },
});
```

It never throws. When the backend fails or takes longer than `timeoutMs`,
500 ms by default, it returns the stored choice without a policy. Pass
`snapshot` to resolve from a manifest you hold instead of calling
`/v1/consent/init`. In a load, use `loadConsent`, which reads the request and
the handle's config from the event. Import `@inth/svelte/kit` and
`@inth/sdk/server` only from server files such as `+layout.server.ts`,
`+server.ts` and `hooks.server.ts`; imported into a component they add server
code to the browser bundle.
