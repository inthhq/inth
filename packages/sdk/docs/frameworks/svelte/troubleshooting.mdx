## The build or dev server fails fetching the manifest

**Check.** `vite build` and `vite dev` download the policy through the `consentManifest` plugin in `vite.config.ts`. By default (`onBuildError: 'runtime'`), both log a warning starting with `@inth/svelte/vite: could not fetch the consent manifest` and continue with runtime fetching; with `onBuildError: 'fail'` or `INTH_ON_BUILD_ERROR=fail`, the command stops with an error. The text in parentheses names the cause:

| Error | Cause |
| --- | --- |
| `/v1/consent/manifest responded 404` | The project URL is wrong or still points to a placeholder. |
| `no backend URL is set` | Neither the `projectUrl` option nor `VITE_INTH_PROJECT_URL` (falling back to `VITE_C15T_BACKEND_URL`) is set, or it is empty. Warns by default; stops when `onBuildError: 'fail'`. |
| `skipped the consent manifest fetch` (a notice) | The project URL is relative. With `onBuildError: 'fail'`, this throws `build-time manifests require an absolute upstream URL`. |
| `/v1/consent/manifest returned an invalid consent manifest.` | The URL responds, but not with an Inth manifest. |
| `fetch failed` or `no response within 10 seconds` | The machine running the command cannot reach Inth. |

**Fix.** Set `VITE_INTH_PROJECT_URL` (falling back to `VITE_C15T_BACKEND_URL` if unset) to your project's absolute URL in `.env` or your CI environment, and make sure that machine can reach Inth. To deploy during an outage when `onBuildError: 'fail'` is set, build with `INTH_ON_BUILD_ERROR=runtime`.

## The browser fetches the manifest at runtime

**Check.** With `manifest()`, the browser requests `<projectUrl>/v1/consent/manifest` on page load instead of resolving from a bundled policy. The build had no policy to bundle: `consentManifest` is missing from `plugins` in `vite.config.ts`, the fetch failed under the default `'runtime'` mode (or `INTH_ON_BUILD_ERROR=runtime`), or the project URL is relative. Without the plugin and without `projectUrl`, `manifest()` throws when it runs.

**Fix.** Add `consentManifest()` or fix the error from [the fetch errors above](#the-build-or-dev-server-fails-fetching-the-manifest), then restart `vite dev` or rebuild. A build fetches once, and `vite dev` fetches the first time the app loads the policy.

## Consent requests go to the wrong backend

**Check.** Inspect `VITE_INTH_PROJECT_URL` and `VITE_C15T_BACKEND_URL` in `.env`, `.env.local`, and the build environment, plus any `projectUrl` in `vite.config.ts` or `src/App.svelte`. `VITE_INTH_PROJECT_URL` wins if both are set; `VITE_C15T_BACKEND_URL` is read as a fallback when `VITE_INTH_PROJECT_URL` is unset. Vite inlines these variables at build time, so changing them has no effect until you rebuild.

**Fix.** Set `VITE_INTH_PROJECT_URL` to your Inth project URL, including any path prefix, remove any stale `VITE_C15T_BACKEND_URL`, and rebuild. Confirm your app's origin is listed in your Inth project's trusted origins.

## The banner appears after the page

**Check.** In a Svelte app without a server, the browser resolves the policy after the page loads, then shows the banner. This is expected; optional categories stay denied until the policy resolves.

**Fix.** For a banner in the first HTML, render the page on a server with SvelteKit. See [choose your setup](/docs/concepts/choose-your-setup).

## Names from an earlier alpha are missing

**Check.** An import from an earlier v3 alpha fails, such as `ConsentManagerProvider`, `Frame`, or `consentManifest({ outputFile })`. `@inth/svelte` was not public in v2, so those alpha names have no alias.

**Fix.** Use the current names:

| Removed | Use instead |
| --- | --- |
| `ConsentManagerProvider` | `InthProvider` |
| `Frame` | `ConsentGate` |
| `hosted({ url })` | `hosted()` with `VITE_INTH_PROJECT_URL` (or `VITE_C15T_BACKEND_URL`), or the provider's `projectUrl` prop |
| `ConsentManifestOptions`, `consentManifest({ outputFile })` | Removed. `consentManifest()` serves the snapshot as `@inth/svelte/generated`. |

## The banner or dialog fails to load

**Check.** Open the console. A warning or error from Inth that says the banner, the dialog or the engine failed to load means the browser could not download one of Inth's chunks, for example during a dropped connection or a deploy that removed old files.

After a failure the page stays as it is: Inth never reloads it, because a reload would discard what the visitor typed into your page. Nothing is recorded, and the banner stays or shows again. The next tap, open or snapshot tries the download again. Your bundler loads chunks with native `import()`. Firefox 155 or later, Chrome 156 or later, and Safari send a new request for a chunk that failed. Earlier Chromium and Firefox keep the failure for the life of the page; there Inth loads the chunk again from its URL with `inth-retry=<n>` added, which works unless another chunk imports it by its plain URL. A chunk whose own dependency failed stays failed in every browser.

**Fix.** Nothing on the page. The next page load downloads the chunk again. If the failures follow a deploy, keep the previous build's chunk files available until cached pages that link to them expire. See [a consent chunk fails to load](/docs/guides/troubleshooting#a-consent-chunk-fails-to-load) for which browsers and builds can retry on the same page.
