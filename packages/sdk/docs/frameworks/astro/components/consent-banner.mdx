## Add the banner to your layout

Render one `ConsentBanner` in the layout that wraps every page, after your page
content:

<include src="../../../shared/examples/astro/layout.mdx" />

`ConsentBanner` renders the consent prompt on the server from
`Astro.locals.inth`, collapsed, in its Card, Banner or Drawer. It ships no
framework JavaScript. Once the consent engine runs, a small chunk takes the
prompt over: Customize opening the choices in place, the phone layout,
blocking, and the commit.

## When the banner renders

The server renders the banner markup only when the resolved policy asks for a
banner and this visitor has not answered yet:

- A returning visitor who has chosen gets no banner markup at all.
- A rule with `prompt: 'none'` renders no banner.
- With no resolved policy, because the backend failed, timed out or matched no
  rule, the server renders a hidden placeholder. The browser renders the banner
  into it if its own `/v1/consent/init` request resolves a policy.

On a prerendered page, the same HTML serves every visitor, so the banner ships
hidden. A small inline script right after it shows the banner at first paint
when the visitor has no stored consent. For a visitor with a stored choice,
the consent runtime decides once it has read the cookie. In `hosted()` and
`manifest()` modes, the build cannot know the policy, so the page carries the
placeholder and the browser renders the banner after `/v1/consent/init`. See
[Rendering and deployment](/docs/frameworks/astro/rendering).

After a choice, the prompt leaves, the outcome is announced to screen
readers, and focus moves to your "Your Privacy Choices" link. After a
`ClientRouter` navigation, the prompt moves to the new page's markup and shows
or hides to match the visitor's state.

## Props

| Prop | Type | Default | Effect |
| --- | --- | --- | --- |
| `title` | `string` | `cookieBanner.title`, or `cookieBanner.noticeTitle` under a notice | Banner heading |
| `description` | `string` | `cookieBanner.description`, or `cookieBanner.noticeDescription` under a notice | Banner body text |
| `acceptButtonText` | `string` | `common.acceptAll` | Accept button label |
| `rejectButtonText` | `string` | `common.rejectAll` | Reject button label |
| `customizeButtonText` | `string` | `common.customize` | Customize button label |
| `dismissButtonText` | `string` | `common.acknowledge` | Label of the button that acknowledges a notice |
| `legalLinks` | `('privacyPolicy' \| 'cookiePolicy' \| 'termsOfService')[] \| null` | `['privacyPolicy', 'cookiePolicy']` | Which links from the integration's `legalLinks` render after the description. A Banner shows only the Privacy Policy. `null` shows none |
| `hideBranding` | `boolean` | `false` | Removes the "Consent by" tag |
| `disableAnimation` | `boolean` | The integration's `disableAnimation` | Skips the enter and exit animations |
| `noStyle` | `boolean` | `false` | Renders the markup without Inth's class names or button styles |
| `class` | `string` | None | Extra class on the prompt root, kept with `noStyle` |
| `force` | `boolean` | `false` | Renders the banner even when the server decided to hide it, for visual tests |
| `nonce` | `string` | `Astro.locals.inth.nonce` | Content Security Policy nonce for this banner's inline scripts and style. See [Content Security Policy](/docs/frameworks/astro/content-security-policy#allow-inth-with-a-nonce) |

A prop wins over the translation for the visitor's language, which wins over
the English default. For wording on every page, set `i18n.messages` in the
integration instead. See [Translations](/docs/frameworks/astro/translations).

`force` does not create a policy. With no resolved policy, or under a rule that
owes no consent interface, the banner still renders nothing. On a prerendered
page, `force` also renders the banner visible.

## Actions come from the policy

The resolved policy rule decides which buttons the prompt shows and in which
order. The same resolver runs for the React, Vue and Svelte banners, so a rule
produces the same actions on every framework:

- A `choice` prompt shows Reject and Accept at equal prominence, plus
  Customize when the rule offers it. Customize opens the choices inside the
  prompt: the cookie categories in the EU, and the sale-and-sharing row and
  Preferences in the US. Save records them.
- A `notice` prompt shows **OK** and, under an opt-out rule, an opt-out link
  (by default "Do not sell or share my data"). **OK** records that the
  visitor saw the notice. It records no consent and changes no permission.

Under an opt-out rule, the prompt's opt-out link opens the sale-and-sharing
rights row inside the prompt, where the visitor can opt out. The link never
records an opt-out on its own and does not open the dialog. Programmatic calls
to `client.optOut()` still opt out in one step and open the opt-out
confirmation view (`OptOutConfirmation`) with its receipt.

Under an opt-out rule while an opt-out is held, clicking **Accept All** on a
choice banner opens the separate two-step opt-in confirmation dialog instead of
saving right away. Nothing changes until the visitor confirms. Under an opt-in
rule, **Accept All** still lifts a held opt-out in one step.
[How consent works](/docs/concepts/how-consent-works) explains prompts, rights
and recorded choices.

## Containers

The integration's `presentation.prompt` option places the prompt for every
page. The policy still decides the actions:

| Container | Positions | Default | Shape |
| --- | --- | --- | --- |
| `{ type: 'card', position }` | `start`, `end`, `center` | `start` | A floating card in a bottom corner, or centred over a backdrop |
| `{ type: 'banner', edge }` | `bottom`, `top` | `bottom` | A full-width banner along one edge |
| `{ type: 'drawer', side }` | `bottom`, `top`, `start`, `end` | `bottom` | A panel along one side that shows every choice at once on desktop |

```js title="astro.config.mjs (partial)"
inth({
	presentation: {
		prompt: {
			container: { type: 'banner', edge: 'bottom' },
			edgeStyle: 'flush',
		},
	},
});
```

`start` and `end` are logical: on a right-to-left page, `start` is the
bottom-right corner. On phones, a `start` or `end` Drawer becomes a bottom
Drawer. `edgeStyle: 'inset'` (the default) floats a Banner or Drawer 12px off
the viewport edges with rounded corners; `'flush'` runs it edge to edge.

Without `presentation.prompt.container`, the policy rule's
`surface.container`, set in the dashboard, places the prompt. `edgeStyle`
follows the same order.

**Blocking.** `blockUntilChoice: true` dims the page, locks scroll, and keeps
focus inside the prompt until the visitor chooses. A centred Card always
blocks. A notice never blocks, and neither does a prompt under an opt-out
model. The policy's `surface.blocking` is a hard rule: `forbidden` never
blocks, and `required` always blocks a choice prompt.

The prompt has no per-page container prop. Every prompt on the site shares
`presentation.prompt`. See the [design gallery](/docs/customization/recipes).

## Legal links

Define the links once in the integration's `legalLinks` option, then pick
which ones this banner shows:

{/* example: fragment */}

```astro title="src/layouts/base.astro (partial)"
<ConsentBanner legalLinks={['privacyPolicy', 'cookiePolicy']} />
```

A key renders only when the integration defines it. Each link opens in a new
tab. A link without a `label` reads as the translated name for its type, such
as "Privacy Policy" in English or "Datenschutzerklärung" in German. Set
`label` in the integration options, such as
`{ href: '/privacy', label: 'Privacy notice' }`, to use your own wording.
[`ConsentDialog`](/docs/frameworks/astro/components/consent-dialog#props)
takes the same `legalLinks` list.

## Accessibility

- The card is labelled by its heading. A non-blocking prompt leaves the page
  usable by keyboard and pointer.
- A blocking prompt puts `role="dialog"` and `aria-modal="true"` on the shell
  around the card. The browser makes the page behind it inert, locks scroll,
  keeps focus inside it and shows a backdrop until the visitor answers. Esc
  folds the choices and never closes the prompt.
- The root carries `dir` for the translation's language, so right-to-left
  text lays out correctly.
- Every action is a `<button type="button">`. Until the prompt's chunk has
  loaded, a click does nothing.

## Style the banner

Theme tokens and `theme.consentActions` change colors, type, radius and button
styles without touching the markup. See
[Customize](/docs/frameworks/astro/customize).

To write your own CSS, target the attributes. They stay with `noStyle`:

| Element | Attributes |
| --- | --- |
| Root | `data-testid="consent-banner-root"`, `data-placement` (`card-start`, `card-end`, `card-center`, `banner-bottom`, `banner-top`, `drawer-bottom`, `drawer-top`, `drawer-start`, `drawer-end`), `data-flow` (`expand-in-place` or `all-in-one`), `data-variant` (`choice`, `us-consent` or `notice`), `data-edge-style`, `data-blocking`, `data-expanded`, `data-state` |
| Backdrop | `data-testid="consent-banner-overlay"`, rendered only for a blocking prompt |
| Shell and card | `data-testid="consent-banner-shell"`, `data-testid="consent-banner-card"` |
| Title and description | `data-testid="consent-banner-title"`, `data-testid="consent-banner-description"` |
| Footer and button groups | `data-testid="consent-banner-footer"`, `data-testid="consent-banner-footer-sub-group"` |
| Each action | `data-action` (`accept`, `reject`, `customize` or `dismiss`), `data-testid="consent-banner-<action>-button"` |
| The choices Customize opens | `data-testid="consent-banner-expand-panel"`, or `data-testid="consent-banner-body"` in a side Drawer |
| Each legal link | `data-testid="consent-banner-legal-link-<key>"` |

Keep Inth's rules loaded when you restyle the prompt. A prerendered page
ships it with the `hidden` attribute, and Inth's rules make `hidden` win over
the prompt's `display` rule.
