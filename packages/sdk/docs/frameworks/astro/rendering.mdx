## Choose a rendering path

Where consent resolves decides what the first HTML contains. A page that is
built once and served to everyone cannot contain one visitor's consent, so the
browser finishes the job. A page rendered per request can.

| Your site | Astro setup | Inth mode | Banner in the first HTML |
| --- | --- | --- | --- |
| Static pages on any static host | `output: 'static'`, no adapter | `hosted()` | No. The browser renders it after `/v1/consent/init` |
| Static pages, with the policy resolved in the browser | `output: 'static'`, no adapter | `manifest({ resolve: 'browser' })` | No. The browser renders it after reading the manifest |
| Pages rendered on each request | `output: 'server'` and an adapter | `manifest()`, the default | Yes |
| A server build with some prerendered pages | `output: 'server'`, `prerender = true` on those pages | `manifest()` | Only on the request-rendered pages |
| Cached pages that still need a per-visitor banner | An adapter, and `ConsentBannerDeferred` in the layout | `manifest()` | Yes, from a server island |
| Local development and tests with no backend | Either output | `testing()` | Depends on the output |

Every path uses the same layout, client entrypoint and scripts from the
[quickstart](/docs/frameworks/astro/quickstart). Only `astro.config.mjs` and,
for cached pages, the banner component change.
[Choose your setup](/docs/concepts/choose-your-setup) explains the trade-off
across frameworks.

## Static output with `hosted()`

<include src="../../shared/examples/astro-static/static-config.mdx" />

Astro builds every page once. At build time there is no visitor, so
`ConsentBanner` renders an empty, hidden placeholder. In the browser, Inth
reads the visitor's consent cookie, calls your backend's `/v1/consent/init` directly, and
renders the banner into the placeholder when the policy says to show one. A
returning visitor keeps their choice, because it comes from their own cookie.

The browser calls the backend from your site's origin, so that origin must be
in the Inth project's trusted origins.

The default `manifest()` does not work here. It injects an on-demand route,
and without an adapter `astro build` stops with an error that names it.

## Static output with browser resolution

`manifest({ resolve: 'browser' })` resolves the policy in the browser from
your project's manifest, with no request to the backend's `/v1/consent/init`:

{/* example: fragment */}

```js title="astro.config.mjs"
import svelte from '@astrojs/svelte';
import inth, { manifest } from '@inth/astro';
import { defineConfig } from 'astro/config';

export default defineConfig({
	integrations: [svelte(), inth({ mode: manifest({ resolve: 'browser' }) })],
});
```

The build downloads the manifest and the integration prerenders it as a
static file at `/api/inth/v1/consent/manifest`, so no adapter is needed. The browser
fetches that file from your own origin, loads the resolver, and resolves the
policy. It has no request location, so without `inputs` or `geoUrl` every
visitor gets the policy your project assigns when the location is unknown.
Use `hosted()` when your policy differs by region and you have no location
source. Consent saves go to the backend, so your site's origin must be in
the Inth project's trusted origins.

## Server output with `manifest()`

<include src="../../shared/examples/astro/server-config.mdx" />

The integration registers a middleware that runs before every page. It reads
the visitor's consent cookie, location headers and Global Privacy Control
signal, resolves the policy, and stores the result in `Astro.locals.inth`. The
components render from it, so the banner is part of the HTML and a visitor who
has already chosen gets no banner markup at all. Such a page holds one
visitor's decision, so keep it out of shared caches. See
[Server API](/docs/frameworks/astro/server#cache-server-rendered-pages-safely).

`manifest()` resolves each request on the server from your project's public
policy file. By default the build downloads that file and bundles it, so a
render never waits on the backend for the policy. With
`manifest({ source: 'runtime' })`, or when a build-time fetch fails under the
default `onBuildError: 'runtime'`, the server downloads and caches the file at
runtime. The browser asks the injected `/api/inth/v1/consent/init` route when it needs a
decision, and saves consent to the project URL. A server-rendered page ships
only the code that saves consent; the code that resolves a policy loads when
a page asks again. `manifest()` needs the project URL as `projectUrl`,
`PUBLIC_INTH_PROJECT_URL`, or `PUBLIC_C15T_BACKEND_URL`; without it, the
config fails to load.
[Data fetching](/docs/concepts/data-fetching) compares this with calling
`/v1/consent/init` for every render.

`hosted()` also works with server output. Every server render then calls the
backend's `/v1/consent/init`, so each page view waits on a backend request.

### Set how long a render waits for the backend

The middleware waits up to 500 ms for the policy. With a bundled manifest the
policy is already on the server, so the budget matters when the server
fetches it at runtime or uses `hosted()`. If the backend has not answered by
then, for example on a cold cache or during an outage, the page
renders without a server decision. The HTML has no banner, optional categories
are denied, and gated scripts and iframes stay blocked. The browser then asks
for the policy and shows the banner when it arrives.

Change the budget in the integration options:

{/* example: fragment */}

```js title="astro.config.mjs (partial)"
inth({ middleware: { timeoutMs: 800 } });
```

Set `timeoutMs: false` to wait however long the backend takes. With
`hosted()`, keep the budget above the backend's usual `/v1/consent/init` response time.

### Skip routes that never render consent

The middleware resolves consent for every route, including your API routes.
List routes that should not pay for that, such as health checks or webhooks.
A prefix also covers the routes below it, and `Astro.locals.inth` stays unset
on a skipped route:

{/* example: fragment */}

```js title="astro.config.mjs (partial)"
inth({ middleware: { skip: ['/api/webhooks', '/healthz'] } });
```

The integration's own route under `routePrefix` is always skipped.

## Prerender pages in a server build

Add `prerender` to a page's frontmatter to build it once in a server build:

```astro title="src/pages/about.astro (partial)"
---
export const prerender = true;
---
```

The middleware sees that the page is prerendered and does not read the build's
request headers or cookies. The page then behaves like a page from a static
build. The browser reads the visitor's cookie, requests the policy from
`/api/inth/v1/consent/init` and renders the banner. Other pages still render per request.

If you call `resolveConsentContext` from `@inth/astro/server` yourself, pass
`prerendered: true` only for output that every visitor shares. It drops the
request's cookie and location, so do not use it to skip the backend for one
visitor's render.

## Cache a page and render the banner per request

A page served from a CDN cache or prerendered once can still show the right
banner to each visitor. Replace `ConsentBanner` with `ConsentBannerDeferred`,
which renders the banner in an Astro server island:

<include src="../../shared/examples/astro/cached-layout.mdx" />

The page HTML stays the same for everyone. The island's request carries the
visitor's cookie and location, so the middleware resolves consent for it and
the banner arrives with the visitor's own policy. Server islands need an
adapter. On a static host with no adapter, use `ConsentBanner` and let the
browser render it.

## Keep consent across `ClientRouter` navigation

With Astro's `ClientRouter`, the browser swaps pages without reloading scripts.
Inth creates one consent runtime per page load and keeps it across swaps. After
each swap it re-attaches to the new page's banner, gated scripts and dialog
triggers, applies the color scheme again, and keeps any stylesheet it linked
for the dialog. The
visitor's choice and an open dialog both carry over, and no new `/v1/consent/init`
request is made.

Your own scripts run once per page load, like Inth's. To update markup after a
swap, listen for `astro:page-load`. See the
[client API](/docs/frameworks/astro/client-api).

## Test without a backend

`testing()` from `@inth/astro/testing` resolves policies in the browser and on
your server with no backend. It is for tests only and throws in production
builds.

```js title="astro.config.mjs (partial)"
inth({ mode: testing() });
```

Import `testing` from `@inth/astro/testing`. Choices persist in the visitor's cookie and
localStorage only. There are no consent records, no hosted policies and no
visitor counts. Pass `policy` to `testing()` to test a specific policy.

On a prerendered page, `testing()` resolves the policy at build time because
it needs no request. The banner is in the HTML but hidden, and a small inline
script shows it in the first paint to visitors with nothing stored.

## Know when the consent engine loads

The `inth()` integration keeps Inth's consent engine out of the page's
first-load JavaScript. The engine is the code that stores consent, saves
choices, runs the script loader and mounts the dialog. The first load carries a
small page script instead: the banner's click handler and the code that
records a banner choice.

`<ConsentScript />` and the banners write the consent state the server
rendered the page from next to the config, in a
`<script type="application/json" data-inth-boot>` data block. Until the engine
loads, `getConsentClient()`, `getConsent()` and `subscribe()` answer from that
state. `client.runtime` is `undefined` until `client.ready` resolves.

The page script loads the engine as soon as it runs. The consent prompt's
Customize, its choices, its commits and its blocking all run on the engine,
so a page that shows the prompt does not wait for it.

The prompt is interactive once its own chunk has loaded beside the engine.
A tap on the server-rendered prompt before then does nothing.

For a visitor the server shows no prompt, such as one with a stored choice,
the page carries none of the prompt's stylesheets. Opening the dialog on that
page adds the stylesheets it needs first.

## Check the rendering path

- **Server output:** view the page source of a first visit. It contains
  `data-testid="consent-banner-root"`. After you choose and reload, it does not.
  In DevTools Network, the browser does not request `/v1/consent/init` on a server-rendered
  page.
- **Static output or a prerendered page:** the page source has no banner
  markup. In DevTools Network, the browser requests `/v1/consent/init` from your backend
  with `hosted()`, `/api/inth/v1/consent/manifest` with
  `manifest({ resolve: 'browser' })`, or `/api/inth/v1/consent/init` in a server build,
  and the banner appears after it returns.
- **Server island:** the page source has no banner markup. In DevTools
  Network, a request to `/_server-islands/ConsentBanner` returns it.
- **Every path:** vendor requests stay absent until you allow their category,
  and a rejection survives a reload. See
  [Verify consent](/docs/guides/verify-consent).
