## What Inth adds to the page

A Content Security Policy for an Astro site using Inth must allow these resources:

| What | Where it comes from | Directive |
| --- | --- | --- |
| The color-scheme script | Inline, in `<head>`, with `colorScheme` `'system'` or `'dark'` | `script-src` |
| The banner reveal script | Inline, after a banner on a prerendered page | `script-src` |
| The early-tap script | Inline, before a server-rendered banner, to hold a tap until the banner's code loads | `script-src` |
| `<style data-inth-styles="inth-first-paint">`, the banner's rules | Inline, in `<head>` from `ConsentScript`, or from the banner on a layout without it, unless `styles: false` or the site uses Tailwind CSS 3. On a page where the server shows no banner, the browser adds the same element with the page's nonce when the dialog opens | `style-src` |
| `<style data-inth-styles="inth-iab-first-paint">`, the IAB banner's rules | Inline alongside the base rules when IAB is configured | `style-src` |
| `<style id="inth-theme">` | Inline, when the integration sets `theme` | `style-src` |
| The page script that starts the consent client, the banner's click handler, and the consent engine | Bundled module scripts from your own origin | `script-src 'self'` |
| The dialog's stylesheet, IAB panel rules for the IAB dialog, and Svelte primitives | Stylesheets from your own origin, linked before the dialog mounts | `style-src 'self'` |
| Full base and configured IAB stylesheets on a Tailwind CSS 3 site, or stylesheets you import with `styles: false` | Stylesheets from your own origin | `style-src 'self'` |
| Vendor `<script>` elements | Created by the script loader when a category is allowed | `script-src`, plus each vendor's hosts |
| Gated inline scripts | Your own `type="text/plain"` scripts, copied into live scripts | `script-src` |

The per-visitor boot payload is not on this list. `ConsentScript` and the banners render it as a `<script type="application/json" data-inth-config>` data block, and `ConsentBanner` adds the state it rendered from as a `data-inth-boot` data block. Browsers never execute data blocks, so your CSP does not need to allow them.

The dialog islands can render `style` attributes, for example on animated sections. If your policy blocks style attributes, allow them with `style-src-attr 'unsafe-inline'`.

Choose one approach to allow the inline code:

| Policy | Use it when |
| --- | --- |
| A nonce from your own middleware | Pages render on each request and you set the policy header yourself |
| Astro's CSP, `security.csp` | You want Astro to generate hashes, including on prerendered pages, and the site does not use `ClientRouter` |

## Allow Inth with a nonce

Set `Astro.locals.inth.nonce` in your own middleware. Inth's middleware runs first with `order: 'pre'`, so `Astro.locals.inth` exists before yours runs. Generate a nonce per request, assign it, render, and send the header with the same nonce:

{/* example: fragment */}

```ts title="src/middleware.ts"
import { defineMiddleware } from 'astro:middleware';

export const onRequest = defineMiddleware(async (context, next) => {
	const nonce = crypto.randomUUID();
	if (context.locals.inth) {
		context.locals.inth.nonce = nonce;
	}
	const response = await next();
	response.headers.set(
		'content-security-policy',
		`script-src 'self' 'nonce-${nonce}'; style-src 'self' 'nonce-${nonce}'`
	);
	return response;
});
```

With the nonce set, every inline `<script>` and `<style>` rendered by `ConsentScript`, `ConsentBanner`, and `IABConsentBanner` carries it. The browser runtime reads the nonce from `data-inth-config` and stamps it on:

- Vendor scripts injected by the script loader, unless a script entry sets its own `nonce`.
- Gated `type="text/plain"` scripts it activates.
- Stylesheet links added the first time a dialog opens.

### Put the nonce on your gated scripts

When the page has a nonce, Inth activates a gated `type="text/plain"` script only if the tag carries that same nonce. Add it to each gated tag you write:

{/* example: fragment */}

```astro title="src/pages/index.astro (partial)"
<script
  is:inline
  type="text/plain"
  data-inth-category="measurement"
  nonce={Astro.locals.inth?.nonce}
>
  console.log('Measurement allowed');
</script>
```

Inth skips a gated tag without the nonce, logs a console warning, marks it `data-inth-activated="untrusted"`, and never retries it. This check prevents an injected HTML tag from running under `'strict-dynamic'` once its category is allowed.

Gated tags you insert dynamically need the nonce too. Pass the page's nonce as the third argument to `activateGatedScripts(snapshot, container, nonce)` from `@inth/astro/client`. Pages without a nonce activate every gated tag.

Nonces work only on request-rendered pages. A prerendered page is built once, so every visitor would share the same nonce. Use Astro's CSP for prerendered pages.

The nonce covers elements rendered by Inth components. Your own inline scripts and stylesheets still need a nonce or hash.

### Pass the nonce to `ConsentBanner` and `ConsentBannerDeferred`

`ConsentBanner` reads `Astro.locals.inth.nonce` by default. Its `nonce` prop overrides the value for that banner only.

`ConsentBannerDeferred` forwards the page's nonce to its server island. Astro loads server islands with inline scripts that carry no nonce, and one script changes per render, so a middleware nonce policy blocks the island loader. On pages with `ConsentBannerDeferred`, use Astro's CSP (which hashes the loader per render) or render `ConsentBanner` instead.

## Allow Inth with Astro's CSP

Enable Astro's CSP with `security.csp` (or `experimental.csp` in Astro 5):

{/* example: fragment */}

```js title="astro.config.mjs (partial)"
export default defineConfig({
	security: { csp: true },
	integrations: [inth()],
});
```

The `inth()` integration adds hashes for the inline code it renders using your configured hash algorithm:

- The color-scheme script.
- The reveal scripts of `ConsentBanner` and `IABConsentBanner`.
- The banner's early-tap script.
- Base and configured IAB banner rules, unless `styles: false` or Tailwind CSS 3 uses external stylesheets.
- The theme stylesheet.
- The inline `textContent` of each entry in the integration's `scripts` option.

Leave `'unsafe-inline'` out, because Astro drops hashes from any directive that includes it.

Add these entries yourself:

- Gated `type="text/plain"` scripts you author: add each script's hash to `security.csp.scriptDirective.hashes`.
- Inline scripts registered in `clientEntrypoint`: the integration cannot see them at config time. With Astro's CSP enabled, Inth logs a console error naming each missing inline entrypoint script and the hash to add.
- Vendor script hosts: add them to `security.csp.scriptDirective.resources`, alongside `'self'`, because a custom list omits `'self'`.

Astro's CSP does not support `ClientRouter`. Use a middleware nonce on sites with `ClientRouter`.

## Allow Inth in `connect-src`

The browser saves consent to `${projectUrl}/v1/consent/records` and requests `/v1/consent/init` when the server did not resolve the policy. Allow these origins:

| Mode | Browser requests go to |
| --- | --- |
| `manifest()` (default) | Your own origin for `/api/inth/v1/consent/init`, and your Inth project origin for `/v1/consent/records` |
| `manifest({ resolve: 'browser' })` | Your own origin for `/api/inth/v1/consent/manifest`, your Inth project origin for `/v1/consent/records`, and `geoUrl` if set |
| `hosted()` | Your Inth project origin for `/v1/consent/init` and `/v1/consent/records` |
| `testing()` | No remote requests |

{/* example: fragment */}

```txt title="Content-Security-Policy (partial)"
connect-src 'self' https://your-project.inth.app;
```

<ProjectUrlHint>Replace `https://your-project.inth.app` with your Inth project URL.</ProjectUrlHint> Server-side requests from the middleware and injected routes run in Astro and are outside the browser's CSP. Under an IAB TCF policy, allow the Global Vendor List host if it differs from your origin.

Vendors add their own hosts to `script-src`, `connect-src`, `img-src`, and `frame-src`. Each [integration guide](/docs/integrations/overview) lists the requests to expect.

## Check your policy

1. Load a server-rendered page with the policy enforced (not report-only) and open the DevTools Console. Confirm no `Refused to execute inline script` or `Refused to apply inline style` error appears.
2. View the page source. Under a nonce policy, confirm the color-scheme `<script>`, `<style id="inth-theme">`, and `<script type="application/json" data-inth-config>` carry a `nonce` matching the response header. (The Elements panel hides nonce values after checking them.)
3. Confirm the banner renders with your theme colors and records a choice.
4. Open the preference dialog and confirm it is styled with no `style-src` violation.
5. Allow a category gating a vendor. Confirm the vendor loads with no `connect-src` or `script-src` violations.
6. Save a choice and confirm `POST /v1/consent/records` succeeds in DevTools Network.
