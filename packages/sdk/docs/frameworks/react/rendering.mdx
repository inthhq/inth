`@inth/react` resolves consent in the browser for every React app, including server-rendered setups. What changes between setups is what the initial HTML contains.

## Pick your rendering path

| Your app | Where consent resolves | Setup |
| --- | --- | --- |
| Vite or another client-rendered single-page app | Browser, after the bundle loads | [Quickstart](/docs/frameworks/react/quickstart) |
| Prerendered or static HTML | Browser, after the page loads | [Quickstart](/docs/frameworks/react/quickstart), see [static pages](#static-and-prerendered-pages) |
| React Router framework mode, Remix, or another server-rendered React app | Browser, after hydration | [Quickstart](/docs/frameworks/react/quickstart), see [server-rendered apps](#react-router-remix-and-other-server-rendered-apps) |
| Next.js or TanStack Start | Server, per request | That framework's guide in the [framework list](/docs/frameworks) |

Use the Next.js or TanStack Start adapter if you run those frameworks: they read the visitor's cookie and location on the server so the banner can ship in the first HTML. [Choose your setup](/docs/concepts/choose-your-setup#server-rendering-or-browser-rendering) compares both models.

## Client-rendered apps

The [quickstart](/docs/frameworks/react/quickstart) connects `InthProvider` to your Inth project URL, which uses `hosted()` mode by default. Policy edits apply on the next page load without a rebuild:

1. The page loads with no consent state and every optional category denied.
2. The browser sends `/v1/consent/init` to your Inth project URL. A [script in `index.html`](#send-init-before-the-app-loads) starts it while JavaScript downloads, and Inth picks the policy from the visitor's location. With an `experiment`, pass `initPrefetch: { experiment }` to `consentManifest()` so the early request carries the visitor's arm; otherwise the provider sends its own `/v1/consent/init` on mount.
3. The provider applies the policy and any stored choice, shows the banner if required, and loads allowed scripts.

Until step 3 finishes, gated scripts and `ConsentGate` embeds stay blocked. If `/v1/consent/init` fails, they remain blocked and no banner renders.

### Show the banner from `index.html`

`vite build` also places the default banner in `index.html`, hidden. When the early `/v1/consent/init` answers, the inline script reveals it before your JavaScript finishes downloading. `<ConsentBanner />` takes over in the same frame once React renders. Clicking a button before React loads hides the banner immediately and records the choice once the app boots.

The build reads your project manifest and renders the banner for its first choice policy in the language of `<html lang>`, or English. The page shows that static banner only when all of these match the `/v1/consent/init` response:

- the policy
- the language
- the branding
- the banner title, description, and button labels

It also stays hidden if the visitor already has a stored choice. Otherwise the inline script removes it and React renders its own banner.

While the static banner is shown, the app defers downloading `<ConsentBanner />` and the `/v1/consent/init` handler until after `fetchpriority="high"` images finish, or immediately on tap, keypress, or scroll, avoiding bandwidth competition with your hero image. Banner stylesheets move from JavaScript into `index.html` so they ship once.

The build cannot inspect your runtime provider options. Disable the static banner with `consentManifest({ staticBanner: false })` whenever your initial banner differs from the default:

- custom `i18n` messages
- `legalLinks`
- a custom `theme`
- `components` slots
- props on `<ConsentBanner />`
- a composed or headless banner

Only entry pages importing `ConsentBanner` receive the static banner, and only in production builds with `/v1/consent/init` prefetch enabled. If the manifest fetch fails during the build, Vite logs a warning and omits the static banner. Under a Content Security Policy, set Vite's `html.cspNonce` or allow the inline script and style hashes.

## React Router, Remix and other server-rendered apps

React Router framework mode, Remix, and similar frameworks use `@inth/react` directly. Render the quickstart `Consent` component in your root layout around the outlet, such as `app/root.tsx` in React Router framework mode.

`InthProvider` renders on the server without touching browser APIs, and the browser takes over after hydration:

- Server HTML contains your page with no banner and no consent state.
- After hydration, the browser calls `/v1/consent/init` and shows the banner if the policy requires one.
- Server and initial client renders match, so hydration produces no warnings and never overwrites a stored choice.

Your Vite config needs no changes, and components render their own `<style>` elements without an extra stylesheet import.

Because these frameworks render their own HTML document, the Vite plugin cannot inject the early `/v1/consent/init` script into `index.html`. Render `buildPrefetchScript({ projectUrl })` from `@inth/react/engine` inside a `<script>` in your root `<head>` instead, unless your server loader passes `initialData` as shown below.

### Skip the browser's first init request

Optionally, call `fetchSSRData` from `@inth/react/server` in your server loader to run `/v1/consent/init` server-side with the visitor's location and language headers. Pass the returned value to the browser, wrap it in a promise, and hand it to `hosted({ projectUrl, initialData })` from `@inth/react/transports` as the provider `mode`. The provider then consumes that response instead of issuing a browser `/v1/consent/init`.

Keep these limits in mind:

- It removes the browser round trip to Inth, but does not render the banner in server HTML; the banner still mounts after hydration.
- Every request calls `/v1/consent/init` server-to-server. Never cache the loader response across visitors.
- It returns `undefined` when the request lacks location and language headers, falling back to browser `/v1/consent/init`.
- The provider reads `mode` once on mount, so create the `hosted()` mode once rather than on every render.
- A relative `projectUrl` resolves against the request `Host` header (`https` for domain names, `http` for `localhost`, IP addresses, or single-label hosts). `fetchSSRData` ignores `x-forwarded-host`, `x-forwarded-proto`, and `forwarded` unless you pass `trustForwardedHeaders: true` behind a trusted proxy.
- If your server accepts arbitrary `Host` headers, pass an absolute `projectUrl` to `fetchSSRData`.

### Render the banner in the server HTML

Inth does not ship a framework-neutral helper for server-rendered banners. While `InthProvider` accepts a server-resolved `prefetch` payload, building it manually from cookies, headers, and a cached manifest ties your app to internal shapes. If the banner must appear in the first server HTML, use `@inth/nextjs` or `@inth/tanstack-start`.

## Static and prerendered pages

Prerendered HTML is shared across all visitors, so it cannot contain one visitor's consent state. Use the quickstart setup: `/v1/consent/init` and `/v1/consent/records` go directly to your Inth project URL, so static hosts need no server routes. Add your site's origin to your Inth project's trusted origins.

Never cache a response containing a visitor's consent in a CDN or shared page cache. See [Data fetching](/docs/concepts/data-fetching) for caching rules.

## Where the browser sends requests

In `hosted()` mode, the browser calls two endpoints on your Inth project:

| Request | When |
| --- | --- |
| `GET {url}/v1/consent/init` | Once per page load to resolve the policy |
| `POST {url}/v1/consent/records` | When the visitor accepts, rejects, or saves |

Add your site's origin to your Inth project's trusted origins so cross-origin requests succeed. [Data fetching](/docs/concepts/data-fetching) compares direct requests and same-origin proxies.

## Check the rendering path

1. Open the site in a private window and view page source. In a server-rendered React app, the HTML includes your page content and no `data-testid="consent-banner-root"` element.
2. Open DevTools Network and confirm one `/v1/consent/init` request fires unless you passed `initialData`.
3. Confirm the banner renders once the policy resolves and vendor requests stay blocked until allowed.

## Bundle the policy at build time

`manifest()` resolves the policy in the browser from a build-time snapshot. It avoids `/v1/consent/init` only when:

- Your policy has no location rules, or every location shows the same banner.
- The page already knows the visitor's location, such as from an edge worker, and passes it via `inputs`.
- You run a same-origin `geoUrl` endpoint returning the visitor's location.

Otherwise the browser still calls `/v1/consent/init` on a first visit, adding bundle bytes without saving a request, and `consentManifest()` logs a build warning. The browser resolver adds about 3 KB gzipped, policy updates require a rebuild, and visits resolved locally do not send `/v1/consent/init`.
