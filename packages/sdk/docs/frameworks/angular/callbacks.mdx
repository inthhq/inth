## Pick the right callback

Run your own code when consent changes through the `callbacks` option of
`provideC15t()`, a script's own callbacks, or a signal in one component:

| You want to | Use |
| --- | --- |
| Send a choice to your analytics or CRM when the visitor makes one | `callbacks.onChoiceRecorded` |
| Start or stop your own code when what may run changes | `callbacks.onPermissionsChanged` |
| Count banner and dialog impressions | `callbacks.onSurfaceShown` |
| Report failed backend requests | `callbacks.onError` |
| Show a message or flush data before a withdrawal reloads the page | `callbacks.onBeforeConsentRevocationReload` |
| Call a vendor's own consent API after its script loads | The script's `onConsentChange` |
| React to consent inside one component | A `ConsentManager` signal in `computed()` or `effect()` |

## onChoiceRecorded or onPermissionsChanged

`onChoiceRecorded` runs only when the visitor accepts, rejects or saves.
`onPermissionsChanged` runs whenever effective permissions change, whatever
the cause:

| Event | `onChoiceRecorded` | `onPermissionsChanged` |
| --- | --- | --- |
| Visitor accepts, rejects or saves | Yes | Yes, if a permission changed |
| Policy resolves under opt-out and allows categories before a choice | No | Yes |
| Global Privacy Control overrides a grant | No | Yes |
| A recorded choice expires | No | Yes |
| Visitor dismisses a notice | No | No |

Use `onChoiceRecorded` for consent records and audit trails, because it fires
only for a visitor's action. Use `onPermissionsChanged` to start or stop code,
because it covers every way a permission changes. Never treat
`onPermissionsChanged` as proof that the visitor agreed to something.

## Pass callbacks to the provider

Write the callbacks in their own module:

<include src="../../shared/examples/angular/consent-callbacks.mdx" />

Then pass them in `src/app/app.config.ts`, next to `mode`:

{/* example: fragment */}

```ts title="src/app/app.config.ts (partial)"
provideC15t({ mode, scripts, callbacks });
```

The callbacks are plain functions, outside any injection context, so they
cannot call `inject()`. To reach an Angular service from one, read
`ConsentManager` signals in an `effect()` instead, as shown below.

| Callback | Payload |
| --- | --- |
| `onChoiceRecorded` | `snapshot`, the state after the choice; `confirmed`, the categories this action recorded; `actionAt`, the time. |
| `onPermissionsChanged` | `snapshot`, the state after the change; `previous`, the permissions before it. |
| `onSurfaceShown` | `surface`, the surface that opened; `shownAt`, the time; `snapshot`; `experiment`, the assigned arm if any. Once per opening, never for a hydrated record or a server render. |
| `onError` | `error`, a message string. |
| `onBeforeConsentRevocationReload` | `preferences`, the permissions after the withdrawal. |

Callbacks run after c15t updates its own state, so `snapshot` and
`ConsentManager` already hold the new values. Visitor actions happen in the
browser, and the runtime never starts on the server, so the callbacks run in
the browser only.

`onBeforeConsentRevocationReload` runs synchronously right before the reload.
Keep it short; the page is about to unload. It does not run when you set
`reloadOnConsentRevoked: false`.

## Script callbacks

Each entry in `scripts` takes its own callbacks:

| Callback | Runs |
| --- | --- |
| `onBeforeLoad` | Before the loader adds the script. |
| `onLoad` | When the script loaded. |
| `onError` | When the script failed to load. |
| `onConsentChange` | When consent changes after the script loaded. Use it to call the vendor's own consent API. |
| `onDispose` | When the configuration is removed or the application is destroyed. |

Helpers from `@inth/integrations` already set these for their vendor.
[Building integrations](/docs/integrations/building-integrations) shows how to
write them.

## React inside one component

For a component that shows or reacts to consent, read `ConsentManager`
signals. A `computed()` re-renders the template; an `effect()` runs code, and
goes away with the component. For a kernel event, such as a recorded choice,
subscribe in an `effect()` with `onCleanup`.
[ConsentManager](./services#listen-to-consent-events) has the example.

## Verify the callbacks

Open the console, clear site data and reload:

1. The banner shows. `onSurfaceShown` logs `banner`.
2. Accept in the banner. `onChoiceRecorded` and `onPermissionsChanged` both
   log.
3. Dismiss a notice, if your policy shows one. Neither logs.
4. Withdraw a category you allowed. `onBeforeConsentRevocationReload` logs,
   then the page reloads.
