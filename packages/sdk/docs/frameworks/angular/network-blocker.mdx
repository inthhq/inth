Hold `fetch`, `XMLHttpRequest` and Angular `HttpClient` calls to tracking
domains until their consent category is allowed.

## When to use the network blocker

The network blocker intercepts `fetch` and `XMLHttpRequest` calls to domains
you list until their consent category is allowed. Angular's `HttpClient` runs
on one of those two transports, so its requests are covered too. Use it as a
backstop for tracking calls from code already bundled in your app, such as an
analytics service or an imported SDK. It is off until you configure it.

Move vendor SDKs into `scripts` first; see [scripts](./scripts). A script
that never loads sends nothing, which is cleaner than blocking individual
requests.

Write the rules in their own module:

Pass them to `provideInth()` in `src/app/app.config.ts`:

{/* example: fragment */}

```ts title="src/app/app.config.ts (partial)"
provideInth({ mode, scripts, networkBlocker });
```

To change the rules later, call
`ConsentManager.updateOptions({ networkBlocker })`. Passing `false` removes
the blocker.

## What a blocked request looks like

A blocked `fetch` resolves to status `451` (`Request blocked by consent`)
without sending a request. A blocked `XMLHttpRequest` aborts and fires an
`error` event. `HttpClient` surfaces either as an `HttpErrorResponse`: status
`451` with `withFetch()`, or status `0` with the default XHR backend.
Unmatched requests pass through without delay. With `logBlockedRequests` on
(the default), Inth logs each blocked request via `console.warn`;
`onRequestBlocked` receives `{ method, url, rule }`.

## When blocking starts

`provideInth()` creates the runtime during application creation, before any
component runs, and begins holding matching requests immediately. The blocker
module loads after the first render and resolves held requests:

- While the policy loads, matching requests wait instead of failing. Once the
  policy and stored choice arrive, permitted requests go out and denied ones
  block.
- If the policy fails to load, optional categories stay denied and waiting
  requests block.
- Synchronous XHR cannot wait. Before the blocker loads, a matching
  synchronous XHR throws `NetworkError` from `send()`.

When the visitor allows a category later, new matching requests go through.
Previously blocked requests do not replay.

## What it cannot stop

The blocker intercepts only `fetch` and `XMLHttpRequest` calls made after
application creation in the browser. It cannot stop:

- Scripts that run before Angular bootstraps, such as `<script>` tags in
  `index.html`, entries in `angular.json`, and top-level code in modules
  imported by `main.ts`.
- Code that cached a reference to `fetch` or `XMLHttpRequest` before
  application creation.
- `navigator.sendBeacon`, `WebSocket`, `EventSource`, `<img>`, `<script>` and
  `<iframe>` requests, web workers and service workers.
- Server-side requests, such as `HttpClient` calls during SSR.

Keep tracking calls in event handlers or effects rather than at module top
level, and check `ConsentManager.has('measurement')` before calling a vendor
from your own code.

## Verify the blocker

Open DevTools, clear site data for your origin and reload:

1. Before choosing, requests matching a rule do not reach the network, and
   the console logs each blocked request.
2. Allow the rule's category. New matching requests appear in the Network
   panel.
3. Reject, reload and confirm they stay blocked.

Running `fetch('https://www.google-analytics.com/g/collect')` in the console
returns status `451` while measurement is denied.
