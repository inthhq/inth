`@inth/react-native` requires the React Native New Architecture. Because its consent engine and stock screens compile into your native binary, native configuration changes and SDK upgrades require a rebuild while compatible JavaScript changes can ship over the air.

## Check supported versions

The current private prerelease supports:

| Component | Requirement |
| --- | --- |
| React Native | `0.83.x` through `0.88.x` (New Architecture enabled) |
| React | `>=19.2.0 <19.4.0`, matching your RN or Expo release |
| Expo | SDK 55 through 58 (custom development or release build) |
| iOS | 16.4 or later (Swift 5.9 language mode or later) |
| Android | API 24 or later, JDK 17, compile SDK 36 or higher host requirement |

Expo Go and the legacy React Native bridge cannot load this module. Pair Expo SDK releases with their prescribed versions:

| Expo SDK | React Native | React | Android compile SDK |
| --- | --- | --- | --- |
| 55 | `0.83.x` | `19.2.0` | 36 |
| 56 | `0.85.x` | `19.2.3` | 36 |
| 57 | `0.86.x` | `19.2.3` | 36 |
| 58 | `0.88.x` | `19.3.0` | 37 |

Bare RN `0.84.x` and `0.87.x` are also supported (`0.87` and `0.88` require compile SDK 37, which does not raise your minimum Android API level). The Expo plugin automatically sets the iOS deployment target to at least 16.4 (including Expo 55's 15.1 default); bare apps must set 16.4 manually. Always test on your minimum and latest supported OS versions before shipping.

## Choose versions for a new app

Target React Native `0.88` with React `19.3`, or Expo SDK `58`, for new apps and complete the [mobile verification checklist](/docs/guides/mobile-verify) before release.

Inth compatibility does not extend upstream framework maintenance. As of November 3, 2026, RN `0.87` and `0.88` are active upstream, `0.86` is End of Cycle, and `0.83` through `0.85` are unsupported upstream. Check [React Native releases](https://reactnative.dev/releases/overview) and the [Expo upgrade walkthrough](https://docs.expo.dev/workflow/upgrading-expo-sdk-walkthrough/). We review each stable RN and Expo release before adding support and drop older versions or raise OS floors only in major Inth releases.

## Keep native artifacts aligned

The npm version (`3.0.0-alpha.2`) and Android native artifact version (`3.0.0-alpha.1`) version independently. Let `@inth/react-native` select the Android native version and keep `inth-core`, `inth-android`, and `inth-consent-ui` on that exact version. On iOS, `InthReactNative.podspec` compiles vendored Swift sources; do not link standalone SwiftPM products alongside it.

## Know when to rebuild the binary

| Change | Rebuild binary? |
| --- | --- |
| Compatible React UI or app logic | Usually no; verify against the installed binary |
| Inth native APIs or Codegen | Yes |
| SwiftUI or Compose stock screens | Yes |
| Native theme, brand assets, or copy metadata | Yes |
| Permissions, ATT description, or native config | Yes |
| Bundled offline policy JSON | Yes |
| Hosted Inth dashboard policy or disclosure edits | No; loaded at runtime |

`InthProvider` validates native protocol version `1` on attach and throws `InthProtocolMismatchError` on mismatch. Rebuild whenever a native command reports a missing capability.

## Configure Expo OTA updates

When `updates.url` is enabled, the config plugin requires `runtimeVersion` (the [Expo guide](/docs/frameworks/react-native/expo) uses Expo's fingerprint policy). Ship OTA updates only to matching native runtimes.

## Migrate an existing consent setup

Keep one `InthProvider`, move optional SDK initialization behind native gates, and replace custom web-style dialogs with the native presenter from the [React Native quickstart](/docs/frameworks/react-native/quickstart) while keeping Privacy settings reachable. Map brand styling to [native customization](/docs/frameworks/react-native/customize), or follow [Build your own UI](/docs/frameworks/react-native/headless) for React-rendered controls.

Preserve stored consent across upgrades; use `reset()` only for explicit user or QA resets. Complete [Verify mobile consent](/docs/guides/mobile-verify) and check [mobile availability](/docs/guides/mobile-status) before release.
