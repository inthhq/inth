Jest and Vitest run your components without the native consent module, so a
`ConsentProvider` on its own throws `NativeInthUnavailableError` there.
`@inth/react-native/testing` gives a test the real consent client over a fake
native core: you choose the starting consent, render your screens, check what
they saved and answer the native prompt the way a person would.

## Set up Jest with jest-expo

Expo's recommended setup is the `jest-expo` preset with React Native Testing
Library. Install them as dev dependencies:

```bash
npx expo install --dev jest-expo jest @types/jest @testing-library/react-native test-renderer
```

`@inth/react-native` ships ES modules, and `jest-expo` only compiles packages
in its allowlist. Add `@inth` to the preset's `transformIgnorePatterns` entry
in `package.json`:

```json title="package.json"
{
	"scripts": {
		"test": "jest"
	},
	"jest": {
		"preset": "jest-expo",
		"transformIgnorePatterns": [
			"/node_modules/(?!(.pnpm|react-native|@react-native|@react-native-community|expo|@expo|@expo-google-fonts|react-navigation|@react-navigation|@sentry/react-native|native-base|@inth))"
		]
	}
}
```

Without it, Jest stops at the first import with `Must use import to load ES
Module`. This setting replaces the preset's whole list. If your project uses
Reanimated, also keep the preset's `/node_modules/react-native-reanimated/plugin/`
entry. You can read your installed preset's list in
`node_modules/jest-expo/jest-preset.js`.

Importing `@inth/react-native` in Jest does not touch the native module. The
lookup runs when a provider or client first needs it, so plain logic tests
can import the package without a test client.

## Choose the starting consent

`createTestConsentClient(options)` takes the state the native core holds when
the test starts. Call it once per test. Each call replaces the previous test
client.

| Option | Default | What it does |
| --- | --- | --- |
| `consent` | `'unset'` | `'unset'`: no choice yet, the prompt is owed and optional categories are denied. `'granted'` or `'denied'`: a stored choice for every optional category. An object such as `{ measurement: true }`: a stored choice where the categories you leave out are denied. |
| `ready` | `true` | `false` keeps the core starting, so every optional category reads `pending` and `useConsent` returns `false`. Call `consent.setReady()` to finish. |
| `nativeUI` | `true` | `false` tests a build without the stock native screens. The provider then presents nothing; render it with `autoPresent={false}` so it needs no `privacyPolicyUrl`. |
| `trackingAuthorization` | `'unsupported'` | The App Tracking Transparency answer. `'unsupported'` is Android's answer, so nothing asks Apple. |
| `snapshot` | none | Raw snapshot fields set over the others, such as `{ model: 'opt-out' }`. |

## Check what the app saved

`consent.commits` lists what your JavaScript sent to the native core, in
order:

| Your code | Entry |
| --- | --- |
| `useSaveConsents()('all')` | `{ action: 'all' }` |
| `useSaveConsents()('none')` | `{ action: 'necessary' }` |
| `useSaveConsents()({ measurement: true })` | `{ action: 'explicit', consents: { measurement: true } }` |

The fake stores each commit the way the native core does: the categories it
names change and the hooks rerender. Accept all and reject all answer the
prompt. A per-category save answers only the categories it names, and the
others keep their value, so the prompt stays owed until every category in the
policy has an answer.

## Change consent from the native side

Consent can change outside your JavaScript, for example on a native screen. In
a test, call `consent.setConsent(state)` with the same values `consent` takes.
`consent.setReady()` finishes start-up, and `consent.setReady(false)` goes back
to it. Components that read a category that moved rerender at once. The
helpers wrap the change in React's `act` when React Native Testing Library has
turned on its act environment, so you do not wrap them yourself.

## Answer the native prompt

The fake presenter behaves like the native one, but draws nothing:

- A `ConsentProvider` that presents (the default, with a `privacyPolicyUrl`)
  opens the owed prompt by itself as soon as it mounts. `consent.prompt.current`
  then has `automatic: true`.
- `presentConsentPrompt()` opens the prompt when one is owed, and answers
  `not-required` when it is not. `presentPreferences()` always opens. Both
  answer `already-presented` while a screen is open.
- `consent.prompt.acceptAll()`, `rejectAll()` and `save({ marketing: true })`
  store the choice and close the screen with a `committed` outcome.
  `acknowledge()` answers a notice: it records the acknowledgement, stores no
  consent and closes the screen with an `acknowledged` outcome.
  `dismiss()` closes it without an answer, and the prompt stays owed. A
  provider does not open a dismissed choice prompt again by itself until the
  prompt changes, for example after consent is reset; a notice opens again.
- As on a device, an answer is not stored, and the screen stays open, while the
  policy is pending, or when standing preferences were opened before consent
  changed elsewhere. The first layer follows such changes and saves normally.
  The choice actions throw on a notice, and `acknowledge()` throws on anything
  that is not a notice. `save()` with nothing changed and nothing owed closes
  the screen as `dismissed` and writes nothing.
- `client.reset()` leaves the cold-start state: nothing granted, no policy and
  no prompt. Call `consent.setReady()` to finish start-up; the policy resolves
  again and the choice prompt is owed.

Check `consent.prompt.isOpen` to see whether a screen is open. Answering when
none is open throws, so a test that expected a prompt fails at that line.
Choices made on the native screens do not appear in `consent.commits`, because
the native screens save without going through JavaScript. Read the result from
your rendered screen or from `consent.client.getSnapshot()`.

## Test a component that renders its own provider

The test client is also the app's shared client until the next test client
replaces it. A root component that renders `<ConsentProvider>` without a
`client` prop, and integrations created without a `client` option, reach the
same fake. You can render your whole `App` without changing it:

{/* example: fragment */}

```tsx
const consent = createTestConsentClient({ consent: 'unset' });

await render(<App />);
expect(consent.prompt.isOpen).toBe(true);
```

## Use Vitest

`createTestConsentClient` does not depend on Jest. In Vitest, your setup must
load React Native the way any React Native component test needs, for example
with a plugin that compiles `react-native` or an alias to a stand-in. Once
`react-native` resolves, the test code is the same, with `test` and `expect`
imported from `vitest`. Add `@inth/react-native` to `server.deps.inline` as
well: the package leaves some imports without a file extension so Metro can
pick each platform's file, and Node cannot load those on its own. A test that
runs under a web preset gets the web client, which has no native screens:
pass `nativeUI: false` to `createTestConsentClient()` and drive the
JavaScript UI, since `consent.prompt` simulates the native screens only.

## What the fake does not cover

- It stores categories, not IAB TCF choices. An IAB save applies its category
  consents and ignores the vendor and purpose choices.
- `identify`, `logout`, `refresh` and `setOverrides` resolve without changing
  consent.
- A tracking request answers with `trackingAuthorization` and never shows a
  prompt.

To check the real native screens, policy resolution and storage, run the app
on a device. See [Verify mobile consent](/docs/frameworks/react-native/verify).
