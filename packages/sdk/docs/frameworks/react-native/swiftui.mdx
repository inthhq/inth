Explore the runnable app in `packages/swift/Examples/swiftui-consent` to see stock SwiftUI screens, a custom category form, consent-gated tracking, and Keychain recovery in action. Its local demo mode uses an internal mock transport to persist choices in Keychain without an account; hosted mode connects to your Inth project URL. For a fresh production setup, choose Swift in the [framework list](/docs/frameworks).

## Build and open the project

The Swift modules ship as private prerelease source in `packages/swift` (`InthCore`, `InthApple`, and `InthConsentUI`), targeting iOS 16.4 or later. With Xcode and XcodeGen installed, generate and open the project from the repository root:

```sh
xcodegen generate --spec packages/swift/Examples/swiftui-consent/project.yml
open packages/swift/Examples/swiftui-consent/InthSwiftUI.xcodeproj
```

Select the `InthSwiftUI` scheme on an iOS simulator and run it (no npm or JavaScript runtime required). Keep ad-hoc simulator code signing enabled so the installer's Keychain probe succeeds.

## Own one engine for the app

The app creates one `AppConsentModel` in `App.init` and shares it through `@StateObject` across every scene:

<include src="../../shared/examples/native/core-swift/swiftui-consent/swiftui-app.mdx" />

`InthApple.install` checks Keychain and hydrates stored consent synchronously so optional SDKs can check gates immediately. A fresh install still resolves policy asynchronously (`decision(for: .measurement)` stays `.pending` until ready). On `protectedStorageUnavailable`, the model keeps optional work off and retries after unlock or scene activation without substituting memory or plaintext storage.

To run against your hosted Inth project, set `INTH_PROJECT_URL` and `INTH_PRIVACY_POLICY_URL` in the app target build settings:

<include src="../../shared/examples/native/core-swift/swiftui-consent/swiftui-hosted.mdx" />

Repeated installation keeps the first configuration. The sample isolates Keychain services across local demo, hosted mode, and UI tests.

## Use stock consent screens

The model holds one main-actor `ConsentPresenter` attached to the core. `.inth` presents an owed choice automatically, while the dashboard's **Privacy settings** button calls `presentPreferences()`:

<include src="../../shared/examples/native/core-swift/swiftui-consent/swiftui-presenter.mdx" />

Accept measurement, tap **Record sample event**, then reopen **Privacy settings** to turn measurement off and confirm the button disables and persists across relaunch. Before shipping a real app, replace stock `ConsentTheme` copy and branding to match your policy (see [Customize](/docs/frameworks/react-native/customize)).

A `.committed` result confirms durable local storage; the dashboard observes `eventStream` and `pendingSaveCount()` to show backend delivery separately.

## Test failure and persistence states

Pass `--demo-unavailable` to simulate an unreachable policy endpoint: fresh installs stay pending with measurement off, while saved choices hydrate from Keychain on relaunch.

The sample's XCTest and UI test suites cover pending gates, grant/withdrawal, refused writes, stale drafts, Keychain hydration, protected-storage retry, and teardown. See [iOS native installation](/docs/frameworks/react-native/apple) and [Offline consent](/docs/frameworks/react-native/offline) for production ownership and delivery behavior.
