## How Inth's styles meet Tailwind

Inth's component rules live in the CSS cascade layer `components`. Each Inth
stylesheet starts with Tailwind CSS 4's layer order,
`@layer properties, theme, base, components, utilities;`, and cascade layers
rank by the order they are first named. On Tailwind 4, Inth's rules stay above
Tailwind's preflight in `base` and below your utilities in `utilities`,
whichever stylesheet loads first. A plain utility such as `p-2` on an Inth part
wins without `!important`.

Tailwind CSS 3 has no cascade layers. It treats `@layer components` as its own
directive and fails the build on a stylesheet that uses it without a matching
`@tailwind components`. Inth's Tailwind 3 PostCSS plugin removes the layer
wrappers from Inth's stylesheets before Tailwind 3 runs. Inth's rules then
win by specificity, as they did in c15t v2, so a utility on an Inth part needs
Tailwind's important modifier, such as `!p-2`. The plugin cannot reach the
`<style>` elements Inth renders itself, so on Tailwind 3 you turn those off
with `styles: false` and import the stylesheet instead. The Astro integration
does this for you when it finds Tailwind 3.

The setups below come from fixtures that CI builds for each framework and
checks in Chromium. The Next.js snippets come from the Next.js 16 Turbopack
fixture. The Next.js 15 and webpack fixtures use the same files. The check
confirms that Inth's banner and dialog keep their styles under Tailwind's
preflight, that a padding utility on the banner root
beats Inth's own padding, and that the `dark:` variant applies. The fixtures run
without a backend, so they use `testing()` mode or a local `projectUrl`. Keep the
`mode` or `projectUrl` from your quickstart.

## Set up Tailwind CSS 4

Install Tailwind's plugin for your build tool and add it to the build. Inth
loads its own styles in every framework, so your CSS entry holds only
Tailwind. Do not import Inth's stylesheet next to Tailwind 4: the stock
components already render the same rules, and the import would hold back the
first paint.

## Set up Tailwind CSS 3

Tailwind 3's preflight is unlayered, so it beats the layered rules Inth
renders itself and strips the banner's padding and borders. On Tailwind 3,
turn those rules off with `styles: false` and import Inth's `styles.css`
through a PostCSS plugin. The Astro integration needs only the plugin: it
detects Tailwind 3 and links `@inth/astro/styles.css` itself. Every Inth
package that ships a stylesheet exports the plugin as
`<package>/postcss-tailwind3`, so use the one from the package you installed:

| You installed | Plugin name |
| --- | --- |
| A framework package, such as `@inth/react` or `@inth/svelte` | That package's plugin, such as `@inth/react/postcss-tailwind3` |
| `@inth/sdk` (script tag in the light DOM) | `@inth/sdk/postcss-tailwind3` |

They are the same plugin.

Make four changes:

1. Set `styles: false` where you configure Inth: `options` in Next.js
   `inth.config.ts`, `options` on `InthProvider` in TanStack Start and React,
   and `styles={false}` on `InthProvider` in Svelte and SvelteKit.
   Vue, Nuxt and Astro need no change.
2. Add the plugin to your PostCSS plugins, before `tailwindcss`. Write the plugins as an object, as the examples below do.
   PostCSS runs them in the order of the keys. Next.js also accepts an array
   of plugin names, but Vite's PostCSS loader rejects that form.
3. Import Inth's stylesheet above the `@tailwind` directives, whatever your
   build tool. Vue, Nuxt and Astro skip this step. Vite drops an `@import`
   that follows another rule, with the warning
   `@import must precede all other statements`, and the banner renders
   unstyled. Next.js 16 with Turbopack fails the build.
4. Set `darkMode: 'class'` so Tailwind's `dark:` variant follows the same
   `dark` class Inth reads.

The plugin also processes the stylesheets the Vue and Nuxt components import,
and the one the Astro integration adds on a Tailwind 3 site. Without it,
Tailwind 3 stops
the build with "`@layer components` is used but no matching
`@tailwind components` directive is present", or purges Inth's rules, because
Inth's class names never appear in your source.

Tailwind 3 has no cascade layers, so Inth's selectors outrank a single utility
class. Add the important modifier to utilities you pass to Inth parts:
`!bg-red-500`, `hover:!bg-red-500`. A bare `bg-red-500` has no effect. Theme
tokens work the same on Tailwind 3 and 4.

Create React App ignores PostCSS config files, so Tailwind 3 cannot run the
plugin and the build fails on Inth's stylesheet. Add the plugin before
`tailwindcss` through CRACO, eject, or move the app to Vite.

## Put utilities on Inth parts

Pass utilities to a component part through your framework's part API. The
fixtures put padding on the banner root, which Inth also pads, with a different
value in dark mode. On Tailwind 4 a plain utility wins. On Tailwind 3, add `!`,
as in `!p-[7px] dark:!p-[11px]`, because Inth's unlayered rules outrank a plain
utility. [Component parts](/docs/customization/slots) lists the parts each
framework exposes.

Tailwind only generates classes it finds in the files its `content` globs or
`@source` rules scan. Keep part classes in a scanned file.

## Use the dark variant

The fixtures make Tailwind's `dark:` variant follow a `dark` class on `<html>`:
`@custom-variant dark (&:where(.dark, .dark *));` on Tailwind 4 and
`darkMode: 'class'` on Tailwind 3. Inth's stylesheet reads the same class, and
in React, Next.js, TanStack Start, Vue, Nuxt, Svelte and SvelteKit an unset
`colorScheme` also copies it into `inth-dark`. One toggle then switches your
utilities and Inth's dark tokens together.

Astro and the script tag follow the system setting by default. [Dark mode](/docs/customization/dark-mode) covers each
case.

## Render the UI in the light DOM

The script tag and `init()` render into a shadow root, so your page's CSS does
not reach Inth and Inth's CSS does not reach your page. To style the UI with
your page's Tailwind build directly, render it in the page with
`data-shadow="false"` or `ui: { shadow: false }`.

On Tailwind 4, that is the whole change. Inth still injects its layered
stylesheet, and the layer order keeps it above preflight:

<include src="../shared/examples/tailwind-v4/html/script-tag-light-dom.mdx" />

On Tailwind 3, keep the default shadow root. Tailwind 3's preflight is
unlayered, so in the page it beats Inth's layered rules whatever their
specificity and removes the button padding and card borders. Linking
`inth.css` from the page does not help, because nothing removes its layers.

To render in the light DOM anyway, turn the injected sheet off with
`styles: false`, and build Inth's rules into your Tailwind CSS with the plugin
instead:

<include src="../shared/examples/tailwind-v3/html/script-tag-light-dom.mdx" />

Import `@inth/sdk/styles.css` above the directives in your Tailwind entry.
Install `@inth/sdk`, which provides both the stylesheet and
`@inth/sdk/postcss-tailwind3`:

<include src="../shared/examples/tailwind-v3/html/tailwind-css-light-dom.mdx" />

<include src="../shared/examples/tailwind-v3/html/postcss-config.mdx" />

In the light DOM your page's global rules reach the banner too, so check
buttons and headings after the switch.

## Check the result

1. Build the app and open it in a private window. The banner has its card
   background, border and button padding, so preflight did not reset it.
2. Inspect the part you gave a utility. In the Styles panel, your utility is
   applied and Inth's rule for the same property is struck out.
3. Add the `dark` class to `<html>`. Your `dark:` utility applies and, where
   Inth follows the class, the banner switches to dark colors.
4. Open the preference dialog. Its rules come from a separate stylesheet in
   most frameworks, so check that it is styled too.
