title: Native IAB commits
description: Native CMP configuration, complete IAB drafts, atomic persistence, restart validation, and exact backend delivery in Swift and Kotlin.
---

The Swift and Kotlin cores own IAB choices and generate TC strings without a JS
runtime. This contract is for native core and platform implementers. RN commands,
shared SwiftUI and Compose screens and complete platform key publication
have separate integration work.

## Configure an approved CMP identity

Pass `IABConfiguration` through Swift `CoreConfig.iab`, or `IabConfiguration`
through Kotlin `NativeConfig.iab`. Supply the approved registered CMP ID, integer
CMP version and publisher country. There is no default CMP identity. Numeric
validation accepts IDs 2 through 4095; it does not prove registration, ownership,
mobile validation or Google certification. Fixture IDs are test data and must
never become production configuration.

The owner supplied CMP ID 490 for c15t. The official [CMP registry](https://cmp-list.consensu.org/v2/cmp-list.json), updated
22 October 2026, lists 490 as `Consent Management Inc`, commercial, with the
`Web` environment only. That identifies the registrant; it does not establish
mobile approval. The owner handles registration and Google App and AC v2
certification. Mobile validation and approval of the exact native candidate builds
remain external release gates. Keep 490 explicit in deployment configuration;
it is not a universal SDK default.

Configuration also carries the disclosure language, consent screen number,
custom-purpose count and publisher restrictions. Language and country codes must
be two uppercase ASCII letters. The default language is `EN`, screen is 1 and
custom-purpose count is 0. Restrictions use TCF types 0 for not allowed, 1 for
require consent and 2 for require legitimate interest. The authority validates
each restriction against the vendor's declared and flexible legal bases.

The authoring profile is service-specific, uses standard texts and discloses
Purpose 1. The native codecs retain their existing UTC-day timestamp encoding.
The exact action time remains in the committed record and backend body.

## Commit a complete native draft

Swift `IABChoices` and Kotlin `IabChoices` hold purpose consent, purpose legitimate
interest and objections, vendor consent, vendor legitimate interest and
objections, special-feature opt-ins, publisher consent and legitimate interest,
and custom publisher purposes. An absent ID has no positive signal. Purpose and
vendor objections cannot overlap their corresponding legitimate-interest grants.
LI is prohibited for purposes 1, 3, 4, 5 and 6. Unknown IDs and duplicates reject
the whole action. Native codecs prune vendor signals that have no supported basis;
the committed choices expose that normalized result.

Use Swift `save(.iab(choices, categories: categories), expectedRevision: revision)`
or Kotlin `save(CommitIntent.Iab(choices, categories), expectedRevision = revision)`.
Custom IAB saves require a revision and otherwise reject with `iab-draft-required`.
Prefer `openIABDraft` and `saveIAB` on Swift, or `openIabDraft` and `saveIab` on Kotlin.
Capture the revision when opening the native draft. A changed revision rejects
with `concurrent-change`, leaving the current decision intact. The category map
records the app categories this action confirmed; it is separate from IAB purpose
and vendor permissions.

Under an IAB policy, `all` grants what the disclosed vendors declare after
publisher restrictions, as the web's Accept All does: purposes and special
features some vendor declares, legitimate interest only where a vendor claims
it, and purposes 1, 3 and 4 when Google ad tech providers are listed. Publisher
purposes stay unset. `necessary` withdraws every optional IAB signal. A category-only custom action rejects with
`iab-choices-required`. Missing CMP configuration or a missing disclosed GVL
rejects with `iab-unavailable`. An IAB draft under another policy also rejects.
Configuration and selection validation failures report `invalid-iab-choices`.

Read the current committed record through Swift `iabConsent()` or Kotlin
`iabConsent`. Native vendor startup can call Swift `isIABAllowed` or Kotlin
`isIabAllowed`, supplying both vendor ID and purpose ID with the intended legal
basis. These checks include expiry, policy validity and publisher restrictions.
A category grant alone does not authorize an IAB vendor-purpose pair.

## Persist and deliver one decision

Before publishing a grant, the core atomically replaces one protected snapshot
item containing the evaluated snapshot, complete IAB record, consent version,
generated TC string and immutable pending HTTP body. No second queue write is
needed for an IAB commit. A failed authoritative write rejects the action with
`queue-write-failed` and preserves the previous state and pending body.

Swift `ConsentStore.set` must atomically replace an item and return only after
storage acknowledges it. Kotlin `KeyValueStore.writeDurably` has the same
obligation. Buffered adapters must override it. The Android fallback uses
synchronous SharedPreferences `commit`; an in-memory `apply` acknowledgement is
insufficient. The encrypted file adapter syncs a temporary file before renaming
it and preserves the previous file if replacement fails. Vendor storage is a
projection; a failed mirror write cannot undo the authoritative commit.

`committed` means local persistence succeeded. It does not mean the backend
accepted the request. Delivery sends `tcString` and `model: "iab"` through the real
`POST /subjects` contract beside category receipts, policy inputs, identity and
`givenAt`. Retry and restart reuse the exact saved HTTP bytes, including their
original domain. Retry bookkeeping updates the same envelope without changing
the decision or body. Grant entries keep their attempt and retention ceilings.
Full denials remain owed until delivery, even beyond those ceilings, including
category withdrawals queued before a switch to IAB. A new full denial supersedes
older queued actions for exactly the same subject ID, external ID and domain.
The queue keeps the newest frozen body unchanged. A later grant retains the owed
denial. Distinct owners never coalesce. If distinct owners fill all 20 slots,
`queue-write-failed` refuses an action that cannot fit and preserves the stored
state. Repeating a denial for an existing owner can still replace its slot.

A newer IAB decision supersedes older queued grants. Remaining withdrawals keep
their original identity, external ID, domain and exact body.
A withdrawal cannot replay an older queued acceptance. Grant delivery checks the
actual saved body against current TC authority, identity and action time. A full
withdrawal has no category, purpose, vendor, publisher, special-feature or LI grants
and can be delivered after the current authority expires or changes. A request
already on the network may finish after a withdrawal; the core cannot recall it.

Backend consent IDs include `givenAt`. The core advances IAB action times by at
least one millisecond, even when the clock repeats. A durable timestamp watermark
survives reset and identity changes so a later decision cannot reuse an earlier
action-time input. If a backward clock jump would put the next logical action
more than ten minutes ahead of the wall clock, the save refuses with
`invalid-action-time` before changing consent or storage. The watermark survives
restart; the host must correct the clock before retrying. This does not establish
live backend acceptance or matching backend consent IDs. The TC creation day stays
unchanged across edits to the same consent record; consent version increments per
successful decision.

Both cores serialize snapshot mutations through a gate separate from the short
in-memory state lock. Preparation, revision validation, durable write and state
publication share that gate. Category actions, identity changes, reset, hydration,
overrides, notice dismissal and init results use the same serialization. Queue
settlement edits only its entry under the queue or store lock and preserves the
latest envelope. Synchronous snapshot, permission, IAB and gate reads remain
available while a store write blocks. A storage callback may use these reads.
A refused write leaves the previous envelope and creates no pending body.
Network delivery, host loggers and error observers run after releasing the
mutation gate.

## Hydrate and invalidate authority

Hydration validates stored IAB choices before exposing authority. It checks CMP
and publisher configuration, subject and external identity, policy fingerprint,
GVL and TCF policy versions, expiry and regenerated TC bytes. Invalid or expired
records lose their grants and pending grant deliveries. Frozen withdrawals keep
their delivery obligation through expiry, clock skew, GVL, policy, model,
configuration and fingerprint changes. A changed list or configuration requires
a fresh decision. The release uses the conservative refresh and retention rules
below. A compatible list within its age limit can support offline commits.

An IAB policy requires valid native authority for every optional category,
including categories outside a permissive policy scope. Legacy category-only
envelopes and backend category receipts cannot restore IAB grants, even when the
host has no native CMP configuration. Reject all can still record a pure
category-only withdrawal when CMP configuration or a GVL is missing. Older SDKs reject envelopes with unknown authority fields and require
a fresh decision; do not rely on downgrades preserving these choices.

On Swift cold launch, an omitted `CoreConfig.user` restores the external ID from
the authoritative stored snapshot. An explicitly configured user takes precedence.
Calling identify with that same stored ID preserves valid consent. Logout stores
an anonymous identity, so a later launch cannot restore the signed-out account.
The host supplies external identity; the SDK never derives it from hardware.

Repeating identify with the same external ID and logout while already anonymous
preserves consent and the queue. Changes to actual IAB authority and reset
atomically persist empty consent authority while retaining frozen withdrawals
under their original delivery owner. Under an ordinary category policy, merely
configuring IAB or retaining an old withdrawal does not change identify behavior. The installation subject ID remains unchanged. A failed write keeps the previous
identity and consent state and emits `identity-write-failed` or
`reset-write-failed`. Reset retains app configuration and the installation subject
ID, then requests a new policy. These operations do not erase backend audit
history. A durable empty record avoids restoring an earlier acceptance after a
failed deletion.

## Verify the contract and remaining release gates

`packages/native-protocol/iab/commit-cases.json` comes from the pinned reference codec.
Both native suites consume it for acceptance, rejection, custom choices,
objections, publisher restrictions and publisher purposes.
`packages/native-protocol/iab/accept-all-declared-signals.json` holds a real served GVL
and what the web's Accept All encodes for it, with and without publisher
restrictions. Native tests also exercise file restart,
failed writes, concurrent commits, expiry, identity transitions and withdrawal.
The fixture generator and its Vitest test are development tools only.

This work does not establish device behavior, vendor SDK interoperability,
performance, registry publication or certification. First release still requires
native UI rendering of TCF 2.4 disclosures, including the preserved
`standardTexts.features`, approved CMP identity and mobile registration, complete
typed IABTCF publication before vendor startup, Google App certification and
RN AC v2 API and UI integration. ENG-510 and the RN acceptance gate of ENG-511
remain required. The selected native screens and RN adapter must consume this authority
without creating a JS consent or TCF engine.

## Recover a missing or corrupt subject

Core hydration owns identity recovery, including raw bootstrap and custom-core
attachment. Missing or undecodable identity with stored records clears the
consent envelope and queue before exposing any restored choice. It emits
`subject-id-missing` or `subject-id-corrupt` once per core launch. A mismatched
envelope emits `subject-id-mismatch`. A normal first launch emits none of these.
Swift checks every public `hydrate()` call; Kotlin checks bootstrap and subject
resolution. The installer must keep its storage probe and refusal behavior and
leave record sanitation to the core so hosts receive these diagnostics.

## Verify native compatibility

The development oracle uses pinned `@iabtechlabtcf/core` 1.5.22. Both native suites
compare actual bytes for ID gaps, deleted vendors, restriction adjacency,
three-day and year-long creation/update intervals, a 133-vendor sparse list and
an excerpt of official TCF 2.4 GVL 182. The excerpt records its source URL and the
SHA256 of the complete fetched document. These fixtures do not submit any CMP
identity for certification.

Custom Kotlin stores must implement `writeDurably` and acknowledge their actual
storage operation. The default refuses without changing data. Memory-cache
readback cannot establish durability. Power-loss behavior, directory fsync and
device latency for full-envelope queue I/O remain unproven release gates.

## Refresh disclosures and work offline

A fresh native GVL remains usable for seven days by default. Configure
`iabListMaxAgeMs` to shorten the limit. Fetch time persists with the authority;
a successful response without a GVL clears offline status but does not renew the
fetch time. A failed retry against unchanged cached authority preserves an open
draft's revision and leaves its snapshot and stored envelope unchanged. Transport
failures still reach the error stream. A future fetch time or
missing fetch time is stale. An old envelope without disclosure binding needs
fresh consent. The `gvl-v2:` binding format also rejects older projected hashes
on hydration because their stored lists may have discarded disclosure fields.
Upgrading those records requires a new decision.

`iabStatus` returns a small availability record and the list and policy versions.
It distinguishes unavailable CMP configuration, missing list, fresh network
list, cached startup, offline cached list and stale list. This read does not
serialize the GVL. Offline cached consent remains valid only while both the
list and choice are within their age limits. Stale lists deny native gates,
refuse drafts and grants, and require a successful list refresh. Reject all can
still commit a category-only withdrawal without encoding a stale disclosure.
List staleness keeps the saved choice and frozen queued grants dormant. An
identical refreshed disclosure restores them while the choice remains current;
choice expiry or incompatible disclosure discards them. No grant is delivered
while its list is stale. Installed foreground and connectivity callbacks finish
replaying pending saves before refreshing policy. The Swift `replayThenRefresh()`
call schedules that sequence and joins an existing delivery pass without blocking
the lifecycle callback. A
one-shot list or choice deadline publishes denial to existing gates without a
network request. Repeated Kotlin snapshot reads return the same instance until
state or authority availability changes. Reopen preferences after refreshing.

This release retains a choice only when CMP and publisher configuration,
identity, policy fingerprint, list version, policy version and the complete
normalized disclosed content all agree. A SHA-256 binding also detects a
changed disclosure served under the same list number. Any difference clears
all IAB grants and obsolete queued grants and requests a new decision. This
includes additions, removals, legal-basis changes, publisher restrictions and
changed standard explanations. No previous grant extends to a new vendor or
purpose. The SDK never turns a refresh into a consent action or regenerates an
old save against new disclosures.

The GVL retains `standardTexts.features` and its other standard explanations
and unknown top-level or nested disclosure fields through narrowing, persistence
and native disclosure reads. Their normalized content participates in the same
binding. Fetch the full list
once when opening a presenter. Use the compact lifecycle record during an open
session. Saves require the revision the presenter opened on, so a refresh or
competing save rejects the old draft with `concurrent-change`. The caller keeps
the rejected draft for explanation, then reloads a compatible disclosure before
asking for another action.

## Commit Google Additional Consent v2

The native cores read the backend's configured `adTechProviders` response. The
backend resolves those IDs from Google's official ATP list and removes providers
Google no longer lists. ATP IDs are a separate namespace from GVL vendor IDs.
The response contains each provider's `id`, `name` and `policyUrl`; native readers
reject duplicate IDs, invalid IDs, empty names and invalid policy URLs as a whole
list. They keep the disclosed list with its fetch time in the same protected
record as TCF.

An absent list keeps an unexpired cache without renewing its age. An explicit
empty array disables AC and invalidates an earlier AC choice. An invalid list
clears it. Any provider addition, removal, name or policy-link change requires a
new native decision. `additionalConsentStatus` distinguishes a missing or stale
list. `adTechProviders` returns current disclosures once for a native presenter.
The next expiry deadline includes the bound ATP cache. If a response renews the
GVL but omits ATPs, the older ATP deadline still revokes existing gates, clears
obsolete queued grants and removes the published AC value without a new read.

Set `adTechProviderConsents` on the complete IAB draft. Native validation rejects
IDs outside the disclosed ATP list. A selected ATP receives consent only when
TCF purposes 1, 3 and 4 are all consented. Otherwise it remains disclosed without
consent. The committed choices expose this normalized result. Read
`IABCommittedConsent.addtlConsent` or `IabCommittedConsent.addtlConsent` and use
`isAdTechProviderAllowed` for a synchronous ATP gate. ATT permission stays
separate and does not change any ATP or TCF choice.

Native encoding follows [Google's AC v2 specification](https://support.google.com/admanager/answer/9681920):
`2~<consented IDs>~dv.<disclosed IDs without consent>`. IDs sort numerically, and a
consented provider occurs only in the consented section. For providers 1, 2, 3,
4 and 10, selecting 1 and 10 produces `2~1.10~dv.2.3.4`. Rejecting all produces
`2~~dv.1.2.3.4.10`. An empty configured list produces no AC string.

`addtlConsent` travels beside `tcString` in the real native `POST /subjects`
body. It shares TCF's atomic commit, identity binding, action time, offline replay
and rejected-write behavior. Retries reuse the exact saved body. A stale ATP
list cannot authorize another grant. Withdrawal can still commit TCF denials
without an AC string if the ATP list is stale. The backend clears its AC value
when it receives a TC string without `addtlConsent`.

The native bus writes `IABTCF_AddtlConsent` as a string into UserDefaults and the
application-default SharedPreferences. Withdrawal publishes the disclosure-only
AC string for a current list. Invalid authority, identity changes and reset
remove it. The complete typed TCF bus and its publication ordering are documented below.

This is the ENG-511 native foundation. Typed RN public adapters, compact events
and IAB UI integration remain a required ENG-511 acceptance gate through ENG-514
and ENG-533. Native presenters must show every disclosed provider and privacy
link before a save. This work does not establish Google App or AC v2 approval.

## Publish the typed vendor storage bus

The cores publish a projection into standard UserDefaults and application-default
SharedPreferences during synchronous bootstrap, before JS or network work. An
explicit, valid native `IABConfiguration` supplies CMP detection immediately.
There is no default CMP ID. Detection does not imply mobile registration or
Google certification. The configured identity must have the required approval
before an app ships.

The [IAB CMP API v2 in-app storage table](https://github.com/InteractiveAdvertisingBureau/GDPR-Transparency-and-Consent-Framework/blob/master/TCFv2/IAB%20Tech%20Lab%20-%20CMP%20API%20v2.md#what-is-the-cmp-in-app-internal-structure-for-the-defined-api)
sets the following contract. Consent rows come from the exact committed TC
bytes, including shaped vendor vectors. Number means a native integer, read with
`integer(forKey:)` on Apple and `getInt` on Android. String means a native string.

| Key | Native type | Source |
| --- | --- | --- |
| `IABTCF_CmpSdkID` | Number | Explicit configuration at initialization; committed CMP ID after a decision |
| `IABTCF_CmpSdkVersion` | Number | Explicit configuration; committed numeric CMP version |
| `IABTCF_PolicyVersion` | Number | Current GVL; committed TCF policy version |
| `IABTCF_gdprApplies` | Number | Resolved policy, 1 for IAB, 0 otherwise; absent while undetermined |
| `IABTCF_PublisherCC` | String | Committed publisher country |
| `IABTCF_PurposeOneTreatment` | Number | Committed flag, currently 0 for authored consent |
| `IABTCF_UseNonStandardTexts` | Number | Committed flag, currently 0 for authored consent |
| `IABTCF_TCString` | String | Exact committed TC String |
| `IABTCF_VendorConsents` | String | Vendor consent bits |
| `IABTCF_VendorLegitimateInterests` | String | Vendor LI bits |
| `IABTCF_DisclosedVendors` | String | Disclosed vendor bits |
| `IABTCF_PurposeConsents` | String | 24 purpose consent bits |
| `IABTCF_PurposeLegitimateInterests` | String | 24 purpose LI bits |
| `IABTCF_SpecialFeaturesOptIns` | String | 12 special-feature bits |
| `IABTCF_PublisherRestrictions{ID}` | String | Restriction types by vendor for that purpose |
| `IABTCF_PublisherConsent` | String | 24 publisher purpose consent bits, when its segment exists |
| `IABTCF_PublisherLegitimateInterests` | String | 24 publisher purpose LI bits, when its segment exists |
| `IABTCF_PublisherCustomPurposesConsents` | String | Declared custom-purpose consent bits |
| `IABTCF_PublisherCustomPurposesLegitimateInterests` | String | Declared custom-purpose LI bits |
| `IABTCF_AddtlConsent` | String | Committed [Google AC v2 value](https://support.google.com/admanager/answer/9681920) |

Bit position zero represents ID 1. Vendor widths follow the committed TC
segments. A vendor consent bit can remain set while a publisher restriction
disallows one of its purposes. Consumers must combine the relevant purpose,
vendor and restriction signals. Restriction keys have a numbered suffix.
Unrestricted positions contain `_`, following the IAB reference
[`InAppTCData` implementation](https://github.com/InteractiveAdvertisingBureau/iabtcf-es/blob/master/modules/cmpapi/src/response/InAppTCData.ts).
The obsolete unnumbered prefix and all numbered restriction keys are removed
when omitted by a replacement publication. Keys outside this table stay intact.

Android replaces the entire map in one `SharedPreferences.Editor.commit()`
transaction. Apple removes TCString and AC first, writes and checks associated
values, publishes AC, then publishes TCString last. Apple has no multi-key reader
transaction. Consumers must observe TCString changes and reread associated
values. A consumer holding an earlier cached string across an update must discard
that cached data. Arbitrary concurrent multi-key reads are not an atomic API.

A rejected authoritative commit preserves the previous bus while its authority
remains current. Publication rechecks authority after durable storage I/O, so an
expired disclosure cannot publish grant rows. A rejected or partial mirror
publication removes the owned values and retries on a later
publication, cold bootstrap or `core.rebuildTcStorageBus()`. Repair uses current
native authority and its clock, never raw stored grants or vendor values.
Mirror writes run outside the core state lock. Queue-only replay bookkeeping
does not republish stored consent rows after current authority has expired.
Android's raw `C15tStore.rebuildTcStorageBus()` restores metadata only because a
store cannot validate current authority. If authority invalidation cannot persist,
the bus still removes its grants. Complete storage failure can also prevent a
cleanup write; startup refusal and vendor initialization remain host duties.

Withdrawal publishes denied vectors and disclosure-only AC for current lists.
Reset, identity transitions and policy/list invalidation remove consent rows.
CMP detection remains while that configured core is installed. Uninstalling a CMP
requires clearing all its vendor-storage values. Refresh on foreground and
connectivity changes; a bus read is not a call into the native gate or its clock.
The SDK does not claim that a suspended process updates preferences at an expiry
instant.

Shared independent-codec fixtures cover the projected values, including sparse
IDs, deleted vendors and custom purposes. Platform tests read actual UserDefaults
and SharedPreferences values, exercise cold restart and write refusal, and repair
a damaged mirror. These tests do not establish device performance, power-loss
persistence, interoperability with a real ad SDK or certification. The AdMob
reference remains the vendor SDK proof gate in ENG-519.
