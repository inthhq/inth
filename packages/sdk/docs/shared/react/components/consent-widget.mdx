<section id="behavior">
  ## Behavior

  `ConsentWidget` renders the preference center inline without a modal: an accordion with one row and switch per category, followed by Reject All, Accept All, and Save Settings actions. `ConsentDialog` renders this widget inside its card. Standalone, it renders in place during SSR and never modifies the active surface, fitting a privacy page or account settings screen.

  Rows include `necessary` plus categories in the active policy's scope that the provider declares through `options.consentCategories`, scripts, network rules, vendors, or discovered frames. When nothing is declared, a permissive policy lists only `necessary` and a strict policy lists its full scope. The `necessary` switch is always on and disabled. Row copy comes from `consentTypes.<category>.title` and `.description`; action labels come from `common.rejectAll`, `common.acceptAll`, and `common.save`. One row expands at a time.

  ### Draft and save

  Toggling switches edits a draft without changing live permissions until the visitor saves. The draft seeds each category off when an active durable opt-out or Global Privacy Control (GPC) signal restricts it, even when a stored choice granted it. Otherwise it reads the recorded choice, then `presentation.preferences.defaults` from the provider options, then the policy default (on under an opt-out rule and on only for preselected categories under an opt-in rule). Save records the displayed categories and reseeds the draft. Accept All and Reject All record immediately. Saving answers a choice prompt and closes an open choice banner, while leaving a `notice` prompt open until acknowledged. Unsaved toggles reset when the widget unmounts.

  If the policy changes in a way that affects choices while the draft has unsaved edits, the widget displays an alert, "The privacy policy changed. Review the current choices before saving.", with a Review choices button that resets the draft, and blocks saving until reviewed. A clean draft reseeds silently.

  ### Sale-and-sharing opt-out block and locked switches

  Under an `opt-out` policy, the widget renders a sale-and-sharing block first, above the category list and outside any accordion item. Under any other policy model, no block renders and the layout stays unchanged.

  - Before the visitor opts out, the block displays the configured opt-out link title from `presentation.optOutLink`, a neutral status sentence (`optOut.notOptedOut`), and an `Opt out` button (`optOut.action`). One click records the opt-out immediately through the same shared action as the opt-out link, with no category toggle and no Save step.
  - Once a durable opt-out is held, the button is removed and the block shows the status line (`role="status"`) with "Opt-out request honored" for a visitor request or "Opt-out preference signal honored" when Global Privacy Control recorded or enforces it. Below the status line, the block renders the same receipt sentence, recorded time, and local reference as `OptOutConfirmation`. When a backend response confirms the refused rights, the heading names them (`sale` and `share`, `sale` and `targeted_ads`, or all three); before confirmation, it keeps the configured link title. When GPC is not locking the opt-out, an `Opt back in…` link appears below the receipt.
  - While the browser's GPC signal is active under a policy that maps it, the signal-restricted switches and `marketing` (or `measurement` when `marketing` is not in scope) stay off and disabled, and no `Opt back in…` link appears. A notice below each locked row explains why and connects to the switch with `aria-describedby`. Save Settings and Accept All do not present or grant locked categories.
  - When an account holds the opt-out and GPC is off, the notice appears below `marketing` (or `measurement` when `marketing` is not in scope) to explain that the account has opted out, and the switches stay usable. Turning `marketing` back on and saving, clicking Accept All, or clicking `Opt back in…` opens a separate confirmation dialog first. Confirming asks the backend to lift the account opt-out, and a refused request leaves it in place.
  - When a device holds the opt-out and GPC is off, opting back in requires two steps under an `opt-out` policy (11 CCR §7028(a)). Turning `marketing` back on and saving, clicking Accept All, or clicking `Opt back in…` opens a separate confirmation dialog (`measurement` decides when `marketing` is not in scope). Focus starts on `Stay opted out`, both buttons have equal prominence, and Escape cancels with nothing saved. Confirming lifts the opt-out and applies the pending save. Turning `measurement` back on while `marketing` stays off keeps `measurement` allowed, skips confirmation, and leaves the opt-out in place. Saving without changing a switch keeps the opt-out in place. Under an `opt-in` policy, Accept still lifts a held opt-out in one step.

  Read the same derived opt-out state and receipt in custom components with `useOptOutState()` and `useOptOutReceipt()`.

  ### Vendors

  When the provider declares `vendors`, each expanded category ends with one collapsible card per vendor whose condition names that category: vendor name and switch in the header, description and privacy policy link inside. Cards start collapsed so long lists stay compact and scroll inside the dialog. Collapsed categories and vendor cards leave their content unmounted until first expanded, avoiding extra render work upfront.

  Vendor switches edit the same draft and record on Save. Disabling one vendor denies only that vendor while keeping the category and its other vendors active. While the parent category is off in the draft, its vendor switches disable with the hint "Turn on this category to choose vendors." Vendors marked `disabled`, or limited to `necessary`, render without a switch. Accept All and Reject All clear all vendor denials, including unsaved ones. Under an `iab` policy, no vendor rows render. Vendors referenced only by script slug without a name and privacy policy URL, or with negated category conditions, still gate loading without appearing as rows. See [vendor consent](../vendor-consent).

  ### Actions

  The preference center always shows Reject All, Accept All, and Save Settings, with Save Settings marked primary. `presentation.preferences.layout`, `primaryActions`, `direction`, and `uiProfile` in the provider options reorder and restyle them; any omitted action is restored. Customize and dismiss never appear here.

  ### When consent is not owed

  Without a resolved policy rule, the widget renders nothing and appears automatically once a rule resolves. A rule with `model: 'none'` and an empty `rights` list renders nothing; a `none` rule listing any right such as `['disclosure']` renders the widget and Save finishes without writing a consent record.

  For a custom preference center, `useConsentDraft()` returns the same draft: `values`, `displayedCategories`, `vendors`, `isDirty`, `isStale`, `set`, `update`, `setVendor`, `acceptAll`, `rejectAll`, `save`, and `reset`. For custom vendor controls alone, `useVendorDraft()` exposes the vendor slice: `vendors`, `setVendor`, `isDirty`, `isStale`, `save`, and `reset`. `useDeclaredVendors()`, `useVendorChoice()`, and `useVendorAllowed(id)` read the declared list, recorded denials, and per-vendor effective state.
</section>

<section id="accessibility">
  ## Accessibility

  Each row is a disclosure pairing a button that expands the description with a switch beside it, so visitors can read descriptions without toggling consent. Each switch uses the category title as its accessible name. Vendor cards sit inside a `region` labelled "Vendors" with the count; each card toggle sets `aria-expanded`, and each vendor switch is named "Allow" plus the vendor name and described by the vendor's name element. The policy-change alert uses `role="alert"`, and restriction notes use an `output` element linked with `aria-describedby`. The root sets `dir` from the active language.
</section>

<section id="composition">
  ## Composition

  Every part is available as `ConsentWidget.<Part>`. `Root` supplies the draft and accepts `noStyle`, `disableAnimation`, and `uiSource`. `OptOut` renders the direct sale-and-sharing block above the category list under an `opt-out` policy; `OptOutStatus` renders the honored opt-out status line (`role="status"`). `Accordion` and `AccordionItems` render the built-in rows; `AccordionItem`, `AccordionTrigger`, `AccordionTriggerInner`, `AccordionContent`, `AccordionArrow`, and `Switch` let you build custom rows; `VendorList` renders one category's vendor rows for a `category` prop. `PolicyActions` renders the resolved actions inside `Footer` and `FooterSubGroup` and accepts `renderAction` to replace any button; `AcceptAllButton`, `RejectButton`, `SaveButton`, and `CustomizeButton` render individual buttons.

  `Accordion` is controlled: pass `value` and `onValueChange` or no category description opens. The built-in `ConsentWidget` manages that state for you. In this snippet, `ConsentWidget` comes from the same import shown at the top of the page:

  ```tsx
  import { useState } from 'react';

  export function PreferenceCenter() {
    const [open, setOpen] = useState<string[]>([]);

    return (
      <ConsentWidget.Root>
        <ConsentWidget.Accordion
          value={open}
          onValueChange={(next) => setOpen(Array.isArray(next) ? next : [next])}
        >
          <ConsentWidget.AccordionItems />
        </ConsentWidget.Accordion>
        <ConsentWidget.PolicyActions />
      </ConsentWidget.Root>
    );
  }
  ```

  Provider component slots for the built-in layout are `manager.root`, `manager.optOut`, `manager.optOutStatus`, `manager.footer`, `manager.actionGroup`, `accordion.root`, `accordion.triggerRow`, `accordion.title`, `accordion.control`, `accordion-item.root`, `accordion-item.trigger`, `accordion-item.content`, `vendor-list.root`, `vendor-list.trigger`, `vendor-list.content`, `vendor-list.item`, `vendor-list.header`, `vendor-list.name`, `vendor-list.description`, `vendor-list.link`, `vendor-list.control`, and `tag.manager`.

  `ConsentWidget` from the package root and `@inth/react/consent-widget` loads its code in a separate chunk on first render, keeping pages that never render it smaller. `@inth/react/components/consent-widget` exports the widget without deferral plus each part as a named export.
</section>

<section id="verify">
  ## Verify

  Open the page with the widget and test an optional in-scope category not restricted by policy or GPC. Confirm one row appears per displayed category with `necessary` on and disabled. Toggle the category on and confirm `useConsent('<category>')` elsewhere still returns the previous value. Click Save and confirm it updates to `true`. An open choice banner closes when the save answers its prompt; a notice banner stays open until acknowledged. Reload the page and confirm the switch keeps the saved state. Without a saved choice or configured draft defaults, optional switches start on under an opt-out rule.
</section>
