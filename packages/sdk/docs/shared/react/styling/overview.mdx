<section id="tailwind-layers">
  Inth places its rules in the `components` cascade layer, and each `<style>` element the components render opens with Tailwind CSS 4's layer order, `@layer properties, theme, base, components, utilities;`. Unlayered CSS, Tailwind 4 utilities, and StyleX atomic classes override Inth's rules without specificity tricks, whichever stylesheet loads first. [Stylesheets and CSS layers](/docs/customization/stylesheets) explains the layer order and which file holds the dialog rules.

  Tailwind CSS 3 has no cascade layers, so its unlayered preflight beats Inth's layered rules. Set `styles: false` in the provider options, import `styles.css` above the `@tailwind` directives, and add the `@inth/react/postcss-tailwind3` PostCSS plugin before `tailwindcss`. Utilities you pass to Inth parts then need the important modifier, such as `!bg-red-500`. [Tailwind CSS](/docs/customization/tailwind#set-up-tailwind-css-3) shows the tested setup for each framework.
</section>

<section id="tokens-intro">
  Colors, radii, shadows, typography, and motion come from `--inth-*` custom properties. The component `<style>` elements set the defaults, as does `styles.css` when you import it with `styles: false`. To change them, render `ConsentTheme` with your theme on the server, or override the variables directly in CSS.

  `ConsentTheme` renders a `<style id="inth-theme">` element with the variables for `theme`. It is not a client component: rendered from a Server Component or another server-only file, the theme generator stays out of the browser bundle. Rendered from a client component it still works, but the browser downloads the generator, about 1.7 KB gzip. The provider does not turn `theme` tokens into CSS. It reads `consentActions` and slot styles from its `theme` option, and warns in development when `theme` holds tokens without an `inth-theme` stylesheet on the page.

  | `ConsentTheme` prop | Purpose |
  | --- | --- |
  | `theme` | Colors, `dark` colors, typography, spacing, radius, shadows, and motion. Defaults to the built-in theme. |
  | `colorScheme` | `'dark'` makes the dark tokens the default before hydration. `'system'` follows `prefers-color-scheme` with a CSS media query. Omit it to follow a `dark` or `inth-dark` class on `<html>`. |
  | `nonce` | Content Security Policy nonce for the `<style>` element. |

  Pass the same `colorScheme` to `ConsentTheme` and to the provider. If your app manages dark mode through a root class, such as next-themes' `dark` class, omit `colorScheme` and include that class in the server HTML. [Dark mode](/docs/customization/dark-mode) covers `theme.dark`, `null`, and a dark first paint.

  To switch between token sets at runtime, render `ConsentTheme` from a client component and update its props, which ships the generator.

  Outside a component, call `generateThemeCSS(theme, colorScheme)` from `@inth/react/utils`. It outputs the same CSS as `ConsentTheme`. Call it on the server or at build time and place the result in a `<style>` element or stylesheet. It escapes `<`, so the output is safe inside `<style>`.
</section>

<section id="theme-migration">
  Earlier v3 alphas generated theme CSS in the browser from the provider's `theme` option. To migrate:

  1. Move the theme into a module without `'use client'` so server and client files can both import it.
  2. Render `<ConsentTheme theme={theme} />` next to the consent root from a Server Component or another server-rendered file. Pass `colorScheme` and `nonce` if you set them on the provider.
  3. Keep passing `theme` to the provider only for `consentActions` and slot styles. Remove a token-only `theme` from the provider.
  4. Components now include default tokens in their rendered rules. If you import `styles.css` with `styles: false`, keep that import.
</section>

<section id="token-roles">
  `consentActions` sets how each action role looks: `default` applies to every button, `primary` to whichever actions the policy or your props mark primary, and `accept`, `reject`, `customize`, and `dismiss` to one role each. Per-action keys win over `primary`, which wins over `default`.

  Each container has its own sizing variables. Override them in CSS when a container needs a different footprint:

  | Variable | Default | Applies to |
  | --- | --- | --- |
  | `--consent-card-width` | `min(440px, 100%)`, `480px` centred | Cards |
  | `--consent-card-offset` | `var(--inth-space-lg)` | Card distance from the viewport edges |
  | `--consent-card-panel-height` | `360px`, `320px` on phones | Card choices panel |

  The classic `--consent-banner-max-width` and `--consent-banner-wall-max-width` still set the corner and centred Card widths. See [classic variable compatibility](/docs/customization/tokens#classic-variable-compatibility).

  The footer lays out its actions by the card's width, not the viewport's. With the default `compact` profile, a card narrower than 22rem places Reject and Accept on one row and Customize on a full-width row below them.

  ## Colors by consent model

  The primary action can change while the brand color stays the same. Set `consentActions.primary` once, then pick the `layout` per policy as shown in [ConsentBanner](../components/consent-banner#per-policy-layouts).

  To give choice and notice banners different colors, scope the tokens to the root's `data-variant`. Include hover and foreground colors when overriding CSS tokens directly:

  ```css
  [data-testid='consent-banner-root'][data-variant='choice'] {
  	--inth-primary: #2f6f4e;
  	--inth-primary-hover: #24563c;
  	--inth-text-on-primary: #fff;
  }

  [data-testid='consent-banner-root'][data-variant='notice'] {
  	--inth-primary: #6b3fa0;
  	--inth-primary-hover: #55327f;
  	--inth-text-on-primary: #fff;
  }
  ```

  These colors apply to the action marked primary. Button layout and color changes do not change the policy or expire a saved choice.

  ## Slots

  Each component part is a slot. A slot accepts any attributes the element takes, so you can pass class strings or an object with `className` and `style`. Set slots on the provider under `components`, keyed by component and part.
</section>

<section id="slot-recipes">
  The root also carries `data-placement`, so you can restyle one container without touching the others. This Tailwind example gives a bottom Banner a brand-colored top edge and tighter text:

  ```tsx
  <InthProvider
  	options={{
  		mode,
  		presentation: { prompt: { container: { edge: 'bottom', type: 'banner' } } },
  		components: {
  			banner: {
  				root: { className: 'group' },
  				card: {
  					className:
  						'group-data-[placement=banner-bottom]:border-t-4 group-data-[placement=banner-bottom]:border-t-emerald-600',
  				},
  			},
  			description: {
  				banner: { className: 'group-data-[placement=banner-bottom]:text-xs' },
  			},
  		},
  	}}
  />
  ```

  `data-placement` sits on the root, so child slots use Tailwind's `group` prefix to read it.

  [Class names and CSS-in-JS](/docs/customization/class-names) shows CSS Modules, vanilla-extract, StyleX, and Emotion classes on a part.

  Set `noStyle` on a component to drop the built-in classes from every part and keep only what your slots pass. Set `noStyle` in the provider options to apply it to every component.

  [Component parts](/docs/customization/slots) lists every part key under `components` and the `data-*` attributes each part carries. Action buttons carry `data-action`, so a single rule such as `[data-action='dismiss']` styles one role across every surface. Right links are underlined text by default, so the only button on a notice is the primary action.
</section>
