<section id="when-to-go-headless">
  The built-in banner and dialog cover most designs through props, slots, and theme tokens. Go headless when your markup must be completely different: a design system component, a native sheet, or a layout the slots cannot express.

  Headless code owns the rendered controls, so it also owns the compliance outcome. The hooks return the actions a policy requires, the rights it must keep reachable, and diagnostics when your presentation drops one. Render from those lists instead of hardcoding buttons so your app adapts automatically if you add a notice region later.
</section>

<section id="banner-api">
  `banner.actionGroups` holds the resolved layout: reject and accept share a group at equal prominence, and the remaining actions follow. `banner.orderedActions` flattens that list. `banner.primaryActions` lists the actions to style as primary. Under a notice, the only action is `dismiss`, and `banner.primaryActions` contains it. `banner.preferenceControls` lists additional buttons for opening preferences. Under a notice it contains `opt-out`, which selects the "Do Not Sell or Share My Personal Information" label. The example renders that button and an "OK" button, keeping each command separate: opening preferences and dismissing the notice.

  This list is a rendering helper. It does not guarantee your UI implements every policy right. Still provide disclosure and persistent access to preferences.

  `useBannerCopy()` returns `title` and `description` for the active prompt. A notice reads `cookieBanner.noticeTitle` and `cookieBanner.noticeDescription`, then falls back to choice copy in the same language before English. `useConsentLabels()` returns `actions`, a label for each action, and `preferenceControls`, a label for each preference control. `dismiss` reads `common.acknowledge`, then `common.dismiss`. Both hooks follow the active language, fill missing keys from English, and return the same strings the built-in banner renders.

  Those hooks wrap `resolvePromptCopy`, `resolveActionLabels`, `resolveOptOutLink`, `resolveOptOutReceiptSentence`, and `resolvePreferenceControlLabels`. Each takes a translations object and ships from `@inth/sdk/engine` so code outside React can produce identical copy. Call `useOptOut()` from `@inth/react/headless` to record an opt-out in one click and open `OptOutConfirmation` under an opt-out policy, or open the preference center under other policy models. Call `useOptOutState()` to read the opt-out display state and receipt (including scope, source, recorded time, local reference, and backend-confirmed rights) for a custom confirmation view.

  `performAction` saves all categories for `accept`, none for `reject`, the current draft for `save`, records a dismissal for `dismiss`, and opens the preference center for `customize`. `banner.diagnostics` reports when a host layout drops a required action or gives equivalent actions different prominence. Review every diagnostic when configuring custom presentation.

  `banner.container` carries the resolved layout for `desktop` and `phone` (`type`, `placement`, `flow`, `edgeStyle`, and `blocking`), and `banner.blocking` the resolved blocking, so a headless surface can match the built-in banner's Card, Banner, or Drawer. The built-in banner traps focus and locks page scroll while `blocking` is true. To match that behavior, call `useFocusTrap(blocking, ref)` and `useScrollLock(blocking)` from the headless subpath with `blocking` set to `banner.isVisible && banner.blocking` and `ref` attached to your banner root element. Scroll locks are reference-counted, so the page scrolls again once both the banner and any open dialog release them.

  Inth can display consent copy in the visitor's browser language, which may run right to left on a left-to-right page. `useConsentTextDirection()` returns `'rtl'` or `'ltr'` for the active copy language. Set it as `dir` on your banner and preference center roots, matching the built-in components.

  The built-in banner and dialog render nothing under the `iab` model so the TCF surfaces inside `<IABProvider>` take over. A custom surface that handles only opt-in and opt-out should do the same: return `null` when `useModel()` is `'iab'`. Call `useIABPolicyGuard()` in it as well. It throws `IABUnavailableError` during render when the policy requires IAB and the app never mounted `<IABProvider>`, surfacing the gap in your error boundary instead of hiding the banner silently.
</section>

<section id="consent-gate">
  `useConsentGate(category)` tells a custom gate what to render for one consent category, with translated copy and an action that opens the preference center. Use it when the built-in `ConsentGate` placeholder does not fit your design, such as a design system card in front of a video or map embed. `ConsentGate` uses the same hook, so both follow identical rules.

  This gate renders its children once `marketing` is granted and the page has hydrated, shows the policy message when the policy blocks `marketing`, and otherwise renders a placeholder with a button that opens the preference center:
</section>

<section id="consent-gate-api">
  | Field | Type | Description |
  | --- | --- | --- |
  | `state` | `ConsentGateState` | `'granted'`, `'pending'`, `'denied'`, or `'policy-blocked'`. |
  | `categoryTitle` | `string` | `consentTypes.<category>.title` from your translations, or the category name if missing. |
  | `title` | `string` or `undefined` | `consentGate.title`, `Accept {category} consent to view this content.`, with `{category}` replaced by `categoryTitle`. |
  | `actionLabel` | `string` or `undefined` | `consentGate.actionButton`, `Enable {category} consent`, with `{category}` replaced by `categoryTitle`. |
  | `policyBlockedMessage` | `string` | `consentGate.policyBlocked`, or the English message if missing. |
  | `requestConsent` | `() => void` | Opens the preference center. |

  The result type is `UseConsentGateResult` and the state type is `ConsentGateState`. Render from `state`:

  - `'granted'`: the category is allowed and the page has hydrated. Render the content.
  - `'pending'`: the category is allowed, but hydration has not finished. Render nothing.
  - `'denied'`: the category is not allowed. Render a placeholder with a button that calls `requestConsent`.
  - `'policy-blocked'`: the policy uses `scopeMode: 'strict'` and excludes the category, so the visitor cannot grant it. Render `policyBlockedMessage` without a button. `necessary` is never blocked.

  Permission matches `useConsent(category)`. An opt-out policy can grant it before the visitor chooses, and a privacy signal such as GPC can override a stored grant.

  Granted content never appears in server HTML. When the server snapshot grants the category, `state` is `'pending'` in server HTML and during hydration, then turns `'granted'`, so an iframe inside a streamed `Suspense` boundary loads once. Server rendering and hydration evaluate the snapshot at its own evaluation time without reading the clock, so the gate works in statically prerendered pages.

  `requestConsent` does not grant the category because the visitor still has to save. It opens the preference center on its default view. Mount a `ConsentDialog` inside the same provider so it has a dialog to open. The built-in gate button preloads the dialog chunk on hover, focus, and idle time. `requestConsent` does not, so without a banner or dialog trigger on the page, the first open waits for that download.

  When it mounts, the hook registers the category with the provider just like `ConsentGate` so the preference center lists it. If you set `options.consentCategories` on the provider, include the category there too so the preference center shows it before any gate mounts.

  The hook renders no wrapper element. Reserve the embed's space in your markup so the page does not shift when the placeholder swaps to the embed.
</section>
