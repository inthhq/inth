The [quickstart](/docs/frameworks/sveltekit/quickstart) wires this up across four files:

| File | Role |
| --- | --- |
| `vite.config.ts` | `consentManifest` from `@inth/svelte/vite` fetches the policy. |
| `src/hooks.server.ts` | `inthHandle()` uses `manifest()` by default to resolve visitors from the fetched policy. |
| `src/routes/+layout.server.ts` | `export { loadConsent as load }` resolves each visitor on the server. |
| `src/routes/+layout.svelte` | `InthProvider state={data.consent}` renders the result. |

The plugin's position in `plugins` does not matter. It fetches the policy once Vite resolves its config, before compilation starts. Without a `projectUrl` option, it reads `PUBLIC_INTH_PROJECT_URL` (falling back to `PUBLIC_C15T_BACKEND_URL` if unset) from the environment or `.env`.

The plugin detects `sveltekit()` and keeps the snapshot on the server. `loadConsent` and `createConsentRoute()` read it with no extra import. The browser bundle never holds the snapshot; `InthProvider` receives the resolved policy from `loadConsent` instead.

Static hosts follow [build a static site](/docs/frameworks/sveltekit/rendering#build-a-static-site) instead.

On SvelteKit 3, `svelte-kit sync` resolves the Vite config, so it also runs the plugin and fetches the policy under the same error rules. SvelteKit 2.68 runs the plugin during `svelte-kit sync` as well, but logs a failed fetch and continues.

To apply policy edits without a rebuild, set `inthHandle({ mode: manifest({ source: 'runtime' }) })` and follow [fetch the manifest at runtime](/docs/frameworks/sveltekit/rendering#fetch-the-manifest-at-runtime). To have Inth resolve every visit instead, set `inthHandle({ mode: hosted() })`. The layout load then calls Inth's `/v1/consent/init`, and so does the browser on pages the server did not resolve.
