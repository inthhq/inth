### A subject move waiting for storage stays with the account that asked

- Moving the visitor to the subject ID an answer names waits for the outbox's storage transaction, which another tab can hold. When another account was identified, or the user signed out, during that wait, an `identify()` link answer, a lift or opt-out answer, or a `409 subject_conflict` for the previous account could still move the subject, or give the new account a fresh subject ID. The account and its identification are now checked inside the transaction and again just before the subject changes, so the account identified now keeps its subject. A `409 subject_conflict` for an opt-out or lift made under another account, or answered after a sign-out, no longer gives the current visitor a new subject ID, also when the act is replayed from the queue.
- An answer to an ordinary save still moves the visitor from a `sub_` ID to its UUID, as before.

### Signing in and out again during a save or init

- When a save or init started while no one was signed in, and a user then signed in and out again before it answered, the save's opt-out answer and init's records were applied, because the user was `null` both times. They now apply only when no one was identified or signed out while the request was out.

### Docs: a provider's `user` going to none signs the user out

- The React, Svelte and SvelteKit provider, Angular `provideInth()` and JavaScript runtime docs now say that changing `user` to none signs the user out of Inth, which includes an auth library that reports no user while it loads or refreshes a session. They show how to keep passing the last confirmed user while auth loads.
